# Android 待设备验证清单

`AGENTS.md` 要求：**当一个有意义的用例无法自动化时，把它写进冒烟文档并明示它仍需设备或生产
验证** —— 这份文件就是那个落点。`docs/SMOKE_TEST.md` 是网关／连接器的，不覆盖 Android UI；
`docs/DESIGN.md §7` 定的是验证**规程**（跑什么、怎么跑），这里记的是规程**跑不到的地方**。

## 什么该进这里

只有同时满足两条的用例：

1. **JVM 测试与 Roborazzi 都覆盖不到** —— 需要真实数据、真实网关状态、或一个本地 mock 造不出的
   运行时相位。仅仅"还没写测试"不算，那种情况应该去写测试。
2. **验不到会让人误判** —— 有数值或结论已经写进了 `DESIGN.md`，但那个结论从未在屏幕上确认过。

**每条必须写明"为什么自动化不了"。** 没写理由的条目会退化成永远不做的待办。

## 状态标记

`待验` 从未在设备上确认 · `已验 <版本>` 确认过，保留作回归参考 · `已失效` 相关设计已改，条目作废

## A-01 「需要你处理」分组：琥珀立柱、组头文字、计数 chip — 待验

**引入** 0.1.114 · **契约** `DESIGN.md §5.2`、`§2.7` 第 2 条

**为什么自动化不了**：本地 mock 的审批窗只开约 6 秒（`scripts/dev/mock-hermes-stream.mjs` 在收到
消息后发 `approval.request`，随即完成），2026-09-10 连拍 8 帧全是转场帧，没抓住。Roborazzi 可以
渲染 `SectionHeader`，但要构造出带 `needsYou` 分组的完整列表状态，成本高于收益。

**前置**：一个处于 `WAITING_APPROVAL` / `WAITING_CLARIFICATION` / `WAITING_ATTENTION` 的会话。
生产环境让 Hermes 跑一条需要审批的命令即可。

**判据**（2026-09-10 扩充：组头文字与计数 chip 现在也走同一个琥珀）
- 会话页顶部出现「需要你处理」分组，组头文字前有一条 3×14dp 圆角竖杠。
- 竖杠、**组头文字**、**计数 chip** 三者**同为琥珀**（`statusColor(WARN)`：浅 `#C2410C`、
  深 `#FBBF24`），与下方「今天」「前 7 天」组的**中性灰**明显不同。
- 该组行内的「等待你的确认」状态文字与上述三者**同色** —— 四处同源，不应有任何色差。

**已算过的数值**：浅色 4.92:1、深色 11.24:1，文字与图形下限都过。取值由
`DesignConformanceTest` 与 `StatusColorsTest` 双重钉死。

**2026-09-10 三次尝试均未抓到**：mock 的审批相位只持续约 2 秒随即转入 clarify，连拍 8 / 20 / 12 帧
都只捕到「运行中」。**要验这条得让真实 Hermes 跑一条需要审批的命令**，本地 mock 不够用。

## A-02 用量页图表的三档蓝 — 待验

**引入** 0.1.114（§2.6 的淡卡底基准随暖调换肤更新）· **契约** `DESIGN.md §2.6`

**为什么自动化不了**：本地 mock 不产生用量数据，用量页在开发栈里恒为空态
（2026-09-10 实拍确认）。`ChartColorsTest` 只能验色值与对比度，验不到实际绘制。

**前置**：一个有真实用量记录的身份（生产 Mac mini 上跑过若干会话）。

**判据**
- 设置 →「用量」（2026-09-11 起入口在设置页，卡片页的本周用量格已随 Stitch 基线-卡片页去掉）→ 用量页，图表出现三段：输入 / 输出 / 缓存读。
- **三段互相分得开**，且「输入」是**对比度最高**的一档 —— 浅色下它最深，深色下它最亮。
  这条方向性最容易错：照搬"最深＝输入"会让深色模式的主段落几乎消失。
- 三段坐在白卡（浅）／`#1A1F27`（深）上，不是坐在页面底色上。

**已算过的数值**：浅色 12.9 / 5.9 / 3.3，深色 9.7 / 5.4 / 3.4，全部 ≥3:1。

## A-04 告警条（Slack 未连接 · N 个定时任务受影响）— 待验

**引入** 0.1.115（改用设计源的柔玫瑰）· **契约** `DESIGN.md §5.2`、`ui/theme/Tiles.kt`

**为什么自动化不了**：告警条只在 `health.total > 0` 时渲染，也就是**真的有渠道断线或定时任务失败**
时。本地 mock 不提供消息渠道，`health.total` 恒为 0，开发栈里这一条永远不出现。

**前置**：断开一个已配置的消息渠道，或制造一个失败的定时任务。

**判据**
- 内缩 16dp、圆角 12dp 的卡，浅色底 `#FFF1F2`、文字 `#9F1239`。
- **重点看它是否还"存在"**：这个底色对纸面只有 **1.04:1** 的亮度差，靠色相而不是明暗区分，
  比它替掉的 `errorContainer`（1.23:1）安静得多。
- **如果它太淡以致看不见**：加深这个填充，**不要退回 `errorContainer`** —— 那个红属于真正的
  错误（删除确认、失败对话框），一条常驻通知涂成同样的红会磨损它。

## A-03 会话 / 机器人分段栏在真机上 — 待验

**引入** 0.1.115 起（下沉胶囊）· **契约** `DESIGN.md §5.2`

**为什么自动化不了**：分段行只在**这台 Hermes 配过消息渠道**时才渲染（0 段或 2 段），
本地开发栈不提供渠道，所以真机上这一行根本不出现。Roborazzi 的
`segmentsTwoZh` / `segmentsTwoEnLargeFontDark` 渲染的是真实 composable，已覆盖形态与
fontScale 1.3，**但没覆盖它在真实页面里与顶栏、告警条的间距关系**。

**前置**：配置任一消息渠道（钉钉 / Slack / 飞书…）。

**判据**
- 分段行出现在顶栏与列表之间，左右与列表行同为 16dp 内缩。
- 选中段是**浮起的浅色片**（不是填满品牌蓝），未选段透明。
- 两段各带 18dp 描边图标（气泡 / 机器人），图标与标签同粗细，不比标签细。
- 深色下选中段仍然看得出来 —— 这一档改前差点翻车（见 `SegmentPillTest`）。

## A-05 中文项目名把会话行撑到 88dp — 已确认是缺陷，待修

**这一条不是"待验"，是已经在真机上量到的缺陷**，记在这里是因为它需要一次独立改动，且当前
没有任何自动化能看见它。

**现象**：项目名含中文的会话行渲染为 **88dp**，项目名是 ASCII 的同类行是 **72dp**。88dp 是
Material `ListItem` 的三行档，三行项**顶对齐**，于是副行下方空出约 16dp 的洞，列表看起来每隔
几行就松一块。

**实测**（2026-09-11，HONOR CLK-AN00 / Android 14 / SDK 34 / density 480 / fontScale 1.0，
mock 数据，项目名「赫尔墨斯远程」）：

| 行 | 副行 | 高度 |
|---|---|---|
| 重构 gateway 路由中间件 | 赫尔墨斯远程 · claude-opus-5 | 264px = 88dp |
| 整理 docs/DEPLOYMENT | 赫尔墨斯远程 · claude-opus-5 | 264px = 88dp |
| 翻译 Android 文案 | nous-hermes-agent-playground · … | 216px = 72dp |
| 调查 DERP 端口冲突 | hk · claude-opus-5 | 210px = 70dp |

**不是等宽字体带来的**：同一台机器上对 `origin/main`（c736350，副行仍是系统字体）跑同一组
数据，两行同样是 264px。也试过给副行加 `includeFontPadding = false` 与
`LineHeightStyle(Trim.Both)`，高度不变，所以那两项没有留在代码里。

**为什么自动化看不见**：Roborazzi 的 fixture 里项目名全是 ASCII（`hermes-remote`、
`xiaomai-daily-report`），而且 CI 只跑 `:app:testDebugUnitTest`，根本不会捕获或校验截图。

**修的时候先查这两处**：`SessionSubline` 的自定义 `Layout` 取子项高度的最大值；`ListItem` 在
supporting 槽超出两行预算时会切到三行几何。加一条项目名为中文的 golden 当回归网。

## 已验证归档

### 会话列表照 Stitch 落地 — 已验 0.1.116（2026-09-11，HONOR CLK-AN00 / SDK 34）

浅色与深色各看过一遍：顶栏 56dp 内容高度、标题完整不裁切；副行等宽、文件夹图标为最淡档；
分组立柱 3×12dp 中性、计数 chip；深色 FAB 近黑且描边环清晰可见。

同一轮里抓到并修掉一个只有真机才会暴露的缺陷：顶栏用 `Modifier.height(56.dp)` 会把状态栏
内边距一起算进这 56dp，内容行被压扁、标题竖向裁切、与首个组头贴在一起。改用
`CenterAlignedTopAppBar(expandedHeight = 56.dp)`。Roborazzi 看不见它，因为 JVM 里没有真实
状态栏内边距 —— 这正是 L2 不可被 L1 替代的那类问题。
