# Android 待设备验证清单

`AGENTS.md` 要求：**当一个有意义的用例无法自动化时，把它写进冒烟文档并明示它仍需设备或生产
验证** —— 这份文件就是那个落点。`docs/SMOKE_TEST.md` 是网关／连接器的，不覆盖 Android UI；
`docs/DESIGN.md §7` 定的是验证**规程**（跑什么、怎么跑），这里记的是规程**跑不到的地方**。

## 什么该进这里

只有同时满足两条的用例：

1. **JVM 测试与 Roborazzi 都覆盖不到** —— 需要真实数据、真实网关状态、或一个本地 mock 造不出的
   运行时相位。仅仅"还没写测试"不算，那种情况应该去写测试。
2. **验不到会让人误判** —— 有数值或结论已经写进了 `DESIGN.md`，但那个结论从未在屏幕上确认过。

**每条必须写明"为什么自动化不了"。** 没写理由的条目会退化成永远不做的待办。

## 状态标记

`待验` 从未在设备上确认 · `已验 <版本>` 确认过，保留作回归参考 · `已失效` 相关设计已改，条目作废

## A-04 告警条（Slack 未连接 · N 个定时任务受影响）— 待验

**引入** 0.1.115（改用设计源的柔玫瑰）· **契约** `DESIGN.md §5.2`、`ui/theme/Tiles.kt`

**为什么自动化不了**：告警条只在 `health.total > 0` 时渲染，也就是**真的有渠道断线或定时任务失败**
时。本地 mock 不提供消息渠道，`health.total` 恒为 0，开发栈里这一条永远不出现。

**前置**：断开一个已配置的消息渠道，或制造一个失败的定时任务。

## A-05 中文项目名把会话行撑到 88dp — 已修（2026-09-12）

**根因是 Material `ListItem` 的行数档**，不是字体：中文项目名让副行换行，`ListItem` 于是按三行项
排版（88dp 且顶对齐），ASCII 项目名的同类行停在两行档的 72dp。会话行在落地第五次 Stitch 拉取的
密度收紧时改成了自绘 `Row`（docs/DESIGN.md §5.2），没有行数档也就没有这个台阶。

同一条根因还带走了另外两个症状：副行下方那块空洞（三行项顶对齐所致），以及**运行中的转圈不在行
的竖直中心**（同上，产品负责人 2026-09-12 真机发现）。

**残留 1.5dp，是有意偏离。** 实测 411dp/420dpi：纯拉丁行 49.52dp，每有一行中文 +1.52dp。稿子的
`leading-[1.35]` 是按拉丁字形推的，中文回退字体需要的 ascent+descent 超过 `字号×1.35`，行框只能
长到字体要求的高度。对照原来的 16dp，这是一个数量级的改善。

**回归网已经补上**：`SessionRowTuningTest`（`@GraphicsMode(NATIVE)`，中英文各一组）与三张 golden
——`row-height-probe` 里新增了中文项目名一行、`session-rows-running` 覆盖运行中与置顶+运行中。
注意 **Robolectric 默认的桩字体会让中英文测出一样高**，这条必须跑 NATIVE 才有意义。

以下是当初的实测记录，保留备查。

**现象**：项目名含中文的会话行渲染为 **88dp**，项目名是 ASCII 的同类行是 **72dp**。88dp 是
Material `ListItem` 的三行档，三行项**顶对齐**，于是副行下方空出约 16dp 的洞，列表看起来每隔
几行就松一块。

**实测**（2026-09-11，HONOR CLK-AN00 / Android 14 / SDK 34 / density 480 / fontScale 1.0，
mock 数据，项目名「赫尔墨斯远程」）：

| 行 | 副行 | 高度 |
|---|---|---|
| 重构 gateway 路由中间件 | 赫尔墨斯远程 · claude-opus-5 | 264px = 88dp |
| 整理 docs/DEPLOYMENT | 赫尔墨斯远程 · claude-opus-5 | 264px = 88dp |
| 翻译 Android 文案 | nous-hermes-agent-playground · … | 216px = 72dp |
| 调查 DERP 端口冲突 | hk · claude-opus-5 | 210px = 70dp |

**不是等宽字体带来的**：同一台机器上对 `origin/main`（c736350，副行仍是系统字体）跑同一组
数据，两行同样是 264px。也试过给副行加 `includeFontPadding = false` 与
`LineHeightStyle(Trim.Both)`，高度不变，所以那两项没有留在代码里。

**为什么自动化当初看不见**：Roborazzi 的 fixture 里项目名全是 ASCII（`hermes-remote`、
`xiaomai-daily-report`），而且 CI 只跑 `:app:testDebugUnitTest`，根本不会捕获或校验截图。
两条都已经补上（见上）；CI 仍然不校验截图，那是另一件待办。

当初写下的怀疑对象是「`SessionSubline` 的自定义 `Layout`」与「`ListItem` 在 supporting 槽超出两行
预算时切到三行几何」—— 后者是对的。

## A-06 杀掉 App 冷启动后的状态行、分组与待确认卡 — 待验

**引入** HG-31 · **契约** `DESIGN.md §5.2`（运行状态跨进程存活）、`ERROR_HANDLING.md`
（`HR-APPROVAL-001/002`）

**为什么自动化不了**：`ColdStartPhaseRestoreTest` 能钉住 store 的恢复逻辑，但钉不住**"真的被系统
杀掉、DataStore 真的落盘、进程真的重建"**这件事本身 —— Robolectric 不会杀进程，也不会重放
DataStore 的跨进程写入时序。通知那一半更是只有真机才有：`cancelSessionCards()` 保留哪些卡，取决于
系统通知栏在进程死亡后实际留下了什么，而各家 ROM 的"划掉 App"语义并不一致（这正是要按 vendor
分别验的原因）。

**前置**：`./scripts/dev/dev-stack.sh start`（后台）+ `./scripts/dev/device-install.py --all`
（`adb install -r` 保留数据，这是验持久化的前提）。本地 mock 够用的只有「已完成」那一半；
「重启后仍在等待」与审批那一半都需要真实 Hermes，原因见判据 1。

**已验（2026-09-12，vivo V2166BA / Android 13）**：判据 2 已确认；「已完成」跨 force-stop 冷启动
保留——两条会话的第三行绿色「已完成」都在（改动前它们会全部消失）。
**已验（2026-09-12，HONOR CLK-AN00 / Android 14）**：同样保留绿色「已完成」；且待审批时杀掉 App
再冷启动，**没有**任何审批卡被复活（这是本次最关键的安全性质）。另实测到一条设计确认：run 在**聊天页
正被查看时**完成不留结论（§5.2），所以要造「已完成」必须在运行期间退回列表页。
**未验**：判据 1 前半截、3、5、6 —— 都要真实 Hermes 或真实的"划掉 App"通知栏取证，见下。

**判据**（每一台都要单独记结果，不要跨设备推广）
1. 造出一条待答 clarify + 一条已完成未读 → 从最近任务划掉 App → 冷启动：两行的第三行文字都在，
   顶部「需要你处理」分组在，进会话后 clarify 的选项**可以选、可以提交**。
   **本地 mock 造不出这一条的前半截**（2026-09-12 vivo 实测）：`mock-hermes-stream.mjs` 在客户端
   socket 断开后会把这一轮跑完，于是冷启动时的对账拿到 `running:false`，按设计正确地把等待态退成
   「已完成」并撤掉卡。要验"重启后仍在等待"，必须让**真实 Hermes** 停在一个真的还没被回答的
   clarify/审批上——与 A-01 的结论同源。
2. 行尾圆点不变：`sessionRowTrailing` 里**未读优先于 `COMPLETED_UNREAD`**，所以一条既未读又已完成的
   会话冷启动后仍是**蓝色未读点**，不是绿点。绿点只属于「已读过、但那一轮跑完了」这种更窄的情形。
   （2026-09-12 vivo 实测确认；本条写在这里是因为它容易被误判成回归。）
3. 正在运行的会话冷启动后先显示「正在恢复连接…」，socket 连上后**自行**变回「思考中…」/「正在输出…」，
   不需要任何手动操作。
4. 离线冷启动**验不到第三行**，别把它当回归：会话行本身来自 REST（`listAllProfiles`），而冷启动的
   列表缓存是内存态，断网时一行都没有，自然也没有第三行。这一条只能验"不出现任何「已中断」"——
   相位过期时是被丢弃的，不会凭时间戳编造结论。
5. 冷启动后通知栏里那张「需要你处理」卡**还在**，没有被降级成 ongoing 卡，点它的动作按钮仍然有效。
6. 真实 Hermes 上：待审批时杀 App 冷启动 → 行内「等待你的确认」在，进会话给出
   `HR-APPROVAL-002` 的说明而**不是**一张审批卡。

**为什么第 6 条要这么设计**：`approval.respond` 只按 session 寻址、不带请求 id、无返回值，从磁盘
复活的卡会指向 Hermes 此刻在等的任意一条审批 —— 可能是用户从未见过的命令。宁可说清楚，也不给一张
看起来正常的假卡。

## A-07 看图器的手势仲裁：1× 换页、放大平移、边缘续翻 — 待验

**引入** HG-35 · **契约** `DESIGN.md §5.4`（图片缩略图与看图器 → 手势仲裁）

**为什么自动化不了**：`ImageViewerGestureTest` 能把三个判定函数（`imagePagerUserScrollEnabled`、
`shouldConsumePan`、`clampPan`）钉死，但钉不住**真实触摸流与 `HorizontalPager` fling 之间的竞争**。
Robolectric 的 `performTouchInput` 合成的是完美线性、无速度的事件序列，而这块会坏的恰恰是
「第二根手指晚两帧落下」「甩动惯性未停就开始捏合」这些相位——合成事件里不存在。

**前置**：一条带 ≥3 张图片的消息（发三张截图即可）。

**判据**
1. 1× 时横向拖动**换页**，图片本身不平移。
2. 捏合到约 3× 后，单指拖动**平移**，页面不换。
3. 放大态平移到右缘后继续左滑，**不会在放大状态下跳页**（要么停在边缘，要么先归位）。
4. 双击回到 1×，翻页立即恢复可用。
5. 任何缩放级别下都**无法把图片拖出屏幕**——松手后总能看到图像内容。
6. 返回键只关看图器，**不会同时拉开抽屉**。

## A-08 极端宽高比缩略图的观感（914×2048 手机截图）— 待验

**引入** HG-35 · **契约** `DESIGN.md §5.4`（单张图片完整显示）

## A-10 涂鸦手感与三档笔宽 — 部分已验（2026-09-12，vivo V2166BA / SDK 33）

**引入** HG-35 · **契约** `DESIGN.md §5.4b`（笔宽按长边比例）

**为什么自动化不了**：JVM 能验 `strokeWidthPx` 的比例性与单调性，验不了**跟手感**（2560px 位图上
逐帧重绘是否掉帧）和**可分辨性**（三档宽度在一张真实截图上是否读成三个重量）。两者都是帧率与
人眼的判断，Robolectric 没有帧率。

**前置**：选一张手机截图进编辑器，涂鸦模式。

**判据**
- 慢速画一个圈，线条**平滑无折角**（中点贝塞尔生效），跟手无可见滞后。
- 三档笔宽在同一张图上并排画，**明显是三个重量**，不是「细、细一点、还是细」。
- 快速甩笔不丢点、不断线；一次手势**撤销一次正好消掉一条**。
- 单击（不拖动）留下一个圆点，不是什么都没有。

**2026-09-12 实测**：一次拖动画出的线平滑、落点与手指一致（合成事件）。**尚未验**：真实手指的
跟手感与三档宽度的可分辨性——合成 swipe 没有帧率也没有速度，这正是本条存在的理由。

## A-11 打码的不可逆性目检 — 部分已验（2026-09-12，vivo V2166BA / SDK 33）

**引入** HG-35 · **契约** `DESIGN.md §5.4b`（打码是像素化）

**为什么自动化不了**：`ImageEditBakerTest` 能断言马赛克区域的像素方差塌陷，但**「塌陷到多少算读不
出来」是人眼的阈值**，而且要在 JPEG 重编码之后、接收方放大之后仍然成立。这是唯一能验证「遮挡真的
遮住了」的检查，合成图替代不了真实字形。

**前置**：一张含真实手机号或账号的截图。

**判据**
- 涂完发送，在**接收侧**把图点开放大到 5×，号码**读不出**。
- 块栅格**对齐且边硬**，看起来是有意打码，不是压缩坏了（这条同时验证 `filter=false` 的上采样）。
- 马赛克笔刷半径之外的像素**完全没被动过**。
- 先涂鸦后打码时，**马赛克盖住涂鸦**（列表顺序即 z 序）。

**2026-09-12 实测**（中文会话列表截图，大号笔刷）：块边硬、栅格对齐，被盖住的标题完全读不出，
笔刷半径外的相邻文字逐字清晰。**尚未验**：接收侧放大到 5×、真实手机号，以及更小字号上的表现——
本轮用的是标题级字号。

## A-12 编辑器的沉浸与返回分层 — 部分已验（2026-09-12，vivo V2166BA / SDK 33）

**引入** HG-35 · **契约** `DESIGN.md §5.4b`（Dialog 宿主与沉浸式）

**为什么自动化不了**：`WindowInsetsControllerCompat.hide` 在 Robolectric 下是空操作，dialog 窗口的
insets 也是合成值。刘海、圆角、手势条与三键导航栏的真实几何只存在于设备上，而且**逐 ROM 不同**。

**前置**：手势导航与三键导航各走一遍；有刘海/挖孔的机器优先。

**判据**
- 进编辑器后系统栏隐藏，工具栏与顶栏**不被刘海或手势条压住**。
- 返回阶梯逐级生效：编辑器 → 预览 → 键盘 → 会话列表，**每次返回只退一层**。
- 有未提交编辑时取消/返回会弹丢弃确认；没有编辑时直接关闭，不问。
- 转屏后**笔迹和裁切框还在**（op 列表走 Saver），不是白干。

**2026-09-12 实测**：vivo 上系统栏确实隐藏，顶栏与工具行都不被遮挡。**尚未验**：刘海/挖孔机型、
三键导航、转屏后的 op 存活。

**一个会误判的现象**：沉浸式转场期间 `adb exec-out screencap` 会在画面顶部留下一排很淡的工具栏
残影。`uiautomator dump` 里没有对应节点，切换工具后残影也不跟随变化——是截屏时序产物，不是重复
绘制。别为它去改布局。
