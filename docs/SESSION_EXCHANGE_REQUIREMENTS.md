# 会话互引：添加会话、分享到会话

> 状态：HG-38 与 HG-40 的需求整理与联合契约，供产品、设计和开发使用。
> 范围：Android `com.hermes.remote` 的会话聊天页——输入区「添加内容」弹层、「更多 › 分享对话」，
> 以及两者共用的会话选择器；中文为默认语言，所有文案需具备中英文版本。
> 本文描述已确认的产品约束，**不授权**改变网关、Hermes 上游协议或附件上传协议。

## 1. 为什么把两条需求写在一份文档里

HG-38 和 HG-40 是同一件事的两个方向：

| # | 编号 | 方向 | 用户原话 |
|---|---|---|---|
| ① | HG-38 | **拉**：把别的会话拉进这一次输入 | 「我可以选择整个系统里的任意一个到多个会话，选中后分别转成 MD 文档，作为附加信息和这次输入的添加」 |
| ② | HG-40 | **推**：把这个会话推到别的会话 | 「把选中的媒介（不管是图片、MD 文档还是一串字符串），分享到当前产品系统里的某一个对话中……也支持开启新对话」 |

两个方向共用三块东西，分开写两份文档会各自把它们半定义一遍，然后漂：

1. **会话选择器**——一个要多选、一个要单选加「开新对话」，但行长什么样、能选到哪些会话、
   空态说什么，必须是同一套。
2. **会话 → Markdown 的口径**——两边生成的 MD 必须是同一份东西，否则「我引过去的」和
   「我分享出去的」内容对不上。
3. **投递到会话的接缝**——把字节交给某个会话当待发附件，这条链路 App 里已经有了（外部分享
   进 Hermes GO 就走它），两边都接在它上面。

## 2. 三条贯穿全文的决定（2026-09-12，产品负责人裁定）

- **只能引当前身份的会话。** 需求原文说「整个系统里的任意一个到多个会话」，但 `DESIGN.md` §1
  原则 1 写着「Profile 是唯一作用域边界，切换身份即切换整个工作区」。把 B 身份的会话内容塞进
  A 身份的对话，等于让 A 的 agent 读到 B 工作区的东西——这正是原则 1 要挡的。所以选择范围
  **等于会话列表所见**（`SessionsViewModel` 取全身份数据后按 `profileManager.active` 过滤，
  选择器必须用同一条过滤，不是另写一份）。
- **投递一律落到目标会话的输入框，由用户按发送。** 不直接发。理由有两条：投递前还能补一句
  「这是什么、我要你做什么」——光甩一份转录给 agent，它多半不知道要干嘛；以及投错对话时，
  代价是删掉一个 chip，而不是已经触发了一次 agent 运行。**新建会话同理**，需求原文
  「作为附件直接发起新对话」按此收窄，并在下文 §6.4 写明。
- **分享是「先选格式、再选去向」两层。** 格式（文字／Markdown／长图）与去向（发到会话／系统
  分享盘）是两个维度，并排放在一层里会让人以为「分享到会话」是第四种格式。代价是多一次点击，
  换来的是两层各自都说得清，且以后再加去向有地方放。

## 3. 共用件一：会话选择器

### 3.1 形态：全屏页，两种模式

```
SessionPickerScreen(mode = Multi(remainingSlots) | Single(allowNewConversation))
```

**是全屏页，不是弹层。** 多选要能滚、能搜、能一眼看见勾了几个；`DESIGN.md` §5.8 还有一条硬
规则说可滚动的弹层必须关掉手势并补关闭把手，等于承认弹层不适合装列表。两种模式共用一个页面，
行的样子才不会在两处漂——与 §5.2 把副行收敛成一个 `SessionSubline` 组件是同一条理由。

### 3.2 能选到哪些会话

| 会话 | 可选 | 为什么 |
|---|---|---|
| 当前身份、非空、非归档的普通会话 | ✅ | 就是会话列表所见 |
| 当前身份的**已归档**会话 | ✅，经搜索找到；行上标「已归档」 | 搜得到就引得到。归档是「从列表里收起来」，不是「不可引用」 |
| 其他身份的会话 | ❌ 根本不出现 | §2 第一条 |
| 机器人／消息渠道会话 | ❌ | 它们不是用户与 agent 的对话，`listAllProfiles()` 已经把它们挡在会话列表外（`isInteractive()`），选择器沿用同一条 |
| 空会话（零消息） | ❌ 不出现 | 转出来是一份空 MD。`listAllProfiles()` 已经过滤 `messageCount > 0` |
| 定时任务派生的会话 | ❌ | 同 `isInteractive()` |
| **当前这一个会话** | ❌ 不出现 | 两个方向都没有意义：引进自己只会让 MD 里出现半份自己，分享给自己是把 A 的转录塞回 A |

数据来源：`SessionRepository.listAllProfiles()` + 活动身份过滤；归档来自 `archived(profile)`。
两者都已存在，不新增网关调用。

### 3.3 行的样子

标题 + `SessionSubline`（`[置顶图钉] [文件夹] 项目 · 模型`），与会话列表、搜索结果、归档页
**用同一个组件**。多选模式在行尾放勾选框；单选模式点行即选中并返回。

行尾勾选框是这个页面唯一的新控件。它不与 §5.2 那个 28dp 状态槽冲突——选择器不显示运行状态、
未读或草稿：这里是在挑一份内容，不是在看哪个会话有动静。

### 3.4 搜索

顶栏一个搜索框，**只做标题匹配**（`SearchResultRows.TitleMatchRow` 的同一条匹配逻辑）。
不做消息级全文搜索：那是搜索页的活，而这里的任务只是「找到那个会话」，找到就走。
归档会话只在有搜索词时才参与匹配（与 §3.2 一致）。

### 3.5 上限与计数（仅多选）

- 多选与待发附件**共用 `ATTACH_CAP = 6` 的名额**。它们最终落在同一条 chip 行上，两套上限会让
  用户选满 6 个会话后才在聊天页被告知装不下。
- 进入选择器时按**剩余名额**封顶：输入框已有 2 个附件，则最多再选 4 个。
- 选满后其余行置灰、不可点，页面底部说明「最多再选 N 个」。**不是选中后再报错**。
- 确认按钮显示「添加 N 个会话」；N = 0 时禁用。

### 3.6 空态与失败

- 当前身份一个可选会话都没有：空态文案「这个身份下还没有可引用的会话」，不给按钮。
- 列表拉取失败：走既有 `ErrorState` + 重试，与会话列表同一套。

### 3.7 明确不做

全选、按项目分组折叠、跨身份、多选里挑具体哪几条消息。第四项特别说明：**只引整个会话，
不引某几轮**。挑消息是另一个交互量级的功能，而「把那次讨论给它看」的真实需求是整段上下文。

## 4. 共用件二：会话 → Markdown 的口径

**复用 `transcriptMarkdown(title, messages, language, exportedAtMillis, model, origin)`，
不新写一份。** 它已经是「分享对话 › Markdown 文件」的产出，两处生成同一份东西正是 §1 第 2 点
要保证的。随之继承它既有的全部口径：

- 一级标题是会话标题，一行元数据（导出时间 · 模型 · Hermes GO），每轮一个 `##` 段。
- 消息正文原样保留 Markdown，代码块与表格无损。
- **文件附件只写一行 `附件：<文件名>`，不下载、不内嵌**（决策 2026-09-05）。被引会话里的图片
  和文件**不会跟着过去**——这是既有导出口径，本文明确继承，不是遗漏。
- 文件名 `transcriptFileBaseName(title, now) + ".md"`，已处理路径分隔符、保留字、换行与超长。

### 4.1 历史从哪来

`SessionRepository.history(sessionId, profile, deviceId)`——已存在，按 id 取任意会话的转录，
带请求合并、内存缓存与磁盘持久化。**生成 MD 时以网络为准**，不拿 `cachedHistory` 凑合：引用
一份少了最后三轮的转录，比慢一秒糟得多。

### 4.2 超长会话

单附件硬顶仍是 `MAX_DIRECT_ATTACHMENT_BYTES`（6 MB）。纯文本转录实际上触不到这个数（6 MB ≈
三百万字），但**必须有行为而不是撞上去才发现**：超出时从**最早的轮次**开始丢弃，并在文首写一行
`> 已省略最早 N 轮，原对话共 M 轮`。不静默截断——一份不说自己被截过的转录会被当成完整的读。

## 5. HG-38 添加会话

### 5.1 入口

「添加内容」弹层里，在「常用提示」**下方**再加一行 `ListItem`：

```
[图标] 添加会话
      把已有对话转成 Markdown 一起发出
```

**是一行 `ListItem`，不是第四张方卡。** 上面那三张方卡（拍照／照片／手机文件）是同一族——
「从这台手机拿一个文件」；「常用提示」和「添加会话」是另一族——「从系统里挑一样已有的东西
插进来」。按族归形，不按顺序排。

### 5.2 流程

1. 点「添加会话」→ 弹层关闭 → 会话选择器（多选，剩余名额封顶）。
2. 勾选 1~N 个 → 「添加 N 个会话」。
3. **立刻回到聊天页**，输入区上方显示「正在生成 N 份对话记录…」。
4. 逐个拉历史 → 转 MD → `ChatViewModel.stageAttachment(bytes, "text/markdown", "<名>.md")`。
5. 全部就绪后一次性落成 N 个 chip；用户可以逐个删、可以继续打字，按发送才走。

**为什么是「全部就绪才落 chip」，而不是逐个落位加一个「生成中」态**：`PendingAttachment` 现在
没有加载态，加一个会波及 chip 行、图片预览器、发送校验、编辑器入口一整串地方，代价与收益不
匹配。一句进度文案就够了，而且 N ≤ 6。

**一个失败不连累其他**：某个会话拉取失败时，其余的照常落成 chip，失败的那个单独报
`HR-SESS-014` 并指名是哪个会话。

### 5.3 发送

走**既有的 FILE 分支**，不新写协议：`ChatFileRepository.upload()` → `file.attach` →
上游返回的 `ref_text` 追加到 prompt 正文。所以 agent 读到的是一个它能打开的文件引用，
这正是需求里「并添加上去作为发送的内容」要的效果。

### 5.4 边界

- 选 3 个就是 3 份独立 MD，**不合并成一份**（需求原文明确）。
- 与图片、手机文件混用没有额外规则：都是 chip，共用 6 个名额。
- 引用的是**生成那一刻**的转录快照。被引会话之后继续对话，不会回头更新这份 MD。

## 6. HG-40 分享到会话

### 6.1 两层

```
更多 › 分享对话
  └─ 第一层 · 格式   文字 / Markdown 文件 / 长图        ← 三项不变
       └─ 第二层 · 去向   分享到会话 / 系统分享盘
```

**第二层的顺序：分享到会话在前，系统分享盘在后。** 依据 `DESIGN.md` §5.4 的既有原则——
「离场动作垫底」。系统分享盘把内容交出 App，是离场动作。

第一层的三项文案与图标一字不改。第二层每项一行说明，讲清去哪儿。

### 6.2 长图的预算闸门提前

「长图 + 系统分享」今天在选中格式时就用 `transcriptImageFitsBudget` 拦一次（策略 A）。
加了第二层之后，**这一拦仍然在第一层**：超预算时不必让用户先选去向再被拒绝。

### 6.3 三种媒介到会话里各是什么

| 格式 | 落到目标会话的形态 | MIME |
|---|---|---|
| 文字 | 输入框正文（追加在已有草稿之后，不覆盖） | — |
| Markdown 文件 | 待发文件 chip | `text/markdown` |
| 长图 | 待发图片 chip | `image/png` |

文字那一行特别说明：目标会话可能已经有草稿（HG-41）。**追加，不覆盖**——覆盖等于删掉用户
自己写了一半的话。

### 6.4 目标选择

会话选择器（单选），列表**顶部固定一行「开启新对话」**。

- 选已有会话 → 投递 → 跳转到该会话，内容已在输入框/chip 里等着。
- 选「开启新对话」→ `session.create` → 投递 → 跳转到新会话。**同样落到输入框，不直接发**
  （§2 第二条）。新会话落在默认项目，与 §5.4 「聊天页没有项目作用域可言」同一条规则。
- **已归档会话不可投递**：投进归档等于让它复活但在列表里看不见。选择器在单选模式下不显示归档
  会话，搜索也不显示——与多选模式的 §3.2 不同，这是刻意的差别，因为「引用」和「投递」对归档
  的意义不一样。

### 6.5 返回落点

投递后跳转走**既有的 canonical 规则**（`openCanonicalChat`）：从会话 A 分享到会话 B，在 B 按
返回回到**会话列表**，不回 A。

HG-39 刚刚为「顶栏 ＋ 新建对话」开了唯一一个叠栈例外，本条**不扩大它**：那个例外的理由是
「答案看完想接着开下一个，返回是想回到那个答案」；分享投递之后人要做的是在 B 里继续说话，
不是回头看 A。**可复议**——真机上用起来如果发现总想返回 A，再加一条例外即可，但要先有那个
实感，不要先把例外摊开。

### 6.6 投递机制

复用 `PendingShareStore`：一次性、按 sessionId 取、进程内。外部分享进 Hermes GO 走的就是它，
链路完整（文字进输入框、图片成待发 chip），本次接在同一条上。

`PendingShare` 现在是「文字 + 单张图（base64）」。需要承载「文字 + 一组附件（含文件）」，
因此**新增一个附件列表字段，直接放字节**：

- 不动既有的 `imageBase64` / `imageMime` / `attachmentName` 三个字段，外部分享那条路径原样不变。
  本次不顺手重构它——那是另一条链路的风险，与这两条需求无关。
- 新字段直接放 `ByteArray`：这是进程内的单例内存传递，base64 编码是纯开销（一张长图还要再涨
  三分之一）。既有字段用 base64 有它自己的历史，不构成新字段也要用的理由。
- 留一条备注：两组字段以后可以合并，合并时外部分享链路要一起回归。

### 6.7 长图需要一个新接缝

`OffscreenTranscriptExporter` 今天把「渲染出 bitmap」和「交给系统分享盘」焊死在同一个
`LaunchedEffect` 里，`onDone` 只回一个布尔——没有任何地方能拿到那张图。

**必须把产出与去处拆开**：渲染照旧，产出交给调用方处置（系统分享 / 投递到会话）。系统分享那
条路径的行为、文案、错误码一律不变。三条硬规则（固定浅色渲染、底部页脚、超预算直接拒绝）
继续适用于两个去向——投到会话里的长图同样是给人看的。

## 7. 错误码

**只新增一个**，其余全部复用（`docs/ERROR_HANDLING.md` 须在使用前登记）：

| 代码 | 条件 | 中文 | English | 可重试 |
|---|---|---|---|---|
| `HR-SESS-014` | 生成 MD 时拉取被选会话的转录失败 | 无法读取「{标题}」的内容，请重试。 | Couldn't read "{title}". Retry. | 是 |

复用的：

- `HR-FILE-002`——MD 字节生成失败（该码的语义就是「无法生成对话文件」）。
- `HR-MEDIA-003`——长图渲染失败。
- `HR-SESS-001`——投递目标会话已不存在。
- `HR-SESS-007`——投递后用户按发送，提交失败；这是既有发送路径，本文不改它。

选择器里「这个会话没有可导出的内容」**不是错误**，是行的禁用态加一行说明（§3.2 已由数据源
过滤掉，此处为兜底）。

## 8. 验证

### L1（JVM + Roborazzi，必跑）

- 会话选择器的可选性判定写成**纯函数**（身份、归档、`isInteractive`、当前会话、剩余名额），
  逐条单测。这是本文档最容易被实现走样的地方。
- 剩余名额计算：已有 2 个附件 → 最多再选 4；选满后其余不可选。
- 超长转录的截断：文首那一行 `已省略最早 N 轮` 必须出现，且轮数对得上。
- `PendingShare` 新字段的一次性语义：按 sessionId 取、取过即空、取错 id 不消费。
- 文字投递**追加而非覆盖**已有草稿（与 HG-41 交叉）。
- 截图 golden：选择器多选态（含选满置灰）、单选态（含顶部「开启新对话」行）、「添加内容」
  弹层多出的那一行、第二层去向弹层；浅色与深色。

### L2（真机，必跑，且必须写明是哪台）

这两条的关键路径都**只有真机能走完**：网关拉取真实转录、`file.attach` 的 `ref_text` 真的被
上游接受、长图真的渲染出来。最少走通：

1. HG-38：引 1 个会话 → 发送 → 在 agent 回复里确认它确实读到了那份 MD。
2. HG-38：引 3 个会话 → 确认是 3 个独立 chip、3 份 MD。
3. HG-38：混合 1 张图 + 5 个会话 → 第 6 个之后不可选。
4. HG-40：三种格式各投递一次到已有会话，确认落到输入框/chip 且**没有自动发送**。
5. HG-40：投递到「开启新对话」，确认新会话拿到内容且停在输入框。
6. HG-40：系统分享盘那条老路径没被改坏。

### L3

仅在触及 `targetSdk` 门控行为时需要；本文预计不涉及。注意本机在接设备最高 SDK 34，
未达 `targetSdk 37`。

## 9. 明确不做（本轮）

- 跨身份引用会话（§2 第一条）。
- 引用机器人／消息渠道／定时任务会话。
- 只引会话里的某几条消息。
- 被引会话的图片和文件跟着过去（§4 继承既有导出口径）。
- 投递到已归档会话（§6.4）。
- 一次引超过 6 个会话（§3.5）。
- 重构 `PendingShare` 的既有 base64 字段（§6.6）。
- 从会话 A 分享到 B 之后返回 A（§6.5，可复议）。
