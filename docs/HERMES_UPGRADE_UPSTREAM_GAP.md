# 首条 Hermes 升级路径的上游接口缺口

这是 HC-01/HC-02 的实验结论和后续开发输入。经负责人明确授权，已于 2026-10-25 提交上游 [hermes-agent #144377](https://github.com/NousResearch/hermes-agent/issues/144377)，尚未修复或重新验收。

## 已确认的输入与结果

来源：0.21.3 / `633dda6d7fdcac7e8340471c9f5ed08cdccbd70c`。
目标：0.22.5 / `bf0203a794a07aac3ff764972ab9087baa4e4f4e`。

官方 install.sh 支持精确 commit，隔离实验已经成功升级和恢复完整旧运行环境。因此“完全不能升级”不是准确结论。尚不能达到 GO 承诺的是：服务排空后从首次 repository 写入到最终提交，所有入口共享同一可靠更新所有权；Desktop/主进程退出后，存活子进程仍阻止另一个更新进入。

`scripts/hermes-compatibility-lock-lab.py --source <隔离旧版 checkout> --target <隔离新版 checkout>` 使用真实兄弟进程和官方原始锁代码复现。两个目录必须在日常 HOME 外且 HEAD/锁文件与固定 commit 一致。脚本只创建自有临时 marker/repository 和进程；报告没有个人路径、token 或原始日志。它是锁探针，不是生产升级适配器。

实验表明：杀死新版锁 owner 后，继承 flock 的子进程仍存在，新版 contender 拒绝，旧版 contender 成功。探针子进程仅休眠并保留锁描述符，没有执行安装写入；该证据证明互斥缺口，不证明已发生并行安装或数据损坏，也不推断上游当前 main 的行为。证据为 `evidence/hermes-compatibility/2026-10-25-update-lock.json`，`oldRefusesSurvivingChild=false`。旧 reader 还会清理超过 20 分钟的活跃 marker，这是源码观察，尚未进行 20 分钟故障实跑，不能混写为实测。

## 需要补齐的有界接口

优先由上游提供或明确支持一个精确目标更新入口，保持官方负责依赖、产品构建、迁移，不在 GO 内再造整套安装器。接口需要：

1. 接受固定 commit，返回实际执行 commit，repository 写入前已建立更新所有权。
2. 对旧入口有可验证的过渡方案；不能只让新入口遵守新锁，却仍允许旧进程并行写。明确哪些旧进程必须退出、如何检测和拒绝。
3. 将更新所有权交给可恢复的进程树，UI 退出不影响任务；owner 强制退出后，存活写入者仍受保护。
4. 状态包含操作 ID、阶段、实际版本及是否允许恢复；阶段可供外部只读查询，不依赖解析人类日志。
5. 确认取消/中断后的收尾责任与允许恢复的时点；新版恢复业务写入后，不静默用旧数据库覆盖新增数据。

## 原 A 范围的交付门槛（历史，已由下述 B 决策调整）

修复需在隔离环境重新验证正常升级、依赖失败、owner 中断、子进程继续、两个入口同时开始、服务停止/重启、Desktop 退出重开、超过 marker 期限及新版产生数据后的恢复拒绝。恢复点需要覆盖代码、依赖、配置及一致数据，恢复到原绝对路径后实际启动并读取历史。

在这些条件满足前，0.21.3→0.22.5 保持候选/验证失败，不批准支持，不开放普通一键升级。管理员页面、CI 队列和签名代码可以继续审阅，但不能用其完成度替代这条路径的结果。将首版改为仅支持新版锁协议来源属于范围调整，需要产品负责人决定，不由实现者自行更改。

## 首版交付条件的产品决策（已选择 B，2026-10-26）

负责人于 2026-10-26 明确回复“那就选B”。首版按 GO 控制的维护窗口继续实施，规划 I0/I4 已同步调整；这不是已经实现的执行器，也不立即解除普通升级门禁。下面保留 A/B 对照作为决策依据。
截至本次核对，上游 issue 仍打开、没有回复；草稿 PR #673 的 `3a62b925` 已通过全部 11 项检查。
正常固定版本升级、旧环境恢复和局部客户端业务都有隔离证据，但普通 Desktop 点击升级仍未实现。

源码核对进一步确认，0.21.3 的 `session.active_list` 只列当前 TUI 服务进程的会话；它不能证明
其他 CLI、机器人或独立服务已停止写入。现有 GO LaunchAgent 控制器的卸载/端口释放证明也只
覆盖自己的服务。把这两种观察拼在一起，不能满足原规划要求的全部入口更新所有权。

| 选择 | 首版承诺 | 对当前本机旧版本的影响 |
| --- | --- | --- |
| A：保持已批准门槛 | 保留旧更新入口并发、owner 强制退出后子进程存活的互斥保证；先取得可验证的上游过渡方案 | 继续不开放一键升级；上游依赖未解决前不能承诺交付时间 |
| B：限定为 GO 控制的维护窗口 | 支持 GO 发起的升级，要求升级期间不运行外部 Hermes 更新；检测到现存未知服务/更新器就拒绝进入。外部旧更新器在故障窗口被另外启动的并发行为明确排除在首版支持范围之外 | 可以继续针对当前旧版本实现和验收执行链路；仍需完成下面全部开发与验证，不能立即开放 |

选择 B 也不能移除以下要求：

- GO 安装、修复、重复点击及 Connector 更新共享同一个操作锁；执行工作进程与页面生命周期
  分离，退出页面不杀升级。
- 升级前识别并停止所支持的写入入口。对无法识别或无法确认停写的外部进程，给出具体处理动作，
  不强杀陌生进程，不把空活动列表视作全局停写证明。
- 使用固定官方目标和官方安装器；恢复点覆盖代码、依赖、配置和一致数据，实际恢复后验证运行、
  历史、账号绑定及客户端业务。
- 中断后先确认已知写入进程退出并核对磁盘状态；无法确认就保留现场并拒绝自动恢复。新版已有
  新数据时不得静默覆盖，不能因选择 B 而弱化这条规则。
- 管理员批准记录、普通用户升级前确认和错误/恢复说明必须同时表达支持条件；不能只在文档中
  写免责说明而让页面继续承诺原范围。
- 完成断网、依赖失败、工作进程中断、页面退出重开、启动失败、已存在的外部更新冲突、恢复重试
  和新增数据保护的实际验收。合并、角色授予、发布及部署仍分别遵守已有授权门禁。

选择 B 改变的是**受支持的并发故障条件**，不是修复了上游锁。负责人已确认据此
修订 I0/I4 支持矩阵，后续按 B 实施和验收。只支持新版锁来源的路径不能解决当前 0.21.3 本机升级，
因此不作为替代目标自动实施。
