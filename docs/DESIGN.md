## 1. 三条根本原则（决策 2026-08-31）

1. **Profile 是唯一作用域边界。** 切换身份即切换整个工作区：会话、项目、归档、搜索、
   定时任务、用量、模型、技能、消息渠道全部只呈现当前身份。唯一例外：身份选择页/切换列表
   可显示其他身份的进行中/待处理计数（切换器天然需要全局视野）。
2. **一处切换，处处生效。** 全 App 只有身份选择页一个显式切换入口；唯一保留的隐式切换是
   通知深链（进会话前先切换）。`switchTo()` 是网关写操作、会失败：**失败时 UI 必须停留在
   原身份**并给出重试提示，禁止乐观更新。
3. **身份只由头像承载。** chrome（顶栏、FAB、分段、分组头、发送键）一律品牌色；
   身份的哈希色/自定义色只出现在头像圆上。列表页、聊天页不出现身份文字。

## 2. 色彩

### 2.1 基础（`ui/theme/Color.kt`，icon-blue 决策 0.1.61）
- 品牌主色 **蓝**：light primary `#0B5FD0`（Blue40）、dark primary `#A9C7FF`（Blue80）；
  背景冷调（light `#F7F9FD`）。历史：Mint 绿已废弃 —— 它与状态语义冲突（primary 同时
  兼任"完成"色只因绿恰好像成功），也与彩色启动图标打架。
- **状态色独立于品牌色**（`ui/theme/StatusColors.kt`，深浅双档、测试钉死）：绿=成功/完成
  只在状态语义中出现，不再与 primary 混用。chrome 永远蓝，状态永远走 StatusColors。
- 中性色、错误色等全部走 `MaterialTheme.colorScheme`；**禁止**新增只在单一主题下定义的
  硬编码色（每个颜色必须同时考虑深浅两个模式）。

### 2.2 深浅模式判定（强制，决策 2026-09-01）
- 深浅由**生效主题**决定：`MaterialTheme.colorScheme.surface.luminance() < 0.5f`。
- **禁止**用 `isSystemInDarkTheme()` 做样式分支。教训：应用内主题（随系统/浅色/深色）与
  系统设置可以不一致，曾导致"应用选深色、卡片仍是浅色白卡"的花屏（0.1.56 修复）。

### 2.3 淡卡语言（卡片页容器，`ui/nav/CardPage.kt`）
- 浅色：填充 `#FAFBFD`（冷调近白，与白底仅差 1–2 灰阶）+ `shadowElevation 1dp`；
  发丝线 `#EBEDF2`。注意：早期暖白 `#FAFAF8/#ECECEA` 在蓝调环境下泛黄，已随 icon-blue
  切换修正 —— 淡卡字面量必须与品牌冷暖一致。
- 深色：`lerp(surface, White, 0.06f)` 微提亮一阶、无阴影；发丝线 `lerp(surface, White, 0.14f)`。
- 精神：卡片轮廓靠**微差与微影**，不靠重填充；深浅两模式必须同一语言。

### 2.4 身份头像（`ui/theme/ProfileAccent.kt`、`ui/components/ProfileAvatar.kt`，决策 2026-09-02 扩展）
- 渲染优先级：**照片 → 自定义色 → 自动色**。照片为中心裁方 512px WebP，存应用私有目录
  `files/avatars/`，DataStore 只记文件名（`ProfileIdentityStore`，设备本地；账号系统上线后
  云同步，记录自带 `updatedAt` 供合并）。
- 自动色：FNV-1a + fmix32 哈希 **profile 名**取色相，固定 `s=0.62, l=0.32`。
  l=0.32 是硬约束：全部 360 色相下白字对比 ≥3.9:1（`ProfileAccentTest` 钉死），因此实心样式
  **永远白字**、无需自适应黑白机制（该机制已于 0.1.55 删除，勿复活）。
- 自定义色：12 个预设色块（`AVATAR_SWATCHES`，10 色相 + 灰 + 近黑）或**色相滑条**（饱和度、
  明度锁定，只选色相，`avatarColorForHue`）。不开完整取色器、不显示色号。设置页色块第一格 =
  本身份的自动色、默认选中；**禁止**出现「自动（按名称生成）」之类解释性选项（用户 2026-09-02
  否决：看不懂）。
- 首字母取**显示名**；颜色永远按 profile 名算（改名不换色，通知强调色只认识 profile）。
- 字母头像两种样式（`AvatarStyle`）：实心 = 填充 + 白字；空心 = 描边 + 彩字、底为 surface。
  空心在深色主题把同一色相提亮到 **l=0.70**（`avatarOutlineColorArgb`；全部色相对 `#121921`
  ≥5.3:1，测试钉死），浅色照用 l=0.32。描边 48dp 及以上 2dp、以下 1.7dp。设了照片时样式开关隐藏。
- 作用域**仅头像**（列表、聊天、通知同步生效），不染 chrome。通知强调色 = 自定义色 ?: 自动色
  （`HermesNotifier.accentFor`）；本轮通知不显示照片。

### 2.5 M3 surface 容器族（决策 2026-09-02，`Color.kt`）
- `surfaceDim/Bright` 与 `surfaceContainerLowest/Low/·/High/Highest` **必须在两套 colorScheme
  里显式定义**（冷蓝中性系同色相推导）。教训：漏定义的 token 会回落到 Material 3 基线的
  紫红默认值 —— `ModalBottomSheet` 默认底色取 `surfaceContainerLow`，曾导致所有弹层/菜单/
  对话框带偏红底色。
- 取值（light → dark）：ContainerLowest `#FFFFFF→#0D141B`、Low `#F1F4FA→#1A212A`、
  Container `#EBEFF6→#1E252E`、High `#E5EAF2→#283039`、Highest `#DFE5EE→#333A44`、
  Dim `#D7DCE4→#121921`、Bright `#F7F9FD→#383F48`。
- 规则：sheet/menu/dialog 的容器色一律来自 colorScheme（默认值即可），**禁止**依赖 M3
  基线默认，也禁止为单个弹层硬编码底色来"修"色偏 —— 色偏必须在 token 层修。

### 2.6 图表色板（决策 2026-09-04，`ui/theme/ChartColors.kt`）
- 用量图表的三段（输入 / 输出 / 缓存读）是**同一个量的三种切分**，不是三个并列类别，因此用
  **同色相蓝的三档明度**，不用三个色相。三色相会读成"三件事"，也会和状态色语义打架。
- 取值（浅 → 深）：输入 `#00306A / #A9C7FF`、输出 `#0B5FD0 / #7793C9`、缓存读 `#5C8FDE / #5B7398`。
- **排序规则是对比度，不是明度**：「输入」永远是对比度最高的一档 —— 浅色下它最深，深色下它最亮。
  照搬"最深=输入"会让深色模式的主段落几乎消失。
- 三档对淡卡底（`#FAFBFD / #20272E`）的对比度全部 ≥3:1（浅 12.5 / 5.7 / 3.2，深 8.9 / 4.9 / 3.1），
  由 `ChartColorsTest` 钉死。**近白卡片上做不到三档都 ≥3:1 又彼此拉得开**，所以最深一档必须压到
  Blue20；不要试图把三档都放在 Blue40 附近。
- 图表色**不复用** `tertiary`。历史：旧版用 primary/tertiary 画输入/输出，珊瑚色在蓝底图表里读成
  警示色。图表色板与状态色（§2.1）同样独立于品牌色，但二者互不通用。

## 3. 字体与文本适配

### 3.1 全局
- Type ramp 见 `ui/theme/Type.kt`；阅读界面（聊天、列表、设置）**跟随系统字体缩放**。

### 3.2 卡片页设计尺度锁定（决策 2026-09-01，仅限卡片页）
- 整页 `fontScale = min(system, 1.0f)`（LocalDensity 覆盖）。此锁**不得扩散**到阅读界面。
- 字号对照（sp，锁定尺度下，权威见 `CardPage.kt`）：

  | 元素 | 值 |
  |---|---|
  | 字标 Hermes GO | 26 Bold |
  | 身份名 | 20 |
  | 统计标签 / 副行 | 15 |
  | 统计数值 | 23 Bold（缩字下限 13） |
  | 快捷行文字 | 17（B 档密度，决策 2026-09-01） |
  | 快捷行右值 | 15（缩字下限 12） |
  | 头像字母 | 0.47 × 圆径，SemiBold（≈字符高占圆径 35%，参考稿实测） |

### 3.3 文本适配三级策略（通用，`CardPage.kt` FitText）
适用于所有"内容必须完整"的受限宽度文本（统计数值、设备名、行右值等）：
1. 单行内逐级缩字至下限；
2. 下限仍溢出 → **保持下限折两行**；
3. 两行仍溢出才允许省略号。数字与设备名不得在 ①② 之前被截断。

工程要点：
- 溢出检测必须用 `isLineEllipsized` —— `overflow=Ellipsis` 时 `didOverflowWidth` 恒为
  false，缩字永不触发（0.1.53 实坑）。
- 同一视觉行的左右两格字号**锁步**：任一格触发缩字，两格一起缩（父级受控状态）。
- 同一视觉行的左右两格**顶部对齐**，且每条文本槽位（标题 / 数值 / 副行）高度锁步：任一格
  折成两行时，另一格的同名槽位留出同样高度。**不得整格垂直居中**——居中会让内容矮的那一格
  被整体推下去，三条基线全部错开（HG-14，2026-09-06 实拍：右格「已连接 · 231 ms」折两行，
  左格「本周用量 / 184.0M / 77 次会话」整体下沉）。折行本身是 ② 级降级的正常结果，要修的
  是对齐，不是禁止折行。
- 延迟显示：<1000ms → `N ms`，否则 `X.X s`（四位数毫秒不配占宽）。

### 3.4 对照设计稿的方法论
参考图的像素与 dp **不可直接换算**（多为放大裁剪图）。规范做法：锚定一个双方共识字号
（如标签 15sp），其余按参考图**内部比例**推导；拿不准以真机观感裁决，并回写本文。

## 4. 图标

### 4.1 风格（唯一）
- **1.7dp 描边**、圆头圆角（StrokeCap/Join = Round）、24×24 viewport 手绘 `ImageVector`。
- **禁止** Material 填充式/outlined 图标混入此体系（它们按 2dp 裁切，观感重一档；
  例外：底部菜单、对话框等弹出层沿用 Material Rounded 与既有交互一致）。
- 语义底线：齿轮必须**带齿圈**（hub+刻线的"太阳式"曾被误读为亮度调节，0.1.58 废弃）。
- **小尺寸补偿**（决策 2026-09-02）：1.7dp 描边按 24dp 定；内嵌到 16–18dp（pill、行内）的图标
  缩放后只剩 ≈1.2dp，比旁边 labelLarge 的笔画还细。此类图标改用 `smallStrokeIcon`（描边 2.4，
  18dp 下 ≈1.8dp），与文字同重。先例：`ArrowToTopIcon`、`PromptListIcon`。

### 4.2 清单与尺寸
- 卡片页私有（`CardPage.kt`）：齿轮、时钟、月亮、立方体、下载盒、细箭头 ThinChevron。
- 公共（`ui/components/StrokeIcons.kt`）：FolderStrokeIcon、HomeFolderStrokeIcon（默认项目：
  文件夹内一间房子）、BranchStrokeIcon（git 分支）、ArchiveBoxIcon、ThinChevronIcon、
  PinStrokeIcon（置顶，小尺寸补偿 2.4 描边）、FeedbackBubbleIcon（圆角对话气泡带尾巴，卡片页
  反馈行；构造与同排的下载盒一致 —— 圆角矩形 + 一个小形状，五枚图标在 22dp 下同一密度；
  **留空心**，填充气泡在本应用已被聊天消息占用）。新增图标**优先入公共文件**。
- 尺寸：快捷行/齿轮钮内 22dp；行尾细箭头 20dp；**统计卡内箭头 16dp**（小一档，避免与
  23sp 数值抢注意力）；列表 leading（文件夹/归档盒）24dp；
  副行内嵌图标 14dp；聊天顶栏副标题内嵌图标与小箭头 12dp。

### 4.3 新增图标操作指引
1. 用 `strokeIcon(name) { pathBuilder }` helper（fill=null、1.7f、Round）；复杂路径可用
   `addPathNodes("svg path data")` 直接转写。
2. 发布前用 SVG 快速目检：把路径贴进 `<svg stroke-width="1.7">` 渲染成图核形状
   （模拟器不可用时的标准替代验证）。
3. 颜色永远交给 `Icon(tint=…)`，路径内 stroke 颜色会被覆盖，写 `Color.Black` 占位即可。

## 5. 页面与组件

### 5.0 Hermes GO 账号与 Hermes 身份

账号模式设计见 `ACCOUNT_MODE_DESIGN.md` 与 `ACCOUNT_PLATFORM_EXPANSION.md`。Android 必须把
**Hermes GO 账号**（邮箱验证码登录、设备授权与 Desktop 绑定）和现有 **Hermes 身份/profile**（Hermes 内部可选
身份）作为两个独立概念显示。账号登录不得删除或取代卡片页现有的 Hermes 身份选择入口。
正常登录后，Hermes GO 账号只放在设置及其账号详情页，不在卡片页、会话列表或
聊天页常驻显示；只有首次登录、凭证失效/撤销或绑定异常需要处理时，账号信息才临时出现在
设置外。
首版账号入口只允许邮箱 + 6 位验证码，不显示 Google/Apple 控件，也不要求平台 OAuth 配置。
邮箱挑战、交换幂等键、访问/刷新令牌和随机安装实例 ID 必须进加密存储；验证码只存在输入状态，
不得进入日志或诊断。后续增加平台登录时，不得用邮箱字符串在本地自动合并身份。
验证码页必须按服务端返回的 `expires_at` 和 `resend_after` 显示到期倒计时及重发冷却，冷却结束前
重发按钮保持禁用；重发成功后用新挑战完整替换旧挑战。应用进程重建时只恢复尚未到期的加密挑战，
始终清空验证码输入；挑战到期或时间字段无效时立即清除挑战并显示 `HR-AUTH-009`，不得向服务端
提交已知过期的验证码。“更换邮箱”与“重新发送验证码”必须是独立操作，前者清除当前挑战。倒计时
只在页面可见时运行，重新进入页面后按绝对时间重新计算；客户端倒计时只负责交互门禁，服务端仍是
到期、冷却、尝试次数和重放判定的最终权威。
账号错误卡片的“重试”必须重做实际失败的操作：发送/重发邮件、交换验证码、刷新设备或重新探测
原目标 Mac，不得统一退化为刷新页面；不可重试错误不显示可执行的重试入口。
账号会话意外失效或撤销后，客户端必须把“需要重新登录”作为加密持久状态保存，并立即停止账号
REST、生命周期收件箱和 WebSocket；即使设备还保留可用的旧版 Relay / App Token，也不得在重启、
分享入口或新建会话时静默回退。成功重新登录、明确执行“退出此手机账号”，或用户主动进入
“远程设备 > 旧版连接”时才解除门禁；保留旧版配置只用于兼容和显式恢复，不等于授权自动切换。
连接模式必须作为加密持久状态明确区分。只要账号仍登录且用户没有主动选择旧版连接，即使当前没有
默认 Mac，REST、WebSocket、启动门和新建会话也不得读取留存的 Relay / App Token；设备级请求返回
`HR-BIND-009` 并进入选设备修复。点击“旧版连接”后才切到旧版模式且跨重启保留；重新完成邮箱登录
或选择/重新检查任一 Mac 后自动回到账号模式。账号级生命周期收件箱在“需要选设备”状态仍可使用
手机 Bearer，但在明确的旧版模式下随旧版连接运行。WebSocket 端点解析遇到“需要选设备”或“需要
重新登录”的本地门禁后必须停止退避；只有修复完成、用户重试或后续前台恢复才开始新连接周期。
清除失效令牌时必须保留最近一次账号 Gateway 地址（不含任何凭据），重新登录的能力发现、发码和
验证码交换优先回到该地址，不得因为同时保存着另一个旧版 Relay 而把验证码流程发往错误服务。
修复式登录/重新选设备作为原页面上的临时目的地，不清空导航栈；账号与 Mac 恢复并通过启动门禁后
返回失效前的聊天或功能页。只有首次安装、冷启动时已无可恢复页面，或原栈不存在时才进入 Chats。
运行中的账号 WebSocket 因权限变化被 Gateway 关闭后，只允许一次重新握手来取得明确分类：账号模式
握手 `401` 持久化重新登录门禁，`404` 只撤销被拒绝的 Mac 路由，两者都停止该连接的退避循环。
客户端必须确认 Gateway 发起的 4403 关闭握手；分类握手本身若因网络/服务异常无法得到 401/404，
同样在这一次后停止，由用户重试或后续前台恢复开启新周期，不得继续无界退避。
若 `404` 属于当前默认 Mac，则清除选择并打开设备恢复；若只属于正在查看的历史/共享 Mac，则保留
仍有效的默认选择并把后续传输恢复到默认 Mac，不得连带清掉它。`HR-AUTH-006` 仅表示敏感操作需要
近期身份验证，不是会话失效，不得清除账号登录。
账号 REST 必须在统一响应边界执行同一套恢复规则，不能依赖当前页面自行清理状态：任意账号请求的
`401` 或 `HR-AUTH-003/004/005` 持久化重新登录门禁；只有明确的 `HR-BIND-011` 才按该请求实际携带的
Mac ID 修复设备路由。普通 `404` 和 `HR-AUTH-006` 不得清除账号、默认 Mac 或历史会话路由。
账号与设备管理页直接调用的已认证 Account API 也必须复用同一分类；进入重新登录或重新选设备状态时，
运行中的 REST/WebSocket 立即停用旧路由，不能等用户下一次请求才生效。`HR-AUTH-006` 使用注册表中的
双语近期验证提示，但仍保持当前账号、默认 Mac 和传输连接不变。
设置 > Hermes GO 账号中的“永久删除账号”是独立能力门控的危险区操作：只有 Gateway 的
`accountAuth.accountDeletion` 为 `true` 时才显示，关闭时整个入口缺席，不能用禁用按钮预告未上线能力。
入口使用错误色文字，点击后打开二次确认对话框；对话框必须同时说明所有云端会话、绑定与共享会立即
失效，云端个人数据会在固定 30 天后清理，原账号不可恢复且无法撤销，但每台 Mac 上的本地 Hermes
数据不会被删除。用户必须逐字输入 ASCII `DELETE`、单独勾选永久删除确认，再用当前账号邮箱完成
6 位验证码验证；输入文字、勾选和验证码只留在页面内存，不得写入存储或诊断。
确认勾选项的整行都是一个至少 48dp 的 Checkbox 语义点击目标，不能让复选框与说明文字形成两个
重复节点；危险色按钮必须使用组件颜色槽，让禁用态回到 Material 的不可用颜色而非继续显示红色。
删除验证挑战、绝对到期/重发时间以及验证幂等键写入加密存储，进程重建后可恢复到验证码步骤但始终
清空验证码输入。取得 `account.delete` grant 后，必须在发出 `DELETE /v2/account` 前同步持久化 grant
和最终删除幂等键；网络结果不明确或进程终止时，使用完全相同的请求自动恢复，不能生成新幂等键。
服务端返回成功或 `HR-ACCOUNT-012` 时均视为删除已提交：清除账号令牌、挑战与删除 grant，但保留一个
不含秘密的“删除已提交”本地门禁和最近账号 Gateway 地址。该门禁优先于留存的旧版 Relay / App Token，
立即停止账号 REST、生命周期收件箱和 WebSocket，并显示“云端账号删除已提交、本地 Mac 数据仍保留”的
终态。由于账号仍处在 30 天清理期，标题不能声称数据已经擦除；
只有用户主动选择“使用其他邮箱账号”或进入“旧版连接”才解除门禁，绝不静默回退。前者只
回到邮箱登录且不得读取旧版凭据，后者才显式启用兼容连接。`HR-AUTH-006/009` 清除已失效的删除
grant/挑战并要求重新获取验证码，不得清除仍有效的账号会话；可重试的网络/服务错误保留删除凭据并
提供“重试完成删除”。
手机端不新增“连接与设备”入口：卡片页现有“远程设备”统计格改为可点击，作为唯一绑定
Hermes 的单一入口。详情页列出当前账号拥有和别人共享给它的 Mac，明确标记“我的设备/共享给我”，
展示 Connector、Hermes、Gateway 与端到端状态，并承接诊断和迁移期“旧版连接”。设置页只管理
邮箱账号和本机登录，不重复显示远程设备。选择设备必须先提交云端默认选择并通过显式设备路径的
端到端探测，再切换本机 REST/WebSocket；任一步失败都保留原连接。
账号已登录但还没有可用 Mac 时，设备页显示 Desktop/共享引导，并且仅在页面可见期间每 5 秒
自动发现一次；离开页面立即停止。发现唯一可用 Mac 后沿用自动选择、云端默认提交和端到端探测，
成功后直接进入连接；发现多台时停止空态轮询并等待用户明确选择。
刷新发现当前选择已被撤销/移除时，若恰好只剩一台可用 Mac，则直接走同一选择与探测门禁接管，
成功时只重连一次；若剩余零台或多台，则清空失效选择并退出旧路由，等待自动发现或用户选择。
替代设备探测失败不得写入本机选择；原设备仍有效的普通手动切换失败则继续使用原设备。
每个会话必须携带并持久化其创建时的 Mac `device_id`（按 Hermes GO 账号 + profile + 会话 ID
隔离）。切换默认 Mac 只改变会话列表、搜索和后续新会话的目标；从列表、搜索、启动恢复、分享入口
或通知打开旧会话时，历史、元数据、运行态、通知动作和 WebSocket 都回到该会话原来的 Mac，不得
因为当前默认设备不同而串机。同一会话 ID 出现在两台 Mac 时必须仍视为两个独立会话/通知身份。
返回 Chats 页后恢复默认 Mac 的传输路由。原 Mac 的共享权限被撤销时，聊天空态显示
`HR-BIND-011` 双语说明，不得尝试到当前默认 Mac 查找同名会话。
正式切换前，现有 Relay URL / App Token / QR 流程仍是已发布版本的实现契约；切换时保留在
“远程设备 > 旧版连接”兼容入口，并按迁移测试门禁逐步退场。

### 5.1 卡片页（抽屉，`CardPage.kt`）
- `ModalDrawerSheet`：宽 86%、上限 360dp，右缘圆角 22dp，容器 = `surface`，遮罩默认 32%。
- **返回契约**：必须传 `drawerState`（预测性返回）+ 外层兜底 `BackHandler`；返回键永远
  先关抽屉、绝不退出应用；从卡片页进入的页面返回时**恢复打开的卡片页**（reopen 机制）。
- 结构：字标+齿轮钮 → 身份卡（仅当前身份 → 身份选择页；文字规则见 §5.10）→ 统计卡（本周用量｜远程设备，
  贯穿竖线，两格 `weight(1f)`）→ 快捷行：定时任务 / 主题 / 模型 / 检查更新 / 反馈与建议。
- **反馈与建议**（决策 2026-09-06）：末行，点击直接拉起 MissionGo 的反馈编辑器（一个独立
  Activity），不是路由行，因此无右值 —— 与「定时任务」同为无值行。**未配置 MissionGo
  endpoint/token 的构建里整行不存在**（含其上分隔线）：新克隆、他人机器和普通 CI 都拿不到这
  两个值，此时正确表现是"这个功能不存在"，而不是一个点了必然失败的入口。编辑器的明暗由宿主
  显式传给 SDK（应用内主题不改变资源配置，SDK 看不到），主题一变即同步。
- **统计卡两格都是入口**（决策 2026-09-03，账号更新 2026-09-08）：各自可点（用量页 / 远程设备页）、各带一枚
  16dp 细箭头、涟漪覆盖整半格（内边距放在 clickable 之内）。历史：曾出现「左半格绑了跳转却
  没有箭头、右半格不可点」的隐形可点区，违反下一条范式 —— 要么给箭头，要么别绑点击。
  单元格水平内边距 14dp（配 16dp 箭头）是为保住 23sp 数值不触发缩字，改宽度前先核算。
- 入口行范式：**图标 + 标题（+右值）（+徽标）+ 细箭头**。纯展示无箭头，可点必有箭头；
  徽标中性色（`surfaceVariant` 底），不用警示色。
- 主题行点开底部三选一（随系统/浅色/深色），与设置→外观共用同一存储。

### 5.2 会话列表（`SessionsScreen.kt`）
- 顶栏 `[头像36] 居中标题 [搜索]`，左右各 52dp 配平；头像即卡片页入口。
- 分段**三段或四段**（会话 / 项目 / [机器人] / 已归档，§5.16）：选中只用底色区分，**`icon = {}` 去打勾**（决策
  2026-09-01：打勾出现/消失会推移标签）。
- 分组顺序：需要你处理 → 已置顶 → **今天 → 前 7 天 → 更早**。
  - 时间桶（`groupByRecency`，决策 2026-09-01）：滚动窗口，精确区间 —
    今天 = `[今日零点, now]`；前 7 天 = `[今日零点 − 7×24h, 今日零点)`；其余（含无
    时间戳）= 更早。本地时区；clock/zone 注入可测。选滚动而非自然周，避免周初
    "本周"组瞬间清空（ChatGPT 同款约定）。
  - 组头可折叠（`SectionHeader`：labelMedium + 计数常显 + 箭头），折叠态
    `rememberSaveable`，**不跨启动持久化**；空组不渲染；组内新→旧。
- 行 = `ListItem`（白 surface 底），**无行间分隔线**（搜索结果页除外）。
- **副行统一组件** `SessionSubline`（决策 2026-09-02，方案 A「副行前缀」）：
  `[14dp 文件夹] 项目名 · 模型名`。项目名 = git 仓库根的 basename，缺失退到 cwd 的 basename；
  项目段最多占副行 60% 后省略号，模型名保持可见。**默认项目不显示项目段**（缺省即默认，
  不写「无项目」占位）。图标用 onSurfaceVariant 中性色，不用品牌蓝。会话列表、已归档、搜索
  标题匹配三处共用；项目内钻入行改为 `[分支图标] 分支 · 模型`（项目名由页头承担）。
  搜索的消息匹配行不显示模型（见下「搜索页」）。
- **置顶标记在副行**（决策 2026-09-02，设计稿 `docs/design/pinned-row.html` 方案 B）：
  `[14dp 品牌蓝描边图钉] [文件夹] 项目 · 模型`，图钉是副行第一个前缀。**不再用 ListItem 的
  leading 槽**：旧版 Material 实心图钉在三行项里顶对齐、两行项里居中，且把标题推到 52dp，
  与其他行不在一条竖线上。分组头「已置顶 · 仅此设备」仍是主要表达，副行图钉负责折叠 / 搜索等
  看不到分组头的场景。TalkBack 由图钉的「已置顶」描述承担。
- **置顶分区的插入不得把内容推出视口**（决策 2026-09-06，HG-11）：pin 存在设备本地，读盘晚于
  首帧就会让「已置顶」段在列表渲染之后才被插到最前面；LazyColumn 锚定原先的首个可见项，于是
  整段新内容落到视口上方，用户以为置顶没生效（实际要自己往回拉才看得到）。两条硬规则：
  ① **pin 未加载完不得渲染出「没有置顶」的形态**——首帧前先拿到 pin 集合（本地读盘，列表本来
  就要等一次网络往返，不增加等待）；② 用户手动置顶 / 取消置顶后，列表要主动把该会话的新位置
  带进视口，让用户看见它去了哪里，而不是从当前位置消失。
- **列表行不出现身份文字**（原则 3 的落地）：多身份时旧版曾在副行拼「身份：xxx」，
  2026-09-02 随副行组件一并删除。
- 长按菜单新增「移动到项目…」（置于重命名与归档之间），副行「当前：<项目>」；会话运行中
  该项置灰（网关 4009 拒绝）。点开的是唯一的选项目底部单（§5.3）。
- **归档一律二次确认**（决策 2026-09-06，HG-5）：会话列表长按菜单与聊天页「更多」菜单**两处
  行为一致**，都弹 `AlertDialog` 说明「归档后会话移到『已归档』，可以再恢复」。**不用 error 红色**
  ——归档是可逆的，§5.5 的「破坏性操作红色」针对的是不可逆动作，把可逆动作也涂红会稀释红色的意义。
  从聊天页归档成功后**退回会话列表**并 toast「已归档」；失败留在原地并给出错误码（`HR-SESS-008`）。
- cron 告警条：复用 `HealthStrip` 形态（ERROR=errorContainer / OVERDUE=surfaceVariant），
  仅失败/逾期时出现。
- 运行状态色走 `StatusColors.kt`（语义色，独立于品牌蓝；深浅双档）。
- **终态显示与清除**（决策 2026-09-02，`SessionRuntimeStore.isTerminalVerdict`）：
  - 「已完成 / 已中断 / 运行失败」是**待查看的结论**：会话不在眼前时保留在行内，**打开会话即清除**
    （三者走同一条 `markRead` 路径；回到前台时对正打开的会话同样清除）。
  - **本机按停止键的中断不显示任何状态**：用户自己做的事不需要提醒，运行时直接回空闲，
    只有聊天页时间线留「已中断」注记。远端 / 未知原因的中断才显示「已中断」。
  - 会话正被查看（前台 + 可见）时发生的中断或失败也不留结论，与「已完成」规则一致。
  - 行尾圆点只给「已完成」（绿）与未读；「已中断」「运行失败」**只留文字不留圆点**——
    终态灰点与未读圆点只差 1dp，曾被误读为未读。

#### 搜索页（`SearchScreen.kt` / `SearchResultRows.kt`，决策 2026-09-03，分析与规划稿
<https://claude.ai/code/artifact/b09c3722-1943-41df-bbae-504c14f85899> /
<https://claude.ai/code/artifact/f73ffe6d-66b3-42a3-affb-ccd6854136d8>）
- **作用域**：当前身份，活跃 + 已归档。标题匹配在本地即时完成，规则只有一条：**标题或项目名**
  （副行显示的那个）包含查询词，活跃与归档同规则，不再匹配完整路径。首帧用仓库缓存出结果。
- **搜索框**：全 app 唯一形态 `ui/components/SearchField.kt` —— 填充式 `surfaceVariant`、圆角 18dp、
  高 40dp、前置放大镜、有字时尾部 ×；IME 动作 = 搜索。聊天内搜索共用。
- **正文搜索触发**：自动。停顿 450ms 且 ≥ 2 字符后请求网关；键盘搜索键立即请求；新输入取消
  飞行中的请求。中文 / 日文 / 韩文 token 由客户端加引号后发送（网关会给未加引号的 token 追加前缀
  通配，而生产库的 CJK 路径把 `词*` 当字面量，永远不命中；`SearchQuery.kt`）。
- **两段结构保留**：「标题匹配」「消息匹配」各自段头（labelMedium primary，右侧计数 /
  状态）。消息段有六态：Idle（< 2 字，标题为空时提示"输入至少 2 个字符可搜索消息正文"）→
  Pending（改词即进入，**旧结果立即消失**）→ Searching（段头右侧「搜索中…」+ 顶部细进度条）→
  Results / Empty（段内一行「消息中没有匹配“xx”」）/ Failed（段内 `errorContainer` 圆角 8dp 错误条：
  `HR-SEARCH-001` 文案 + 「重试」，长按复制脱敏诊断）。标题段永不受正文失败影响。
- **消息匹配行**：主行 = 会话标题（单行省略）+ 已归档标签 + 相对时间（`relativeTimeLabel`，与列表
  时间口径一致）；副行 = 片段最多两行，以首个命中处为中心截取 ±40 字（`centerSnippet`，网关
  片段长度随搜索路径变化，客户端统一）；第三行 = `[文件夹 14dp] 项目名`，默认项目不显示。

  展开搜索条、填入词、定位第一处命中（§5.4）。查询词经 `SavedStateHandle` 跨进程重建。

### 5.3 项目 / 已归档
- **默认项目**（决策 2026-09-02）：网关启动目录是一个真实项目，名为「默认项目」，永远排在
  项目页第一位（即使 0 个会话），leading 用 HomeFolderStrokeIcon + onSurfaceVariant；
  副行「网关启动目录 · N 个会话 · 最近活跃」。术语只用「默认项目」，不再出现「无项目」
  「未关联」「无工作区」。
- **新建规则一句话**：会话页（及项目总览、默认项目内）新建 = 默认项目；钻入某个项目后

  视野——实测中用户因此判定「没收到文件」并向助手追责。图片不下移：助手生成的图片本身
  就是内容，不是正文的附产物。
- **文件附件卡整卡可点 = 打开**（决策 2026-09-06，HG-12）：卡片原先只有右侧「打开」「分享」

  可点；上传中 / 失败态不可点（宁可没有涟漪，也不要点了没反应）。这是入口行「可点必有箭头」
  范式的一处显式例外：文件名 + 类型/大小本身就表达了「这是一个可打开的东西」，卡片不再加箭头。

    列表项间距 = `listItemTop 2` + `listItemBottom 2` + 字体升降部 ≈ 11dp，而同一项折行是 12.6dp
    —— **项边界比行边界还弱**，「1、2、3 点」因此塌成一堵信息墙。靠调行高解决不了这个问题。

  - **列表标记**：有序与无序共用 **28dp 定宽标记列**，两种列表的文字左缘对齐。28dp 是按
    17sp 下两位数 `10.` 的宽度定的 —— 标记列自适应时，列表跑到第 10 条文字左缘会整体右移。

  - 「会话开始」段：灰字、无序号（留同宽空位对齐）、无时间。点行 = 关闭弹层并按胶囊同一规则跳到
    该组起点，气泡落地高亮 1.5s。英文 Your prompts / N prompts / Latest / You are here / Start of chat。
  - 数据侧待办（另立项）：连接器给历史消息补 `created_at`，之后副行时间自然出现。

- **聊天内搜索**（决策 2026-09-03，`ChatSearchBar.kt` / `ChatSearchHighlight.kt`）：
  - 搜索条**替换顶栏位置**（同一高度，`Scaffold.topBar` 二选一），消息列表不位移；行 =
    `SearchField` + 计数 `n/m`（0 时中性色）+ ↑ ↓ + ×；返回键先关搜索条。下一行三选一：当前命中的
    来源标签（正文 / 思考 / 工具）+ 片段（命中词高亮）；历史未加载完「正在加载对话…」；
    0 命中且 ≥ 2 字「此会话中没有匹配」+ 「在全部会话中搜索」（导航到搜索页 `search?q=`）。
  - **子串高亮**：正文经 Markdown 渲染器的 `annotator` 在 TEXT token 内加背景色 span；用户气泡、
    思考、工具输出是纯文本，直接 `AnnotatedString`。当前命中所在回合的标记 primary@38%，其余
    回合 primary@16%；整回合描边高亮（§5.4 既有）保留。多词查询按「整句优先，其次每个 ≥2 字
    的词」标记，因为 Markdown 行内文本按空白 / 标点切 token，整句很少落在同一 token 里。
  - **自动展开**：当前命中来源是思考 / 工具时，该回合内含查询词的思考卡 / 工具卡自动展开
    （`shouldAutoExpand`）；关闭搜索不强制收回。
  - **手动刷新 = 用户发起的验真**（决策 2026-09-05，覆盖 0.1.70「运行中排队等完成」）：刷新钮
    与列表下拉在运行中**不再排队**——"看起来不对"恰恰是 App 对运行状态的认知可能过期的时刻。顺序：
    先 `session.resume` 探测（Hermes 回 `session.info{running}`，最多等 1.5s），再拉历史按对账规则
    接受，最后三选一反馈：「已同步 · 运行已结束」（状态过期已纠正）/「已同步 · 仍在运行 · 已运行 N 分钟」
    /「当前对话已刷新」。视觉仍是顶部 `TopProgressLine`（§5.6），不新增指示物。同一探测函数也由
    前台唤醒与看门狗自动调用（`SessionRuntimeStore.probe`）。
  - **工具时间线的折叠**（决策 2026-09-05）：回合**进行中**时间线全铺开——它是进度。回合**已完成**
    后时间线顶部多一行摘要「N 次工具调用 · 总耗时 · M 次失败」+ 箭头；**首次以已完成状态进入视图的
    卡默认折叠**，只留摘要行。运行中看着它跑完的卡保持展开，不在完成瞬间收起——收起会让钉在底部的
    视口跳一下。展开态按回合记住（`rememberSaveable`）；搜索命中在工具里时自动展开（同上一条）。
    依据：0.1.93 首次把完成后的时间线保留下来，25 行常驻在完整回答上方，读起来是噪音而不是信息
    （用户反馈）。
  - **两次及以上就并成一组**（决策 2026-09-06，HG-3，`timelineThreshold = 2`）：原先要连续 3 次
    才并组，两次调用被画成两张各自带边框的卡，读起来就是「两件独立的事」，而它们其实是同一个回合
    里连着做的两步。**只有一次调用仍保持独立卡片**——那时没有「组」可言。与上一条叠加后，两次
    调用在回合完成时折成一行「2 次工具调用」灰字，正是本条要的效果。
  - **完成后的摘要是一行安静文字，不是卡片**（决策 2026-09-06，HG-15）：折叠只解决了长度，没解决
    重量。0.1.94 把完成后的时间线折成一行摘要，但容器仍是 `Surface` + 1dp 描边 + 16dp 圆角、文字
    labelLarge SemiBold，「查看思考过程」也仍是 M3 `AssistChip` —— 一个几乎不会被展开的控件用着
    卡片级重量，还占着答案的开场位置，读起来仍是噪音。回合**已完成**时：思考与工具摘要合并为**一行**
    `labelMedium` / `onSurfaceVariant` 文字 + 12dp 细箭头，**无描边、无填充、无 chip 形体**；
    **点击与自动展开行为一字不改**。工具时间线**进行中**不受此条约束——那时它是进度，该看得见，
    展开态仍用带描边的卡片承载明细。**思考开关两种状态都用安静样式**：它从来不显示进度（运行中的
    思考由 `RunningStatusLine` 表达），永远只是一个折叠开关，按状态换样式只会在完成那一刻闪一下。
    位置保持在正文之上（决策 2026-09-06 明确否掉「完成后挪到正文下方」：内容换位会在完成那一刻
    让钉底视口跳一下，正是上一条为之保留展开态所要避免的）。
  - **任务清单卡不得在回合结束后仍自称「进行中」**（决策 2026-09-06，HG-16）：卡片画的是 Hermes
    最后一次 `todo` 结果，而 Hermes 常常跑完就不再更新，于是一个 `in_progress` 条目会永久地假装
    还在做。回合结束后该条目**中性化**：去掉加粗与实心进行中标记，按普通未完成项渲染。**不标注
    「未完成」**——App 无从知道它是真没做完还是做完没回报，写死结论会冤枉它。卡片头部的状态方块
    同样必须跟随真实进度，不得写死 `in_progress`（3/3 也显示进行中是旧写法的 bug）。
  - **带词打开**：`ChatLaunch.initialQuery` 非空时进入即展开搜索条并填词，历史加载完后由既有
    的匹配 / 高亮流程定位第一处；每次进入只消费一次（`rememberSaveable`），旋转或返回不重开。

### 5.5 长按菜单与底部弹出框范式
统一 `ModalBottomSheet`：标题（≤2 行）+ `ListItem` 操作项（leading 图标）；破坏性操作
红色（error）且必须 `AlertDialog` 二次确认。
- **标题一律左对齐**（决策 2026-09-02）：titleMedium，与列表项文字共用 24dp 左基线。
  理由：会话名标题常折两行，居中后第二行短、与下方左对齐的操作项错位；短标题居中的收益
  小于长标题的代价，一套规范只选一个。模型选择器原先的居中标题已改为左对齐，右侧刷新钮
  保留。
- **聊天消息长按 = 开操作菜单，不是进选中态**（决策 2026-09-09）。这与 GPT/Claude 相反，是
  有意的取舍：
  - **为什么**：① 助手正文是 `markdownRenderBlocks` 切块后的多个 Composable，里面有可点链接、
    横向滚动的代码块（`CodeWithCopy`）、点击进全屏的表格（`ChatTableCard`）；`SelectionContainer`
    罩上去会与这些手势互抢。② 长按腾给菜单，历史消息就不必每条挂一排常驻图标 —— 常驻操作行
    只留在**最新一条**助手回答下。③ 会话是反向 `LazyColumn`，表项会被回收，**跨消息连选在任何
    方案下都不成立**，所以「像 GPT 那样」能拿到的上限也只是单条消息内选择。
  - **划词走全屏选择页**（`TextSelectionDialog`）：关闭钮 + 标题「选择文本」+ 右侧文字钮切换视图，
    正文是 `SelectionContainer` 包一个纯 `Text`。
  - **默认给正文，不给源码**（决策 2026-09-09）：进入时展示 `readableText()` 处理过的可读正文
    —— 标记去掉、结构留下（代码块逐字保留、空行保留、列表缩进保留）。来这里的常见动机是摘一句
    话发给别人，`**加粗**` 和 `| --- |` 不是读者看到的东西。右上「显示原文」一键切回 Markdown
    源码，旋转不丢（`rememberSaveable`）。链接在正文视图下只留文字，要 URL 就切原文。
  - **「选择文本」在菜单里固定第 2 位**，紧跟「复制」：它是复制的同族操作、粒度更小，也是进入
    选择的唯一入口；排在「换个模型重试」「朗读」后面等于藏起来。用户消息与助手回答同一规则。

### 5.6 动效与加载态（`ui/theme/Motion.kt`、`ui/components/BrandLoader.kt`）
- 导航转场：120–190ms tween + 轻微横向位移（chat 进出场见 `HermesNav.kt`）；
  折叠/列表项用 `animateItem()`；节制使用 —— 新动效先对齐这些时长再谈新曲线。

**加载动效体系（决策 2026-09-04，设计稿 `docs/design/loading-motion.html`）**
全 App 的"不确定等待"由启动图标推导：图标是四色四象限的折面 H，明暗只由单一光源决定，
所以我们的加载语汇是**光在转、形不动**，不是转盘在转。三条硬规则：

1. **多彩只属于品牌时刻，页面内一律单色 primary。** 依据 §1 原则 3 与 §2.1：加载动效里出现
   绿色会与 `StatusColors` 的"已完成 / 已连接"抢语义。多彩形态**只**留在启动门（§5.11），页面内
   没有例外：更新下载条也是单色 primary 的 M3 进度条。（早期草案想让确定进度也走三色渐变，
   砍掉了 —— 多一条例外就多一处会漂移的边界。）
2. **一个周期 `Motion.LoopPeriod = 1200ms`，一个延迟门 `Motion.RevealDelay = 250ms`
   + `Motion.RevealFade = 200ms`。** 1200ms 已是发送呼吸环与启动流光的周期；
   250ms 内结束的等待**什么加载物都不出现**（同 §5.4 气泡呼吸、§5.11 启动状态）。
   延迟门只管**占位型**加载 —— 在空白处新插入的加载物（`LoadingState` / `ListLoadingState`）。
   **原地替换一个已有图标**的行内标记（顶栏刷新钮、行尾切换态、上传图标）不加门：它不是多出来的
   家具，是同一位置的状态切换，用户刚点完就该立刻有反馈。
   聊天历史骨架原本自带 1350ms，已并入本 token。
3. **标记只替换"转盘形态"。** 进度条是另一个家族：页面刷新用顶部细线，下载 / 检查更新这类
   **卡内进度**继续用 M3 `LinearProgressIndicator`（有百分比是确定态，没有是不确定态）。
   永不显示假进度。`reduceMotion()`
   （系统"关闭动画"）下所有循环停在最亮一帧的 60%，静态可读，不留空框。

形态与场景对照（权威见 `BrandLoader.kt`）：

| 场景 | 形态 | 尺寸 |
|---|---|---|
| 行形状已知的列表首载（会话 / 项目 / 已归档 / 搜索） | `ListLoadingState` = 骨架行 | 照真实行，封顶 `SKELETON_MAX_ROWS = 5` |
| 行形状未知的页面首载（用量 / 模型 / MCP / 记忆 / 工具） | `LoadingState` = `HermesMark` | 32dp |
| 已有内容的刷新 / 加载更多 | `TopProgressLine` | 2dp 全宽，置顶不遮挡 |
| 聊天运行中（尚无内容 / 生成中 / 思考 / 跑工具） | `RunningStatusLine` = 标记 + 状态文字 | 14dp |
| 行内等待（刷新、切换身份、上传、图片加载、横幅） | `HermesMark` | 14–24dp，跟随原尺寸 |
| 下载 / 检查更新（卡内进度） | M3 `LinearProgressIndicator`，单色 | 全宽 |

- **标记**：H 静止，一束锥形亮光绕横梁中心（图标四色的交汇点）顺时针转；暗部 `DIM_ALPHA = 0.30`
  保证任何相位下 H 都读得出来。比例 14:15 取自图标本身。**不做**旋转形状、不做四象限跳闪。
- **骨架**：全页是**一条**斜向高光扫过（`rememberSkeletonSweep`），不是每块各闪；
  底色与高光 (`skeletonBaseColor` / `skeletonHighlightColor`) 与聊天历史骨架同一套。
  行形状不稳定的页面**禁止**画骨架 —— 猜错的骨架比转盘更差，内容一到就重排。
- **聊天页只有一个指示物**（决策 2026-09-04）：删除三点跳动 `TypingIndicator`。

**4. 手上有内容就不许盖骨架（决策 2026-09-07）。** 骨架只属于**冷开**——本机一个字都没有的那一次。
   一旦本地缓存能给出这条会话的历史，进入会话就**直接显示内容**，后台刷新走上表的
   `TopProgressLine`，不再把 alpha 压到 0 用骨架蒙住。
   在此之前，磁盘上没有历史，`markHistoryLoading` 期间 `historyLoading=true` 会把
   `initialPresentationReady` 摁回 false，于是**即使内存里已有这条会话的消息，用户看到的仍是骨架**，
   要一直等到网络回来 —— 内存缓存只省了布局，没省等待。真正的判据不是"有没有在刷新"，而是
   "**有没有东西可给用户看**"。
   保留的那一半是对的、不能删：揭示前仍要等 LazyColumn 连续几帧坐标稳定
   （`INITIAL_PRESENTATION_STABLE_FRAMES`），否则首帧是几条用户气泡、下一帧才吸附到助手尾部。
   命中缓存时这只是几帧，不是一个网络往返。
   缓存落在 `filesDir/transcript-history/`（gzip 的原始 REST 报文）：**不能放 `cacheDir`** ——
   `file_paths.xml` 的 `<cache-path name="captures" path="."/>` 把整个 `cacheDir` 交给了
   FileProvider，而 transcript 是用户的全部对话内容。备份侧已由 `allowBackup=false` 挡住。
- **指示物属于会话的这一轮运行，不属于某个气泡**（决策 2026-09-05，HG-8）：运行中而尚无
  assistant 气泡在流式（Relay 先观测到 `run.started`、`message.start` 还没到；或一次历史对账把
  进行中的行换掉了）时，同一个 `RunningStatusLine` 以"只有标记"的形态渲染在列表的**常驻底部槽位**
  （`bottom-edge`，与后台进程卡同槽），不新插 item——条件性插入会把钉在底部的视口顶起来。
  列表行说"思考中"、聊天页却一片空白，是这条规则缺席时的形态。
  它是 IM 的"对方正在输入"，而这里发生的是"你的 Mac 在干活"（启动页 0.1.81 删跳动省略号同一理由）。
  首个 token 之前**只有标记、不给文字**（「正在准备」只会被读一次就被真状态替换）；
  文字出现后标记不动、行高不变，48dp 页脚高度契约不变（§5.4 尾跳保护）。
  状态文字不再随呼吸变透明度 —— 一次只有一个东西在动。
- **审批 / 提问卡只活在等待它的那一轮运行里**（决策 2026-09-06，模拟器验 0.1.98 发现）：阶段一离开
  活动集（完成、失败、中断、观测到 `run.completed`），`pendingApproval` / `pendingClarify` 随
  `isGenerating` 一起在 `normalized()` 里清掉，不靠某个写入方记得。Hermes 对没人答的审批会超时
  自行拒绝再往下走，且不通知客户端；卡片若活过运行，重开已结束的会话就会再弹一张返回键关不掉的
  「需要审批」，答一次还把会话打成幻影「思考中」。断线（RECONNECTING）仍属活动，卡片保留（HG-8）。
  对已看到终态的运行再作答不重启它（`continueAfterInput`），从未见过终态的新进程仍乐观进入思考中。
  验证：`StalePendingCardTest`。
- **仍然用 M3 转盘的三种情况**（决策 2026-09-04，逐处在代码里写明原因）：① 按钮 / FAB 内部
  （新建会话），② 画在照片或头像上（全屏图保存、身份换头像）—— 这两种的底色不可预知，单色标记
  没有对比度保证；③ 颜色承载**状态语义**的指示器（会话行 `RuntimeIndicator` 走 `StatusColors`），
  染成品牌色会把两套色彩系统搅在一起。除此之外页面内不应再出现转盘。
- 验证：`BrandLoaderTest`（延迟门、行数封顶、关闭动画仍可见）、`RunningRowTest`（三态只有一个指示物）、
  截图 `status-preparing / loading-mark / loading-skeleton / loading-skeleton-dark`。

### 5.7 无障碍
- 可点目标最小 **48dp**（含 IconButton 默认触达区，图标本体可小于此）。
- 纯装饰图标 `contentDescription = null`；可操作图标必须给双语描述。
- 颜色对比：正文 ≥4.5:1，大字号/图形 ≥3:1（头像白字由 §2.4 的明度硬约束保证）。

### 5.8 间距
无独立 spacing scale（现状快照）：页边距 24dp（卡片页）/16dp（列表），组件内 16/18dp。
新界面**沿用最近似的现有页面取值**，不发明新值；如需体系化 scale 另行立项。

### 5.8 自下而上弹层（全局硬规则，决策 2026-09-02）
- **高度**：所有 `ModalBottomSheet` 一律使用 `ui/components/SheetDefaults.kt` 的
  `hermesSheetState()`（`skipPartiallyExpanded = true`）：内容多高弹多高，超过屏幕上限
  封顶全展开，**禁止半展开中间态**（半截可见、需手动上拉的形态是 bug）。需要额外约束
  （如审批弹层禁滑关）走它的 `confirmValueChange` 参数，不得另起状态。
- **手势（全局硬规则，决策 2026-09-03，由模型弹层专属升级）**：凡内容可滚动的 `ModalBottomSheet`
  一律 `sheetGesturesEnabled = false` + `dragHandle = { SheetCloseHandle(onDismiss) }`
  （`ui/components/SheetDefaults.kt`）：列表滚动永不带动、收起或关闭弹层；关闭只有三个入口：
  抓握区点按或短下拉（48dp 阈值）、点遮罩、返回键。已对齐：模型选择、我的提问。新弹层默认照此。
- **模型选择弹层**（`ModelSelector.kt`）：标题「选择模型」居中、刷新按钮居右；
  「当前状态卡」把模型（含作用域/恢复默认）与推理强度合为一张 surfaceVariant 卡
  （强度是模型的属性，禁止拆成两个并列框）；搜索框为填充式圆角（surfaceVariant 底），
  弹层圆角统一 16dp。
- **列表待处理项揭示**（`NeedsYouReveal.kt`）：会话新进入「需要你处理」组时，视口在顶部
  附近（首可见 ≤2）且非拖动中 → 自动滚顶展示；深翻列表时**禁止拽走读者**，改浮
  「↑ N 个会话需要处理」pill，点按跳顶，抵顶自动消失。

### 5.9 检查更新页（决策 2026-09-02，覆盖 2026-09-01 版）
- 页面仍是**单一推荐更新**界面：只有 manifest 的 `latestVersionCode` 可下载/安装。
  「版本记录」**常驻**推荐卡之下：最近 10 条直接铺开（一行摘要=首条说明，点击展开全部；
  当前版本带绿色「当前」徽标），更早的收进「更早版本（N）」显式展开。旧版本永不直接安装
  （Android 禁止覆盖降级）；**保留最近 5 个版本的 APK** 作回滚材料，更早的在每次检查时清理。
  APK 尚存的旧版本行提供「导出安装包」（复制到公共下载目录，导出前重新校验哈希）与
  「如何回滚？」说明（导出→卸载→安装→重新配置；渠道级回滚走 docs/APP_UPDATE.md 的
  roll-forward runbook）。
- 顶栏左对齐（二级页规范），「重新检查」为顶栏右侧刷新图标按钮，检查中原位转圈。
  当前版本区显示相对时间（刚刚/N 分钟前/今天·昨天 HH:mm/完整日期）。
- 状态色只出现在标题前的 8dp 圆点与徽标上（StatusColors 契约），标题一律正文色。
- 下载态压缩为一行：`已下载/总量` 左、百分比右、进度条下方，并明示「可离开本页，
  后台继续」。推荐卡说明超过 6 条折叠为「展开全部」。
- **分场景自动安装**：更新页处于前台（RESUMED）时下载校验完成→自动拉起系统安装器
  （每个任务只自动拉起一次）；页面不在前台→发「新版本已就绪」通知（activity 渠道，
  固定 id，点击回到本页），绝不从后台弹安装器。安装始终由系统安装器要求用户确认。
- 「我的」页入口行：索引预检（每小时最多一次、失败沿用旧值）发现新版时，行尾显示
  「新版本 x.x.x」与 7dp error 色圆点；升级完成后自然消失。
- **版本记录不排除当前版本**（决策 2026-09-06，HG-13）：只有当某个版本正**作为可下载更新**
  呈现在上面那张推荐卡里时，才从版本记录中省略它（同页不重复同一份说明）。已是最新时，当前
  版本必须留在版本记录第一条并带「当前」徽标——否则你正在用的这一版，它的更新说明在 App 里
  无处可读（0.1.98 实测：版本记录从 0.1.96 起，装着的 0.1.98 与漏发的 0.1.97 都读不到）。
- 索引超过 100 条时客户端取最新 100 而非整体拒收（字节上限 1 MiB 仍 fail-closed）。
- 进入页面即自动检查，同时独立恢复本地下载任务；断网或索引失败不得隐藏已下载、可安装
  的任务。下载可取消、失败可重试；暂停原因、下载错误和安全校验失败使用各自的双语错误码
  与恢复动作，技术原因仅在脱敏详情中显示。
- TalkBack 只播报阶段变化，不逐百分比播报；版本标题与「版本记录」使用 heading 语义，
  历史行播报「点击展开更新内容」；所有按钮保持 48dp（历史行内操作 40dp）最小触达区。

### 5.10 通知（决策 2026-09-02，设计图「Hermes GO 通知栏方案」）

- **一个会话一张卡。** 账号模式下通知 id 由设备 ID + profile + 持久会话 ID 共同决定，旧版模式仍由
  profile + 持久会话 ID 决定（`notificationIdFor`）；运行中 → 需要审批 →
  已完成是同一张卡的状态更新，绝不按事件类型堆卡。WebSocket、Relay 收件箱、未来的 FCM 都先归约进
  `SessionRuntimeStore`，再由 `SessionNotificationProjector` 投影出卡片；不存在第二条出卡路径。
- **账号收件箱属于手机安装，不属于当前 Mac。** 账号模式的 `/api/mobile/events`、送达确认和读取
  状态必须直接使用手机会话 Bearer 访问 Relay 自有端点，不得加 `/v2/devices/{id}` 前缀、转发到
  Connector 或回退携带旧版 App Token。持久游标按 Gateway + 账号 + 手机安装隔离并用哈希键存储；
  旧版连接继续沿用原游标。同步期间账号发生变化时，本批不得消费、确认或推进另一安装的游标。
- **卡片各位置只放一种信息**：小图标永远是 App 的 H 字形单色图标，`setColor` 用头像色
  （`avatarColorArgb(profile)`），部分国产 ROM 会用启动图标替换，所以颜色只是辅助；header 副文本 =
  「身份名 · 状态词」（单身份用户省略身份名），时间用事件真实发生时间（`setWhen`），运行中用
  计时器；标题 = 会话标题（无则「新会话」）；正文 = 该状态的具体内容；`setSubText` 放错误码或用时；
  动作最多 3 个，只放能在通知栏内完成的事。
- **语义色只出现在状态词与「拒绝」按钮**（设计图层面；Android 通知模板本身不支持给状态词着色，
  由系统渲染）。
- **状态与渠道**：运行中 / 重连中 → `run_progress`（LOW，静默常驻，`onlyAlertOnce`，有待办计数时显示
  进度条与「第 n/m 步」）；需要审批 / 需要你的回答 / 等待处理 → `attention`（HIGH，横幅 + 声音）；
  已完成 → `completed`（DEFAULT）；运行失败 / 需要检查 → `failures`（DEFAULT，独立渠道以便单独关闭）；
  后台连接 → `service`（MIN）；新版本 → `updates`（DEFAULT）。设置页四个开关分别对应前四个渠道；
  `service` 与 `updates` 没有开关。
- **连接状态的视觉分级**（决策 2026-09-04）：聊天页顶部横幅分三档，判据是「用户需不需要做点什么」。
  ① **不说**——中断短于 **2.5 秒**的一律不出横幅，也不出「连接已恢复」提示。切走再切回造成的
  socket 抖动对正在跑的任务毫无影响，为它闪一下横幅只会让人以为坏了。计时从**连接首次丢失**
  那一刻起算，不是从最近一次状态变化起算——重连退避会在 Reconnecting → Connecting 之间来回跳，
  按每次变化重新计时会让真正的长时间断线永远不显示。计时**只在聊天页可见时走**：App 在后台时
  空闲连接本来就是被主动关掉的，若让宽限期在后台跑完，切回来第一帧就成了「已中断」，接着又为
  一次用户从未看见的断开播报「已恢复」。用户看不见的时间不算打扰。
  ② **进度档**（`secondaryContainer` + 转圈）——`Connecting` / `Reconnecting` / `Disconnected`。
  中断会自行恢复（回到前台的一方立即重连），所以它是「带错误码的进度」而不是故障；文案仍写明
  `HR-CONN-004`，「详情」入口保留，便于复制诊断信息。
  ③ **故障档**（`errorContainer` + 详情 + 重试）——只留给 `ConnectionState.Error`，即 Relay 真的
  拒绝了我们（`HR-CONN-002`）。
  「连接已恢复」提示只在①之外出现：没告诉过用户断了，就不必告诉他修好了。
- **「后台监控方式」不随通知开关置灰**（决策 2026-09-04）：这组选项现在同时决定「任务运行时是否
  保持连接」，而「省电」是唯一能关掉保活的开关。跟着通知总开关一起禁用，等于让关掉通知的用户
  完全失去控制权——恰恰是最需要这个开关的那批人。其下四个按渠道的开关仍然跟随总开关禁用，
  因为它们确实只影响通知。

- **后台连接卡的出现条件**（决策 2026-09-04，修正 2026-09-02 的隐含规则）：`service` 渠道那张
  MIN 静默卡跟随前台服务，而前台服务的开启条件是「这台手机负责的任务还在跑」——手机自己发起的，
  或当前正打开着其聊天页的。**它不再受通知总开关约束**：通知开关回答的是「能不能打扰我」，
  连接保活回答的是「这个任务还要不要继续跟」，两者绑在一起会让关掉通知的用户（这是默认值）
  在任务跑到一半时被断连。因此关掉全部通知开关后，任务运行期间仍可能看到这张 MIN 卡；
  这是保住连接的必要代价，设置页的通知说明需要写明。**「省电」策略仍然压过这条规则**——
  那是用户明确要求停止后台工作，不是顺带的偏好。任务结束后卡片随服务一起消失。

- **审批卡**：正文 = 描述或「要运行命令」+ 命令；标准档动作「允许一次 · 本会话允许 · 拒绝」，高风险档
  「拒绝 · 打开查看」。**回答卡**：选项 ≤ 2 且非多选时选项直接做按钮 + 「回复…」；否则正文列编号
  选项，动作「回复… · 打开」。**已完成卡**：正文 = 最后一条回复前 140 字（无则「点击查看结果」），
  副文本 = 用时。**失败卡**：本地化短说明，副文本 = 错误码，动作「查看详情」；**需要检查卡**
  （已停止未确认）同渠道，动作「打开检查」。通知栏内不做「重试」，重发走聊天页的发送链路。
- **抑制规则**：正看着该会话的聊天页（App 前台且该会话可见）→ 不发；App 前台但在别处 → 静默发
  （`setSilent`）；后台 → 按渠道提醒。同一 kind 的刷新（工具切换、进度）永不重新提醒。
- **消失规则**：审批 / 提问被任一端回应 → 卡片随状态变为运行中；运行结束 → 同一张卡变已完成 /
  失败；进入该会话聊天页 → 取消；用户划掉的卡在状态种类不变前不再出现；已在聊天页看过的终态卡
  离开后也不再出现。
- **动作反馈**：按下后卡片变「处理中…」并撤下按钮；成功后随状态更新；失败时按钮回来，正文追加
  「发送失败，请重试」，副文本 `HR-NOTIF-001`。
- **锁屏脱敏版**（`setPublicVersion`）只保留图标、状态词、会话标题；命令、问题、回复内容不上锁屏。
- **多会话**：两张以上时发分组摘要「Hermes GO · N 个等待处理 · M 个运行中 · K 个已结束」；排序
  等待处理 > 失败 > 已完成 > 运行中。

### 5.11 开屏 / 启动门（`ui/startup/StartupScreen.kt`，决策 2026-09-02，设计稿 `docs/design/startup-redesign.html`）
- **层级**：字标是主角，图标是陪衬。图标 144dp（自适应前景层，可见 H 约 96dp）→ 12dp →
  字标 `HERMES GO` 32sp/Bold/字距 0.16em（`colorScheme.onSurface`）→ 8dp → 英文标语 14sp 次要色。
  取消旧版 250dp 图标与 8% 透明度光晕（近白底上不可见，等于白画）。
- **位置**：品牌组不再固定 -48dp 居中，图标顶边锚在屏高 **22.5%**（视觉中心约 42%），
  随屏幕高度按比例；**加载态与失败态图标、字标位置完全一致**，失败时不跳位。
- **状态归入品牌组**：标语下 44dp 放状态文字（13sp 次要色）+ 12dp + 进度条；进度条
  **144dp × 3dp** 与图标同宽，蓝→绿→黄渐变**锚定整条宽度**、用 clip 露出进度（旧版随填充
  拉伸，右端永远是黄）。屏幕底部只留版本行 `0.1.81 · DEBUG`（labelSmall，导航栏内边距外 32dp），
  测试渠道靠它对版本。
- **快启动不解释**：状态文字与进度条延迟 `STATUS_REVEAL_DELAY_MS = 700ms` 才淡入；若在此之前
  已到 READY，则**整段始终不出现**——快的启动只看到一次淡入，不看到流水账。文案从六段合并为：
  连接前四阶段共用「正在连接」（恢复场景「正在恢复连接」）、「正在准备会话」（恢复「正在恢复当前页面」）、
  「连接就绪」。阶段粒度仍驱动进度条。删除省略号跳动，进度条流光是唯一持续动效，READY 后停止。
- **入场 / 退场**：冷启动图标从系统 splash 落点（屏幕中心、**2×**——系统 splash 容器 288dp 对
  我们的 144dp，真机实测 118dp:58dp；2026-09-03 由 1.5× 修正）缩放平移到位（320ms，Standard），
  字标与标语延迟向上淡入 12dp；就绪后整屏 `fadeOut + scaleOut(0.98)`（`Motion.DurationMedium`），
  首页同时 `fadeIn + 上浮 16dp`（`MainActivity`）。失败态无 splash 可承接，改为 150ms 淡入。
- **热恢复静默**（决策 2026-09-03，取代「热恢复遮罩 150ms 淡入」）：**只有冷启动和真正的失败态
  可以占屏**。`CONNECTION_RECOVERY` 的加载态一律不渲染门 —— 会话页留在原位，继续显示它已经提交的
  内容，socket 由 `HermesGatewayClient` 自己的 500ms→10s 退避重连恢复。恢复失败才升起失败态门
  （它带错误码和「重新连接」/「检查连接设置」两个动作，是可操作的）。同时 `HOT_START_DEBOUNCE_MS`
  200ms → **3s**：先让退避重连自愈，抖动一次不再触发探测与首屏数据恢复。
  由来：旧规则下任何一次掉线都把全屏门盖到聊天页上，实测 2026-09-03 单日 55 次重连 = 几十次
  「被弹回启动页」，用户读作 App 崩了；同一次恢复还会把 0.5 MB 的 transcript 重复下载 7 次。
- **深浅**：由生效主题判定（§2.2）。底色是全 App 唯一必须与 window 资源一致的颜色
  （`@color/startup_background` 浅 `#F8FAFD` / `values-night` 深 `#0D141B` = surfaceContainerLowest dark），
  故浅深两组字面量成对写在 `StartupPalette`；次要色 `#74777F / #9AA0A8`，轨道 `#E7ECF6 / #2B323A`。
  多彩图标两种模式不变，字标走 `onSurface`，错误色走 `colorScheme.error`。已知限制：系统 splash
  只跟随 OS 夜间模式，「系统浅色而应用选深色」时 splash→门有一次颜色切换。
- **失败态**：进度条**隐藏**（半截彩条与红色错误文案打架）；错误摘要 bodyMedium 错误色、最宽 280dp；
  错误码 `HR-*` 从括号里拿出来**单独一行**等宽 labelSmall 次要色；「重新连接」实心钮 240dp × 44dp
  居中，「检查连接设置」文字钮同宽，不再通栏。账号启动探测必须保留结构化原因：只有
  `HR-AUTH-003/004/005` 进入重新登录；`HR-AUTH-007` 保持可重试限流，`HR-CONN-005` 明确提示启动
  Desktop，`HR-ACCOUNT-001` 明确提示账号不可用，`HR-ACCOUNT-002` 保持账号服务重试，不得全部折叠为
  登录失效或通用 `HR-CONN-002`。持久化重新登录门禁在冷/热启动都直接进入 `HR-AUTH-003` 修复态，
  不得探测或连接仍留存的旧版凭据。
- **紧凑（横屏 / 高度 < 560dp）**：图标 96dp 与字标（24sp）横排、左对齐，品牌组顶边 10% 屏高，
  状态与失败态仍在其下方居中。
- 验证：`StartupScreenTest`（延迟揭示、READY 早到不揭示、文案合并、失败态结构、版本行、
  热恢复不占屏、热恢复失败仍占屏）、`StartupCopyTest`，截图
  `startup-loading / startup-loading-dark / startup-failed`。

### 5.12 底部主操作按钮（决策 2026-09-02，首例 `ui/profiles/ProfileEditScreen.kt`）
- **适用**：页面有一个明确的提交类主操作（保存 / 连接 / 创建）且内容可能超过一屏。
- **形态**：Scaffold `bottomBar`，实心 `Button` 52dp 高、左右 16dp、上 8dp、下 16dp，再加导航栏
  内边距（`navigationBarsPadding`）；键盘弹出时随键盘上移（`imePadding`）；内容在其下方滚动，
  列末留 16dp。不加分隔线或底色，靠留白与内容分离。
- **不适用**：表单很短、主操作不需要随时可达的页面（定时任务编辑）用跟随内容的普通按钮，
  顶部 16dp；对话框内按钮按 M3 默认。
- 历史：身份设置页曾把 52dp 通栏按钮放在滚动列末尾，高屏留一大截空白、矮屏又随内容滚走，
  两头不靠——这是本条的由来。

### 5.10 新会话空态（决策 2026-09-03）
- 本地新建且无任何消息的会话渲染**居中问候组**：身份头像（48/64dp）＋时间问候＋固定副行
  ＋**纯展示**状态胶囊（`模型 · 推理档位` 前置 6dp 连接点，绿=已连接/琥珀=连接中）。
  组置于光学中心（垂直 bias −0.12）；IME 弹起时整组缩一档（头像 48dp、标题 19sp、副行隐藏）。
- 问候按时间五段（5–8 早上好 / 9–13 上午好 / 14–18 下午好 / 19–23 晚上好 / 其余 夜深了）；
  名字取身份自定义 displayName，未设置则省略（不显示占位名）。断连时副行换
  「连接恢复后就能开始」、胶囊换「等待连接…」——**新会话任何情况下不显示"历史消息暂时
  无法加载"**（isNewSession 独立分支）。
- 空态组无任何可点元素：模型/推理切换保持在输入框原位，胶囊只随其实时镜像；加号、发送、
  语音的位置与交互不因空态改版发生变动。首条消息出现，整组 150ms 淡出。
- TalkBack：整组一个语义节点，播报「新会话。{问候}。{副行} 当前 {胶囊}」。
- 未来的智能建议（服务端推荐/历史提炼）在胶囊下方追加，不改本节既有元素。

### 5.13 分享对话（决策 2026-09-02）
- 「更多 › 分享对话」**先弹格式选择层**（三项：文字 / Markdown 文件 / 长图），选定后才跳系统
  分享盘。每项一行说明，讲清各自适用场景，不让用户猜。
- **文字**：`EXTRA_TEXT` 直发，适合短对话直接粘贴。
- **Markdown 文件**：写入 `cacheDir/transcripts/`，经 FileProvider 以 `text/markdown` 分享。
  文件名 `HermesGO-<标题>-<时间戳>.md`，标题必须过 `transcriptFileBaseName` 清洗（路径分隔符、
  保留字符、换行、超长一律处理）。正文原样保留 Markdown，代码块与表格必须无损。
- **长图**：离屏 GraphicsLayer 渲染（`OffscreenTranscriptExporter`），三条硬规则 ——
  ① **固定浅色**渲染，无论 App 当前主题（深色长图在他人聊天里过重，且更扛不住二次压缩）；
  ② 底部**页脚**标注会话标题与导出时间 + Hermes GO；
  ③ **限长策略 A**：渲染前用 `transcriptImageFitsBudget` 预估，超出
  `TRANSCRIPT_IMAGE_MAX_HEIGHT_PX`（12000px，GPU 纹理与内存的安全线）**直接拒绝出图**并引导改用
  Markdown 文件 —— 宁可不出，也不给用户一张残缺或渲染失败的图。
- 长图中的图片附件：**已缓存的正常渲染，未缓存的画占位框**；导出绝不触发下载，分享动作不得
  阻塞在网络上。
- **导出必须记录文件附件**（决策 2026-09-05）：Markdown 与长图此前都只输出 `text`，文件附件
  在导出件里完全消失。用户拿导出的对话记录核对交付时，会把一次成功的附件投递误判为失败
  （2026-09-05 实际发生）。两种导出都要在该条消息末尾补一行 `附件：<文件名>`；长图同样只
  写文本行，**不下载文件**，与上一条的不阻塞原则一致。

### 5.14 用量页（`ui/usage/`，决策 2026-09-03 定位 / 2026-09-04 结构）

> 小节编号说明：本文 §5 的编号已被并发追加撞号（现存三个 5.10、两个 5.8、一个 5.13）。此处取
> 下一个未使用的号，不重排既有小节，以免与他人正在编辑的段落冲突。

- **定位：活动量优先，成本弱化为参考**（决策 2026-09-03）。主指标是 token 体量、会话数、调用数、
  模型占比；金额降级为带口径标注的次要信息。理由：Hermes 只统计成功返回用量的主对话调用，静默
  漏掉全部辅助调用与服务商侧重试，上游自己在面板里**默认隐藏**该数字，因为"看起来精确到可以和
  账单比"比不显示更糟。我们不重复这个错误。
- **三块必须对得上账**（决策 2026-09-04）。上游给的是两本互不相交的账：`daily`/`totals` 出自
  sessions 表、**只含主对话**；`by_model` 已把辅助调用合并进去。因此：
  - 顶部总量 = 主对话 + 辅助，且**显式写出这个拆分**；
  - 「按模型」标注**含辅助调用**，其逐行之和大于主对话是正确的，反过来才是回归；
  - 「按辅助任务」是同一笔辅助量的另一种切分，不额外计入总量。
- **每日图只能画主对话**（上游硬约束，不是取舍）。辅助用量按 `(model, task)` 聚合，**不带日期
  维度**，客户端补不出来。图表标题必须如实标注，不得把辅助量摊进日线。
- **范围分段 7 / 30 / 90 天，默认 30**（决策 2026-09-03），走 `days` 查询参数（上游钳制 1–365）。
  选择存设备本地，不上行、不跨设备同步 —— 它是查看偏好，不是身份数据。
- **稀疏行必须先补齐日历再取窗口**。上游对无会话的日子不发行，直接消费原始行会让「本周」变成
  「最近 7 个**有活跃**的日子」（稀疏使用时可跨月），也会让图表把不等间隔画成等距。
- **页面结构**（自上而下）：主指标卡 → 每日趋势 → 按模型 → 按辅助任务 → 成本 → 口径脚注。
  容器一律走淡卡语言（§2.3），列表行**无分隔线**（§5.2 同规），下拉刷新。
- **趋势图规范**：真实日期轴（两端 + 中点标注）、Y 轴三档刻度、点选某天打开当日明细弹层。
  禁止无坐标、无日期、不可点的纯色块 —— 那样的图只能看出"有起伏"，看不出任何一天。
- **成本区块**：独立成块并常驻一枚 ⓘ，点开说明口径（本机估算 / 不含辅助调用与重试 / 缓存写入
  不计 / 实际账单通常更高）。金额**不给两位小数**（`≈$4.2` 而非 `$4.23`），伪精度即误导。
  若上游 `dashboard.show_token_analytics` 为 false，则**跟随隐藏**成本区块（经 `/api/config` 读取，
  不需要改上游）。
- **空态与错误态必须可区分**：无用量 → 空态文案；取数失败 → `ErrorState` + 错误码 + 重试。
  历史：旧版两种情况都显示 `0 / 0 / $0.00`，用户无法分辨是没用过还是连不上。
- **口径脚注常驻**：统计窗口 N 天 · 按会话开始日归集 · 日界为 UTC。三条都是上游行为，写出来
  比让用户自己发现好。UTC 日界对 UTC+8 用户意味着凌晨 0–8 点的会话记在前一天 —— 这是已知偏差，
  改它需要动上游 SQL，属独立立项。
- **不属于用量的指标不放这里**：「会话总数 / 已归档 / 消息数」是被删除的 session-admin 页遗留，
  量纲与用量不同，已于 2026-09-04 移出。
- **抽屉统计格副行 = 会话数**，不是金额（决策 2026-09-03，§5.1）。半格可用文字宽仅约 95–107dp，
  放不下两段信息。

### 5.14b 启动门的阻塞规则（决策 2026-09-05）

启动门的职责是**在没有界面可显示时占位**，不是报告故障。一旦背后有可用界面，它就该让位。
**阻塞与否由 `reason` 决定，不由 `failure` 决定**：

| 场景 | 规则 | 理由 |
|---|---|---|
| 冷启动 / 首次配置 | 全屏 + 重试 | 背后什么都没有，阻塞是唯一诚实的选择 |
| 热启动 + 可自愈失败（`HR-CONN-001/002/005`、`HR-RPC-001`）| **隐藏启动门** | 界面早已渲染，用户上一秒还在看。交回给健康条（可达性）、聊天页横幅（socket）、页面自身刷新（数据）——它们都能报告而不夺走整个 App |
| 配置 / 鉴权（`HR-CONFIG-001/003`、`HR-AUTH-001`）| 冷热都接管 | App 真的没法工作，必须让用户去修。走 `RepairRequired`，不经过上面这条 |

- **完成动效只属于冷启动**。热启动就绪后立即隐藏，不再多停 `SUCCESS_COMPLETION_MS`——背后本来
  就是可用画面，多出的半秒是「无缘无故闪了下启动页」而不是仪式感。
- **首屏恢复的成功判据是历史对齐，不是拿到 live handle**。跑完的会话本来就没有 handle，把它
  当失败会让一次完全正常的返回变成全屏报错（HG-1）。

### 5.15 诊断页（`ui/settings/DiagnosticsScreen.kt`，决策 2026-09-05）

- **release 构建默认关闭，debug 构建默认开启**（决策 2026-09-08）。开关文案必须同时讲清三件事：
  记什么、令牌不记、记录存哪里存多久。少任何一条，用户就无法判断该不该开、开了要不要关。
  由来：默认关闭意味着一次故障只有在用户**事先**打开过开关时才留得下证据，于是首次发生的那一次
  必然查不了——HG-27 之所以只能停在「现有日志无法判定」，一半原因在此。当前所有交付给测试者的
  APK 都是 debug 构建（`scripts/package-debug-apk.sh` → `Hermes-Remote-<版本>-debug.apk`），
  所以这条实际等于「日常在用的这个 App 一直在记」。release 保持关闭，隐私决定不变。
  **用户的显式选择在两个方向上都压过默认值**：在 debug 构建里关掉它，重启后必须仍然是关的。
- **记录跨进程存活**（`data/diagnostics/DiagnosticLogStore.kt`）。开启后条目除了进内存环形缓冲
  （500 条），还滚动落盘到应用私有目录（两个文件轮换，各 256KB，保留 7 天），下次启动读回。
  理由：最值得看的那些运行——崩溃、息屏后被系统杀——恰恰是内存缓冲活不下来的那些。
- **上一次运行的条目必须标出来**。恢复的条目时间戳与本次运行同一时钟，光看时间分不清，所以
  行首标签追加「· 上次运行」并改用 `onSurfaceVariant`（本次运行为 primary）。**禁止**只靠
  时间戳暗示来源。
- **分享导出磁盘全量，且必须是文件**（决策 2026-09-05）。页面列表仍只显示最近 500 条（滚动
  性能），但分享出去的是整个滚动文件——内存那 500 条在会话活跃时只覆盖几分钟，通常短于"遇到
  问题→走到设置"这段路，导出封顶等于把现场丢掉。载体是 `FileProvider` 附件而不是
  `EXTRA_TEXT`：几百 KB 的 Intent extra 会撞 Binder 事务上限，侥幸没撞的接收方也常自行截断，
  截掉的正是让全量导出有意义的那前半段。读盘必须离开主线程。
- **每次开启写一条会话头**（`session` 频道）：版本号、versionCode、pid、系统与机型。导出既然
  按一条流读回，per-entry 的"上次运行"标记无法再表达进程边界，改由会话头承担；顺带补上截图
  永远带不出来的构建信息。
- **「标记现场」按钮**：往日志插一条显眼分隔。否则读一份分享来的日志第一步永远是猜哪一分钟
  才是现场——而末尾那几行通常是用户走到设置页的导航，不是故障本身。
- **轮询噪音必须压住**。收件箱轮询在前台每 2 秒一次；请求与响应各记一行时，基线约 1 行/秒，
  500 条缓冲约 8 分钟就被挤空。快速成功的轮询不记（它说不出 `lifecycle` 频道没说过的事），
  慢的或失败的照记；传输层异常也必须记——只有开头没有结果，读起来和"请求再没回来"一模一样。
  **同一条规则适用于所有轮询**（2026-09-08 扩充）：`process.list`（每个活跃运行 5 秒一次）、
  `/api/profiles/sessions` 与 `/api/messaging/platforms` 的刷新。HG-27 那份报告里这四类占了
  500 条环形缓冲的 30%，与解释故障的行争抢同一份字节预算（磁盘上限是 2×256KB，实测 460KB
  只买到 31 小时，所以"加日志"必须同时"减噪音"）。
  **`/api/status` 是明确的例外，永远照记。**「REST 一路 200 而 socket 卡死」这个对比正是
  HG-27 能被读懂的原因；健康探针改为只在**档位**变化时出声之后（`Healthy` 带着 `latencyMs`，
  按值比较时每次探针都算"变化"，那条去重从来没生效过），它是唯一还承载这个信号的行。
  流式增量同理：`message.delta` / `reasoning.delta` / `thinking.delta` 一律不记——
  `thinking.delta` 曾漏在过滤器之外，占了 HG-27 缓冲的 5%。
- **连接快照**（决策 2026-09-08）。横幅升起的那一刻、以及提交反馈报告的那一刻，往 `ws` 频道写
  一行 `snapshot`：连接状态、socket 代号、`manuallyClosed`、就绪门是否完成、握手看门狗是否还活着、
  socket 是否存在、已经处在 `Connecting` 多久、距上次 `gateway.ready` 多久。
  由来：HG-27 的现场散在十几行里，而**恰好该说话的几处一行都没有**，结论只能停在"无法判定"。
  一行全量读数比十行散点更能回答"它当时到底卡在哪一步"。健康时这两个时刻都不会到来，
  所以字节成本接近零。**票据与令牌永不进入这一行**——WS URL 把单次票据带在查询参数里。
- **兜底路径不许静默**（决策 2026-09-08）。看门狗放弃、退避重连被丢弃、App 主动关闭连接、
  票据环节失败——这些"什么都没发生"的分支必须各自留一行，并写明**是哪一条 guard、哪一个调用方**。
  恢复机制的失败在日志里的样子就是"没有样子"，静默的提前返回等于没有兜底。
- **清除即彻底清除**：内存与磁盘一起清，不留"看不见但还在"的副本。
- **按会话筛选与导出**（决策 2026-09-05）：日志里出现过的会话 id 各成一枚 `FilterChip`（最近提到的在前，
  首枚「全部」）；选中后列表与「分享」都只包含提到该会话的行（`s=<id>` / `session=<id>`），分享主题
  带上 id。用户报告问题时交出的是**那一条会话**的证据，不是一周的全部活动。状态机的 `[phase]` 行、
  对账的 `[history]` 行、观测事件的 `[lifecycle]` 行都带 `s=<id>`，是这个筛选成立的前提。
- 崩溃报告（`data/diagnostics/CrashReporter.kt`）在面包屑之后、堆栈之前附带诊断日志，空区块
  不出现空标题。堆栈永远在最后一段——读的人滚到底就是崩溃点。


### 5.16 消息渠道与机器人会话（决策 2026-09-06，设计稿见上方画布索引第三条）

Hermes 可以接进钉钉、Slack、飞书等 33 个平台。这带来两类内容，**性质不同，位置也不同**：

| | 会话（内容） | 渠道管理（配置） |
|---|---|---|
| 位置 | 主屏分段第 3 位「**机器人**」 | 设置 → 消息渠道 |
| 出现条件 | **配过 ≥1 个渠道、或有渠道历史时才出现**；最后一个渠道移除后让开 | 常驻 |

**为什么是分段而不是一级页**：「已归档」是先例——同样是一类特殊会话，同样并进分段。
**为什么不直接混进「会话」段**：机器人流量会淹没交互式列表。分段是隔开的，不淹没任何东西。
**为什么配置必须留在设置里**：条件分段没渠道时不存在，「添加第一个渠道」需要一个常驻入口。

- **段名叫「机器人」**，不叫「渠道」。它同时解释了这些对话为什么只读；而「渠道」在公司语境里
  容易读成销售渠道。英文 `Bots`。
- **四段的宽度是硬约束**：390dp 屏、左右各 12dp → 每格 91.5dp。英文标签因此定为
  `Chats · Projects · Bots · Archive`——`Sessions` / `Archived` 在 fontScale 1.3 下会被截断
  且没有省略号，读起来像拼写错误。由 `ScreenshotTest` 的 `segments-*` 五张钉死。
- **段内按渠道分组**，组头带状态点；不用会话列表的时间桶——这里的问题是「Hermes 在钉钉上干了什么」。
- **本段不显示 FAB**。这些对话由对方在那边发起。

#### 机器人会话页：分类交给聊天页，本页只负责画

**硬规则**：这一页**不得自己判断一条消息是什么**。每一行先过 `botTurnKind()`，它转调聊天页的
`isHiddenTimelineMessage` / `timelineNoteFor`；只有判为真实轮次的才画成气泡或正文。

由来：这一页是同一份历史的第二条渲染路径，而它每次自行判断都会漏掉聊天页早就处理好的一类
消息——上下文压缩交接、待办快照、Markdown 渲染，最后是把
`[ASYNC DELEGATION COMPLETE …]` 画成一个带对方署名的聊天气泡，仿佛是本人打的字。
上游新增一个标记时，走同一条管线才能两个界面同时生效。

#### 机器人会话页：只读，且没有任何动作

Hermes 在这些平台上是**机器人身份**。从这里发出的任何内容都会以机器人名义出现，不会是本人；
handoff 也救不了（只有「本地会话 → 平台」一个方向，且要求会话活在 dashboard 进程里）。
所以这一页**没有输入框，也没有动作按钮**，顶部横幅与底部说明把这两件事直接讲出来。

气泡归属沿用 §5.4：**说话的人拿气泡，Hermes 无气泡**。私聊场景下右侧那个其实就是用户自己
（只是通过钉钉说的）；群聊里靠气泡上的署名区分。

#### 渠道状态：一律取服务端 `state`，禁止自算

服务端返回 `connected` / `pending_restart` / `startup_failed` / `gateway_stopped` /
`not_configured` / `disabled`。历史教训：客户端曾用 `enabled && gateway_running` 自算，
而这个组合**分辨不出「已连接」和「已保存但网关没重启」**，于是刚配好的渠道和启动失败的渠道
都显示成绿色「已连接」，而机器人一声不吭。

- 字段缺失或值未知时退化到「未配置 / 已停用 / 状态未知」，**永不退化成「已连接」**。
- `pending_restart` 是「一步没做完」而不是故障：用**中性淡卡**承载并带「重启网关」动作，
  不占用 `errorContainer` 警示条。重启会中断所有渠道当前的对话，必须 `AlertDialog` 二次确认（§5.5）。
- 状态色只走 `StatusColors`，且只出现在圆点上；`not_configured` / `disabled` 的灰
  **借用 `outline`**（`StatusColors` 只有 GOOD/WARN/BAD 三档，未新增第四档）。
- 平台标识用**中性圆容器 + 按类别的线性图标**（聊天 / 邮件 / 短信 / 通知 / 程序化），身份靠名字。
  不用品牌字形：破坏 §4.1 且涉及商标。
- 列表默认只显示**已配置**的；全目录在第二个分段里。

#### 一个告警槽位，根因优先

主屏顶部只有**一个**告警条，消息渠道与定时任务共用，位置在分段行之下、与选中哪一段无关。

渠道断线时，投递到它的定时任务失败**不计进定时任务徽标**，改写进渠道条文案
（「Slack 未连接 · 3 个定时任务受影响」），点进去是渠道——修在那儿。
自身原因失败的任务保留自己的告警。归并要求任务的 `deliver` **明确指名**该平台；
`origin` 解析不出具体平台，保留独立告警——**没归属的失败好过归错的失败**。

#### 三张列表共用的骨架（决策 2026-09-08）

会话 / 机器人 / 定时任务 / 消息渠道的列表页共用同一副骨架：

```
固定分段（不随列表滚动）
↓  可点的告警条（带箭头）
↓  分组列表
↓  右下 extended FAB（新建 / 添加）
```

**行尾一律是细箭头，整行可点**（§5.1「可点必有箭头」）。测试连接、启用开关这类操作放在详情页，
不塞进行尾——一行里三个可点区域，用户无法预判点下去会发生什么。
**顶栏不放「+」**：新建统一走 FAB，与会话列表既有范式一致。

渠道列表是唯一保留 leading 图标的：33 个平台需要区分。图标表达的是**类别**（聊天 / 邮件 /
短信 / 推送 / 程序化，`MessagingCategory`），不是品牌——品牌标志是填充式、多色且涉及商标，
三样都与 §4.1 冲突。未分类的平台落到「聊天」：绝大多数确实是，而给 webhook 画个对话气泡，
比给对话画个 webhook 图标错得轻。

#### 定时任务列表与本段同构（决策 2026-09-07）

三张列表（会话 / 机器人 / 定时任务）共用一套行文法与分组：

```
[名称] [状态点]                    [⋮]
副行：节奏或落点 · 上次结果
```

**健康的行不说「上次成功」**——那会让唯一失败的那行淹没在一片成功里。副行由纯函数生成
（定时任务是 `cronSublineText`），由测试钉住，而不是各画各的。

**行尾是溢出菜单，不是时间。**「下次运行」的精确时间在列表里帮不上判断（「每 10 分钟」加
「上次失败」才是决定要不要点进去的依据），留给详情页；而暂停 / 立即运行 / 编辑 / 删除
必须有入口。

分组一律 **需要你处理 → 正常 → 非活动**。定时任务列表因此去掉了 leading 图标
（原为 Material 填充图标，§4.1 禁止），状态改由标题行尾的圆点承载并走 `StatusColors`
（原先用 `colorScheme.primary` 当成功色，是 §2.1 那笔旧账的重演）。
唯一差别：**渠道列表保留 leading 类别图标**，因为 33 个平台需要区分。

#### 转到消息渠道（handoff）

入口在**聊天页的「更多」菜单**，作用对象是**自己的会话**，不是机器人会话。
只列出真的会被接受的渠道（已启用、已配置、设过落点）。

不可逆，所以确认框在点击前列出全部后果：目标渠道当前那条对话会结束、这条对话会从手机列表消失
（source 变成该渠道）、搬过去拉不回来。成功后退回列表，失败留在原地。

#### 通知

**只报渠道故障**，渠道里的新消息不提醒——钉钉已经响过一次了。独立通知分类，可单独静音。
检查搭在通知回退本来就有的十五分钟唤醒上，**不单开定时器**。
断线的渠道只提醒一次，恢复后再断才会再提醒。

## 6. 文案

- 产品名统一 **Hermes GO**（字标、磁贴、关于页、崩溃报告、诊断/对话分享主题、表格导出
  文件名 `HermesGO-Table-*`）。安装包 ID 与签名不变。
- 「切换身份」专指 profile；聊天内 Persona 选择叫「切换人格」，不得混用（决策 2026-09-01）。
- 所有用户可见文案走 `localized(language, zh, en)` 双语；错误提示遵循
  `ERROR_HANDLING.md` 的 `HR-<AREA>-<NNN>` 规范。
- **界面语言默认跟随系统**（决策 2026-09-06，实现 2026-09-08）。语言页三项：跟随系统 /
  简体中文 / English，默认选中「跟随系统」。解析规则：系统语言码为 `zh` 用简体中文，
  **其余一律英语**——不是回落到产品第一语言。繁体（zh-TW / zh-HK）按语言码匹配，暂落简体中文；
  繁体翻译另立条目，落地时是在这条规则里加一个分支，不是改这条规则。

  **类型上分两层，不要合并。** `LanguagePreference{SYSTEM,ZH,EN}` 是用户的选择，
  `AppLanguage{ZH,EN}` 是解析后真正用来绘制的语言，约 1000 处 `localized(language, zh, en)`
  只认后者。这与主题同构：`ThemeMode` 有 SYSTEM 档，而 UI 读的是它解析出的布尔值。
  把 SYSTEM 塞进 `AppLanguage` 会给每一个调用点留下一个它处理不了的分支。

  已安装用户中**从未打开过语言页的**（DataStore 无该键）升级后一并转为跟随系统，不写迁移；
  英文手机上的老用户因此会看到界面由中文变为英文，这是有意为之的一次性变化。
  显式选过语言的用户保持原选择。
