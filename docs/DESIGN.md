## 1. 三条根本原则（决策 2026-08-31）

1. **Profile 是唯一作用域边界。** 切换身份即切换整个工作区：会话、项目、归档、搜索、
   定时任务、用量、模型、技能、消息渠道全部只呈现当前身份。唯一例外：身份选择页/切换列表
   可显示其他身份的进行中/待处理计数（切换器天然需要全局视野）。
2. **一处切换，处处生效。** 全 App 只有身份选择页一个显式切换入口；唯一保留的隐式切换是
   通知深链（进会话前先切换）。`switchTo()` 是网关写操作、会失败：**失败时 UI 必须停留在
   原身份**并给出重试提示，禁止乐观更新。
3. **身份只由头像承载。** 身份的哈希色/自定义色**只出现在头像圆上**，绝不进 chrome —— 这是本条
   不可动摇的部分。chrome（顶栏、分段、发送键）默认品牌色，另有两处例外（决策 2026-09-10）：
   - **FAB 用中性近黑**（§2.7 第 1 条）：创建入口要与运行状态色分开。
   - **分组头跟着它那一组的语义走**，不再一律品牌蓝（§5.2）：「需要你处理」用琥珀，其余中性。
     旧写法把四个组头涂成同一个品牌蓝，等于告诉用户"这四组一样重要"，而它们并不是。
   两条例外都**不涉及身份色**，所以本原则要挡的东西没有被放宽 —— 放宽的只是"chrome 一律品牌色"
   这句话本身，它当初是作为实现手段写下的，不是目的。
   身份的哈希色/自定义色只出现在头像圆上。列表页、聊天页不出现身份文字。

## 2. 色彩

### 2.1 基础（`ui/theme/Color.kt`，暖调换肤 决策 2026-09-10；前身 icon-blue 决策 0.1.61）
- 底色是**暖纸**：light `surface`/`background` `#FAF9F5`，dark `#0F1217`。设计源是 Stitch 项目
  Hermes GO 的 design system `Hermes Mobile System`。
- **这推翻了 0.1.61 的冷调结论，但不是把旧方案捡回来。** 当年废掉暖白 `#FAFAF8/#ECECEA` 的理由是
  它配蓝 chrome 泛黄；那是"冷底 + 一块暖白卡"的局部冲突。本轮是整套重推 —— 纸面、中性族、
  容器族一起转暖，白色改作浮起层。冷暖必须整套一致这条原则没变，变的是基准。
- 品牌主色仍是**蓝**（原则 3：chrome 一律品牌色）：light `primary #004AC6`、
  `primaryContainer #2563EB`、`onPrimaryContainer #EEEFFF`。dark primary 见 §2.7，未定案。
- **列表行直接坐在 `surface` 上，不再有白卡。** 换肤前 `surface` 是纯白、`background` 是浅冷调；
  现在 `surface` 就是暖纸，纯白 `#FFFFFF` 降级为 `surfaceContainerLowest`，只用于浮起层
  （弹层 / 菜单 / 对话框 / 淡卡，§2.3、§2.5）。**这一条改变每一个 `ListItem` 的底色，全 App 生效**，
  不是会话列表的局部改动。
- 浅色角色色全表（括号内为实测对比度，全部达标）：

  | 角色 | 取值 | 配对 | 实测 |
  |---|---|---|---|
  | `surface` / `background` | `#FAF9F5` | `onSurface #1B1C1A` | 16.24 |
  | `onSurfaceVariant` | `#494641` | on surface | 8.92 |
  | `outline` | `#7A766C` | on surface（图形 ≥3.0） | 4.30 |
  | `outlineVariant` | `#C9C7C2` | 仅分割线，不设下限 | — |
  | `primary` | `#004AC6` | `onPrimary #FFFFFF` | 7.51 |
  | `primaryContainer` | `#2563EB` | `onPrimaryContainer #EEEFFF` | 4.54 |
  | `secondary` | `#605C54` | `onSecondary #FFFFFF` | 6.65 |
  | `secondaryContainer` | `#E4E1DA` | `onSecondaryContainer #605C54` | 5.10 |
  | `tertiary` | `#824500` | `onTertiary #FFFFFF` | 7.50 |
  | `tertiaryContainer` | `#A65900` | `onTertiaryContainer #FFEDE1` | 4.56 |
  | `error` | `#BA1A1A` | `onError #FFFFFF` | 6.46 |

  `onErrorContainer` 保留现有的 `#410002` 而不用设计源的 `#93000A`（后者 7.24 也达标）：
  `ErrorColorsTest` 钉的是现值，换它没有收益。
- **中性族与 secondary 族按暖调重推**（决策 2026-09-10）。设计源给的是冷调灰
  （`#434655` / `#737686` / `#C3C6D7` / `#5B5E68` / `#DCDFEB`），坐在暖纸上是 §2.3 那条教训的
  镜像版本 —— 冷暖必须整套一致。上表的值是保持或超过原对比度后重推的结果，深色档同理
  （`onSurfaceVariant #A8A49C` 7.55、`outline #8D897E` 5.37、`outlineVariant #423F3A`）。

- **状态色继续独立于品牌色**（`ui/theme/StatusColors.kt`，深浅双档、测试钉死）。
  **取值于 2026-09-10 与设计源逐条对齐**，改了两处：
  - **新增 `RUNNING`（青，浅 `#0369A1` 5.63 / 深 `#67E8F9` 12.94）。**「思考中」「正在输出」
    「正在使用 X 工具」此前落在 `onSurfaceVariant` —— **与副行同一个灰**，于是一个正在跑的会话
    和一个静止的会话，行内颜色完全一样。设计源给这个状态青色正是为了把"跑着呢"从静态信息里
    拎出来。这条从未被拿去与稿子比对过，直到用户指出。
  - **`WARN` 改为 `#C2410C` / `#FBBF24`，并去掉"仅限圆点"的限制。** 旧值 `#C77700` 在纸底上
    只有 3.29，注释写着 DOT ONLY，而会话行一直把它当 12sp 文字画。新值 4.92，限制不再存在。
  - 设计源用了三个琥珀（亮的给圆点与立柱，深的给组头与状态行），这里**收敛成一个**：最深的那个
    同时满足图形下限，而一行里三个相近的琥珀，读者无法据此做任何区分。
  - `StatusColorsTest` 的 AA 断言从"只查 GOOD 与 BAD"扩到**遍历全部 tone** —— 当年就是因为
    WARN 不在断言里，它才能带着 3.29 活那么久。
  - **深色档"四档等重"这条有一个有意的例外**：`RUNNING` 对暗底是 12.94，而 GOOD 10.71 /
    WARN 11.24 / BAD 10.68。原文说深色档"彼此等重、只靠色相区分"，那是针对**结论类**状态
    （完成/失败/等待都是已经发生的事）；`RUNNING` 是唯一表示"此刻正在发生"的状态，让它比
    其余亮一档是有意的，实机上它确实是一屏里唯一"活着"的那行。
  暖底上实测：浅色 GOOD `#2E7D32` 4.87、BAD `#C62828` 5.34、WARN `#C77700` 3.29；
  深色对 `#0F1217` 三档都在 11:1 一档（`#7CDC80` 11.08 / `#FFB945` 10.97 / `#FFB4AB` 11.05）。
  WARN 浅色档 **仍然只能作圆点，不能作文字**（3.29 < 4.5），这条约束换肤前后一致。
- **设计源里的绿 `#16A34A` 不可直接采用**：它在 `#FAF9F5` 上只有 **3.13**，作圆点达标、
  作状态行文字不达标。状态行文字一律走 `StatusColors` 的 `#2E7D32`。
- 中性色、错误色等全部走 `MaterialTheme.colorScheme`；**禁止**新增只在单一主题下定义的
  硬编码色（每个颜色必须同时考虑深浅两个模式）。
- **例外只有 Glance 小组件**（`widget/HermesWidget.kt`）：它在 `MaterialTheme` 之外，只能写
  字面量，取值须等于 light `primary`。它曾是唯一漏掉 0.1.61 换色的地方，一直挂着废弃的
  Mint40 `#087A5C`，直到暖调换肤把它衬得无处可藏（决策 2026-09-10 改为 `#004AC6`）。
  **换品牌色时不要忘记这个文件** —— 它不在 colorScheme 的保护范围内。

### 2.2 深浅模式判定（强制，决策 2026-09-01）
- 深浅由**生效主题**决定：`MaterialTheme.colorScheme.surface.luminance() < 0.5f`。
- **禁止**用 `isSystemInDarkTheme()` 做样式分支。教训：应用内主题（随系统/浅色/深色）与
  系统设置可以不一致，曾导致"应用选深色、卡片仍是浅色白卡"的花屏（0.1.56 修复）。
- **这条也管默认参数**（决策 2026-09-10）。`statusColor(tone, dark = …)` 的默认值一直是
  `isSystemInDarkTheme()`，于是"应用深色 + 系统浅色"时，未显式传 `dark` 的两个调用点
  （会话列表的「已完成」圆点、`StatusDot`）把**浅色档**状态色画到了暗底上：绿 3.66:1、
  红 3.34:1，都低于 §5.7 的 4.5:1。默认值已改为 `isDarkSurface()`。**新增按主题取色的
  API 时，默认值必须取生效主题**，别把正确性押在每个调用点都记得传参上。

### 2.3 淡卡语言（卡片页容器，`ui/nav/CardPage.kt`，方向反转 决策 2026-09-10）
- **浅色：卡比底亮。** 底是暖纸 `#FAF9F5`，卡是纯白 `#FFFFFF`（= `surfaceContainerLowest`）
  + `shadowElevation 1dp`；发丝线 `#EFEEEA`（= `surfaceContainer`）。
- **这与换肤前相反**：旧版底是纯白、卡是近白冷灰 `#FAFBFD`，卡比底**暗**一档。暖纸本身带色，
  白色就成了"浮起"的信号，方向必须跟着翻。旧文那句"淡卡字面量必须与品牌冷暖一致"仍然成立 ——
  成立的正是它，所以基准转暖之后结论跟着反过来。
- 深色：不变。`lerp(surface, White, 0.06f)` 微提亮一阶、无阴影；发丝线 `lerp(surface, White, 0.14f)`。
- 精神不变：卡片轮廓靠**微差与微影**，不靠重填充；深浅两模式必须同一语言。
- **卡片页自 2026-09-11 起用稿子的纸色描边卡**（Stitch 基线-卡片页第二版，`Tiles.kt` 的 `card*` 令牌）：
  浅色 **`#F4F3EE`**（不是纯白 —— 第二版把卡降了一档）+ **1px 描边 `#ECEBE8`** + 1dp 微影，圆角 **16**；
  暗夜 `#1E232B` + 1px `#262C35`、无阴影；抽屉容器暗夜用 `surfaceContainerLow #161A22` 而非 `surface`。
  **卡片只剩两张**（身份、远程节点）：快捷行第二版起不在卡里，是坐在抽屉上的裸行 + `#EFEEEA` 发丝线。
  用量页仍用上面两条的旧淡卡（`tileColor()`），等它自己的稿再统一 —— 产品裁决，两份真相是暂时的。

### 2.4 身份头像（`ui/theme/ProfileAccent.kt`、`ui/components/ProfileAvatar.kt`，决策 2026-09-02 扩展）
- 渲染优先级：**照片 → 自定义色 → 自动色**。照片为中心裁方 512px WebP，存应用私有目录
  `files/avatars/`，DataStore 只记文件名（`ProfileIdentityStore`，设备本地；账号系统上线后
  云同步，记录自带 `updatedAt` 供合并）。
- 自动色：FNV-1a + fmix32 哈希 **profile 名**取色相，固定 `s=0.62, l=0.32`。
  l=0.32 是硬约束：全部 360 色相下白字对比 ≥3.9:1（`ProfileAccentTest` 钉死），因此实心样式
  **永远白字**、无需自适应黑白机制（该机制已于 0.1.55 删除，勿复活）。
- 自定义色：12 个预设色块（`AVATAR_SWATCHES`，10 色相 + 灰 + 近黑）或**色相滑条**（饱和度、
  明度锁定，只选色相，`avatarColorForHue`）。不开完整取色器、不显示色号。设置页色块第一格 =
  本身份的自动色、默认选中；**禁止**出现「自动（按名称生成）」之类解释性选项（用户 2026-09-02
  否决：看不懂）。
- 首字母取**显示名**；颜色永远按 profile 名算（改名不换色，通知强调色只认识 profile）。
- 字母头像两种样式（`AvatarStyle`）：实心 = 填充 + 白字；空心 = 描边 + 彩字、底为 surface。
  空心在深色主题把同一色相提亮到 **l=0.70**（`avatarOutlineColorArgb`；全部色相对 `#0F1217`
  ≥5.3:1，测试钉死；暖调换肤后最差色相 h=240 实测 5.64，约束依旧成立），浅色照用 l=0.32。描边 48dp 及以上 2dp、以下 1.7dp。设了照片时样式开关隐藏。
- 作用域**仅头像**（列表、聊天、通知同步生效），不染 chrome。通知强调色 = 自定义色 ?: 自动色
  （`HermesNotifier.accentFor`）；本轮通知不显示照片。

### 2.5 M3 surface 容器族（决策 2026-09-02，暖调重取值 2026-09-10，`Color.kt`）
- `surfaceDim/Bright` 与 `surfaceContainerLowest/Low/·/High/Highest` **必须在两套 colorScheme
  里显式定义**。教训不变：漏定义的 token 会回落到 Material 3 基线的紫红默认值 ——
  `ModalBottomSheet` 默认底色取 `surfaceContainerLow`，曾导致所有弹层/菜单/对话框带偏红底色。
- 取值（light → dark）：ContainerLowest `#FFFFFF→#0A0D11`、Low `#F4F4F0→#161A22`、
  Container `#EFEEEA→#1A1F27`、High `#E9E8E4→#1E232B`、Highest `#E3E2DF→#262C35`、
  Dim `#DBDAD6→#0F1217`、Bright `#FAF9F5→#2E343D`。浅色档来自设计源，深色档按同一暖中性
  色相推导（设计源只给了三档深色底，见 §2.7）。
- 相邻层级差（对比度比值）浅色 1.05–1.10、深色 1.04–1.12，都在可辨范围内。
  `surface → ContainerLowest` 是 1.053 —— 纸面到白卡故意只差一线，正是 §2.3 的"微差"。
- **`surfaceTint` 同样必须显式定义**（决策 2026-09-10）。它是 tonal elevation 叠色的目标，
  漏定义时回落到 `primary` —— 冷调时代蓝色叠在白 surface 上看不出来，换成暖纸后每一个
  `tonalElevation > 0` 的容器都变成冷蓝灰块（聊天页输入条实测 `#EDF0F3`，页面底是 `#FAF9F5`）。
  取值：light `#FFFFFF`（浮起 = 更接近白，与 §2.3 同一套语言）、dark `#E2E0DB`（深色没有可用
  阴影，tonal elevation 是唯一的抬升手段，必须朝亮走、绝不朝品牌蓝走）。由 `SurfaceTintTest` 钉死。
- 规则：sheet/menu/dialog 的容器色一律来自 colorScheme（默认值即可），**禁止**依赖 M3
  基线默认，也禁止为单个弹层硬编码底色来"修"色偏 —— 色偏必须在 token 层修。

### 2.6 图表色板（决策 2026-09-04，淡卡底随暖调更新 2026-09-10，`ui/theme/ChartColors.kt`）
- 用量图表的三段（输入 / 输出 / 缓存读）是**同一个量的三种切分**，不是三个并列类别，因此用
  **同色相蓝的三档明度**，不用三个色相。三色相会读成"三件事"，也会和状态色语义打架。
- 取值不变（浅 → 深）：输入 `#00306A / #A9C7FF`、输出 `#0B5FD0 / #7793C9`、
  缓存读 `#5C8FDE / #5B7398`。**换肤不需要重推三档蓝** —— 变的只是它们坐的那块卡。
- **排序规则是对比度，不是明度**：「输入」永远是对比度最高的一档 —— 浅色下它最深，深色下它最亮。
  照搬"最深=输入"会让深色模式的主段落几乎消失。
- 淡卡底基准随 §2.3 更新为 `#FFFFFF / #1A1F27`（原 `#FAFBFD / #20272E`），三档实测
  浅 12.9 / 5.9 / 3.3，深 9.7 / 5.4 / 3.4，全部 ≥3:1，由 `ChartColorsTest` 钉死。
  浅色档因为底从近白换成纯白，对比度反而略升。
- 图表色**不复用** `tertiary`。历史：旧版用 primary/tertiary 画输入/输出，珊瑚色在蓝底图表里读成
  警示色。图表色板与状态色（§2.1）同样独立于品牌色，但二者互不通用。

### 2.7 暖调换肤的四项定案（2026-09-10）
换肤过程中与设计源不一致、需要人裁定的四项，结论如下。四项都已落进 `Color.kt` 与本文档。

1. **FAB 用中性近黑**，浅暗两档都是 `#181C24`，白色 28dp 加号（白字对比 17.07）。深色档 2026-09-11
   由 `#1E232B` 改为与浅色同值，照暗色稿（§7 第 8 条）。
   采纳设计源的理由：创建入口要与运行状态色分得开。§1 原则 3 已相应放宽字面 —— 它要挡的是
   身份色渗进 chrome，近黑不涉及身份色。Stitch 项目里的 `会话页功能需求.md` 第 7 节
   （「FAB 品牌色底」）与本条冲突，**以本条为准**，那份需求文档需要同步改。
2. **分组立柱四档全部照稿上色**（本条 2026-09-11 重写，取值与理由见 §5.2 的表）。
   09-10 原定「只给需要你处理上色、其余中性」，09-11 上午复核时维持，同日下午产品负责人看过
   全灰的真机截图后推翻：一列灰立柱读起来太平。现在需要你处理 = 亮琥珀、已置顶 = 蓝、
   今天 = 绿、前 7 天与更早 = 石板灰，**但只有立柱上色**，标签与计数 chip 仍只有需要你处理带色。
   - 当年反对绿的理由（与「已完成」撞车，深色下同为 `#34D399`）依然成立，是被接受而不是被推翻的
     代价；记在 §5.2 与 fixture 的 `note` 里。
   - 立柱色是字面量而非 token，定义在 `Tiles.kt` 并给足浅暗两档 —— §2.1 禁的是**只在单一主题下
     定义**的硬编码色，两档齐全的成对字面量不在此列（`FabContainer*`、`Spinner*` 同例）。
3. **中性族整族转暖**，见 §2.1 的表与其下那条。
4. **深色 `primary` 沿用 `#A9C7FF`**（对 `#0F1217` 10.99），不采用设计源的
   `royal-cobalt-dark #3B82F6`（5.10）。§2.1 立的规矩是深色档「状态与品牌同权重、只靠色相区分」；
   深色三档状态色都在 11:1，换成 5.10 会让「已完成」的绿、「运行失败」的红明显压过顶栏与分段。

## 3. 字体与文本适配

### 3.1 全局
- Type ramp 见 `ui/theme/Type.kt`；阅读界面（聊天、列表、设置）**跟随系统字体缩放**。
- **字号阶梯对齐设计源，但按字号对齐、不按 token 名对齐**（决策 2026-09-10）。设计源
  `Hermes Mobile System` 的 token 名与 M3 槽位不是同尺寸：它的 `body-sm` 是 13px 而 M3
  `bodySmall` 基线是 12sp（本仓 70 处在用），`label-lg` 是 13px 而 M3 `labelLarge` 是 14sp（22 处）。
  **照名字对齐会把上百个调用点静默改大**。因此每个槽位保持既有字号，只吸收设计源的
  字重 / 行高 / 字距。
- 本轮实际变化三条：
  1. **字距在 16sp 及以上翻向**。设计源一律收紧（−0.01 ~ −0.02em），旧值一律放松
     （+0.1 / +0.15 / +0.2sp）。同一句话，收紧后明显更密实。
  2. **字重 500 → 600**（`titleMedium`、`labelLarge`、`labelMedium`）。设计源用字重拉层级，
     旧 ramp 只用字号拉层级。
  3. **`bodySmall` 与 `labelSmall` 补上定义**。它们此前未定义、静默继承 M3 基线 —— 与
     `surfaceTint` 回落 primary 是同一类隐患（§2.5）。取值等于基线原本给的，所以**不移动**
     任何现有版面，只是把它钉死。
- **两处刻意不采纳设计源**：
  - `bodyLarge` 保持 16sp。设计源的阅读档是 15px，但 `bodyLarge` 是聊天正文 —— 全 App 主要
    阅读面，缩小它是可读性决策而不是换肤细节。会话行需要的 15sp 由 §5.2 的专用样式提供。
  - 设计源的 **18px 档不落地**：本仓无消费者，且 M3 在 `titleLarge`(20) 与 `titleMedium`(16)
    之间没有槽位，塞进 `headlineMedium` 会让该槽小于 `headlineSmall`。记录于此，不落代码。
- **散文仍是系统默认字体；数据走打包的 JetBrains Mono**（决策 2026-09-11，推翻同日早些时候
  「不引入等宽字体」的决定，理由是改为严格照稿 —— §7 第 8 条）。
  - 资源 `res/font/jetbrains_mono.ttf`，**一个可变字重文件**在 400 / 500 / 600 三个实例上使用
    （`Type.kt` 的 `HermesMono`）。minSdk 26 正是可变字体起点，比打三份静态字重省约 80 KB；
    APK 因此增加约 187 KB。许可证 SIL OFL 1.1，随包发在 `assets/licenses/JetBrainsMono-OFL.txt`。
  - **只用在稿子标了 `font-mono` 的地方**：组头标签、「仅此设备」注记、计数 chip、会话副行的
    「项目 · 模型」，以及**仅**「正在使用 X 工具」那一条状态行。
  - **中文不受影响**：JetBrains Mono 不含 CJK 字形，中文照旧回落系统字体，浏览器里也是如此。
    真正变成等宽的是西文与数字 —— 仓库名、模型名、计数、工具名，以及英文界面下的组头。
  - Inter 仍未打包（2026-09-10 的评估不变）：它只改西文观感，对中文为主的界面性价比不足。

### 3.3 文本适配三级策略（通用，`CardPage.kt` AutoShrinkText）
适用于所有"内容必须完整"的受限宽度文本（统计数值、行右值等）：
1. 单行内逐级缩字至下限；
2. 下限仍溢出 → **保持下限折两行**；
3. 两行仍溢出才允许省略号。数字与设备名不得在 ①② 之前被截断。

工程要点：
- 溢出检测必须用 `isLineEllipsized` —— `overflow=Ellipsis` 时 `didOverflowWidth` 恒为
  false，缩字永不触发（0.1.53 实坑）。
- 同一视觉行的左右两格字号**锁步**：任一格触发缩字，两格一起缩（父级受控状态）。
- 同一视觉行的左右两格**顶部对齐**，且每条文本槽位（标题 / 数值 / 副行）高度锁步：任一格
  折成两行时，另一格的同名槽位留出同样高度。**不得整格垂直居中**——居中会让内容矮的那一格
  被整体推下去，三条基线全部错开（HG-14，2026-09-06 实拍：右格「已连接 · 231 ms」折两行，
  左格「本周用量 / 184.0M / 77 次会话」整体下沉）。折行本身是 ② 级降级的正常结果，要修的
  是对齐，不是禁止折行。**这一条的原始场景（卡片页的两格统计卡）已随 2026-09-11 的稿子取消**，
  规则本身对任何左右分栏仍然成立，用量页就在用；`FitText` 那个父级受控的实现也随之删除，
  卡片页现在只用 `AutoShrinkText`。
- 延迟显示：<1000ms → `N ms`，否则 `X.X s`（四位数毫秒不配占宽）。

### 3.4 对照设计稿的方法论
参考图的像素与 dp **不可直接换算**（多为放大裁剪图）。规范做法：锚定一个双方共识字号
（如标签 15sp），其余按参考图**内部比例**推导；拿不准以真机观感裁决，并回写本文。

**例外是 Stitch 导出的 HTML**（决策 2026-09-11）：它是 Tailwind 类名写死的 CSS px，按 390 视口作图，
**1 CSS px = 1 dp**。间距、字号、圆角、动效时长直接读类名（`px-4` = 16dp、`text-[15px]` = 15sp、
`rounded-xl` = 12dp、`duration-200` = 200ms），不需要锚点换算；`scripts/design/stitch-render.sh` 能把它
按 Roborazzi golden 的尺寸（411dp @ 2.625x）渲染成可叠图的参照。仍需锚点法的只有位图：截图、
AI 生成的整页图 —— 那种东西量不出 dp，只能定风格不能定尺寸。

## 5. 页面与组件

### 5.0 Hermes GO 账号与 Hermes 身份

账号模式设计见 `ACCOUNT_MODE_DESIGN.md` 与 `ACCOUNT_PLATFORM_EXPANSION.md`。Android 必须把
**Hermes GO 账号**（邮箱验证码登录、设备授权与 Desktop 绑定）和现有 **Hermes 身份/profile**（Hermes 内部可选
身份）作为两个独立概念显示。账号登录不得删除或取代卡片页现有的 Hermes 身份选择入口。
正常登录后，Hermes GO 账号只放在设置及其账号详情页，不在卡片页、会话列表或
聊天页常驻显示；只有首次登录、凭证失效/撤销或绑定异常需要处理时，账号信息才临时出现在
设置外。
首版账号入口只允许邮箱 + 6 位验证码，不显示 Google/Apple 控件，也不要求平台 OAuth 配置。
邮箱挑战、交换幂等键、访问/刷新令牌和随机安装实例 ID 必须进加密存储；验证码只存在输入状态，
不得进入日志或诊断。后续增加平台登录时，不得用邮箱字符串在本地自动合并身份。
验证码页必须按服务端返回的 `expires_at` 和 `resend_after` 显示到期倒计时及重发冷却，冷却结束前
重发按钮保持禁用；重发成功后用新挑战完整替换旧挑战。应用进程重建时只恢复尚未到期的加密挑战，
始终清空验证码输入；挑战到期或时间字段无效时立即清除挑战并显示 `HR-AUTH-009`，不得向服务端
提交已知过期的验证码。“更换邮箱”与“重新发送验证码”必须是独立操作，前者清除当前挑战。倒计时
只在页面可见时运行，重新进入页面后按绝对时间重新计算；客户端倒计时只负责交互门禁，服务端仍是
到期、冷却、尝试次数和重放判定的最终权威。
账号错误卡片的“重试”必须重做实际失败的操作：发送/重发邮件、交换验证码、刷新设备或重新探测
原目标 Mac，不得统一退化为刷新页面；不可重试错误不显示可执行的重试入口。
账号会话意外失效或撤销后，客户端必须把“需要重新登录”作为加密持久状态保存，并立即停止账号
REST、生命周期收件箱和 WebSocket；即使设备还保留可用的旧版 Relay / App Token，也不得在重启、
分享入口或新建会话时静默回退。成功重新登录、明确执行“退出此手机账号”，或用户主动进入
“远程设备 > 旧版连接”时才解除门禁；保留旧版配置只用于兼容和显式恢复，不等于授权自动切换。
首次从仍可用的旧版连接登录账号属于受控迁移，不属于上述失效恢复：账号令牌与“等待激活”状态
必须一起写入加密存储，但旧版连接继续作为权威传输；客户端按 capability 发现账号 Mac，并且只有
Bearer 端到端探测成功后，才把设备、路由模式与“激活完成”原子提交并重连。未发现 Mac、网络失败、
服务错误或账号令牌在此阶段失效，都不得中断旧版连接；进程重启后仍须恢复同一等待状态。对于此前
已经启用账号传输后发生的令牌失效，仍执行前述 fail-closed 重新登录门禁，绝不借此回退旧版。
连接模式必须作为加密持久状态明确区分。只要账号仍登录且用户没有主动选择旧版连接，即使当前没有
默认 Mac，REST、WebSocket、启动门和新建会话也不得读取留存的 Relay / App Token；设备级请求返回
`HR-BIND-009` 并进入选设备修复；上述首次迁移的显式“等待激活”状态除外。点击“旧版连接”后才切到
旧版模式且跨重启保留；修复登录后选择/重新检查任一 Mac，或首次迁移的账号 Mac 通过探测后，才
回到账号模式。账号级生命周期收件箱在“需要选设备”状态仍可使用手机 Bearer，但在明确的旧版模式
下随旧版连接运行。WebSocket 端点解析遇到“需要选设备”或“需要
重新登录”的本地门禁后必须停止退避；只有修复完成、用户重试或后续前台恢复才开始新连接周期。
清除失效令牌时必须保留最近一次账号 Gateway 地址（不含任何凭据），重新登录的能力发现、发码和
验证码交换优先回到该地址，不得因为同时保存着另一个旧版 Relay 而把验证码流程发往错误服务。
修复式登录/重新选设备作为原页面上的临时目的地，不清空导航栈；账号与 Mac 恢复并通过启动门禁后
返回失效前的聊天或功能页。只有首次安装、冷启动时已无可恢复页面，或原栈不存在时才进入 Chats。
运行中的账号 WebSocket 因权限变化被 Gateway 关闭后，只允许一次重新握手来取得明确分类：账号模式
握手 `401` 持久化重新登录门禁，`404` 只撤销被拒绝的 Mac 路由，两者都停止该连接的退避循环。
客户端必须确认 Gateway 发起的 4403 关闭握手；分类握手本身若因网络/服务异常无法得到 401/404，
同样在这一次后停止，由用户重试或后续前台恢复开启新周期，不得继续无界退避。
若 `404` 属于当前默认 Mac，则清除选择并打开设备恢复；若只属于正在查看的历史/共享 Mac，则保留
仍有效的默认选择并把后续传输恢复到默认 Mac，不得连带清掉它。`HR-AUTH-006` 仅表示敏感操作需要
近期身份验证，不是会话失效，不得清除账号登录。
账号 REST 必须在统一响应边界执行同一套恢复规则，不能依赖当前页面自行清理状态：任意账号请求的
`401` 或 `HR-AUTH-003/004/005` 持久化重新登录门禁；只有明确的 `HR-BIND-011` 才按该请求实际携带的
Mac ID 修复设备路由。普通 `404` 和 `HR-AUTH-006` 不得清除账号、默认 Mac 或历史会话路由。
账号与设备管理页直接调用的已认证 Account API 也必须复用同一分类；进入重新登录或重新选设备状态时，
运行中的 REST/WebSocket 立即停用旧路由，不能等用户下一次请求才生效。`HR-AUTH-006` 使用注册表中的
双语近期验证提示，但仍保持当前账号、默认 Mac 和传输连接不变。
设置 > Hermes GO 账号中的“永久删除账号”是独立能力门控的危险区操作：只有 Gateway 的
`accountAuth.accountDeletion` 为 `true` 时才显示，关闭时整个入口缺席，不能用禁用按钮预告未上线能力。
入口使用错误色文字，点击后打开二次确认对话框；对话框必须同时说明所有云端会话、绑定与共享会立即
失效，云端个人数据会在固定 30 天后清理，原账号不可恢复且无法撤销，但每台 Mac 上的本地 Hermes
数据不会被删除。用户必须逐字输入 ASCII `DELETE`、单独勾选永久删除确认，再用当前账号邮箱完成
6 位验证码验证；输入文字、勾选和验证码只留在页面内存，不得写入存储或诊断。
确认勾选项的整行都是一个至少 48dp 的 Checkbox 语义点击目标，不能让复选框与说明文字形成两个
重复节点；危险色按钮必须使用组件颜色槽，让禁用态回到 Material 的不可用颜色而非继续显示红色。
删除验证挑战、绝对到期/重发时间以及验证幂等键写入加密存储，进程重建后可恢复到验证码步骤但始终
清空验证码输入。取得 `account.delete` grant 后，必须在发出 `DELETE /v2/account` 前同步持久化 grant
和最终删除幂等键；网络结果不明确或进程终止时，使用完全相同的请求自动恢复，不能生成新幂等键。
服务端返回成功或 `HR-ACCOUNT-012` 时均视为删除已提交：清除账号令牌、挑战与删除 grant，但保留一个
不含秘密的“删除已提交”本地门禁和最近账号 Gateway 地址。该门禁优先于留存的旧版 Relay / App Token，
立即停止账号 REST、生命周期收件箱和 WebSocket，并显示“云端账号删除已提交、本地 Mac 数据仍保留”的
终态。由于账号仍处在 30 天清理期，标题不能声称数据已经擦除；
只有用户主动选择“使用其他邮箱账号”或进入“旧版连接”才解除门禁，绝不静默回退。前者只
回到邮箱登录且不得读取旧版凭据，后者才显式启用兼容连接。`HR-AUTH-006/009` 清除已失效的删除
grant/挑战并要求重新获取验证码，不得清除仍有效的账号会话；可重试的网络/服务错误保留删除凭据并
提供“重试完成删除”。
手机端不新增“连接与设备”入口：卡片页的「远程节点」卡（2026-09-11 前是“远程设备”统计格）整卡可点，
作为唯一绑定 Hermes 的单一入口。详情页列出当前账号拥有和别人共享给它的 Mac，明确标记“我的设备/共享给我”，
展示 Connector、Hermes、Gateway 与端到端状态，并承接诊断和迁移期“旧版连接”。设置页只管理
邮箱账号和本机登录，不重复显示远程设备。选择设备必须先提交云端默认选择并通过显式设备路径的
端到端探测，再切换本机 REST/WebSocket；任一步失败都保留原连接。
账号已登录但还没有可用 Mac 时，设备页显示 Desktop/共享引导，并且仅在页面可见期间每 5 秒
自动发现一次；离开页面立即停止。发现唯一可用 Mac 后沿用自动选择、云端默认提交和端到端探测，
成功后直接进入连接；发现多台时停止空态轮询并等待用户明确选择。
刷新发现当前选择已被撤销/移除时，若恰好只剩一台可用 Mac，则直接走同一选择与探测门禁接管，
成功时只重连一次；若剩余零台或多台，则清空失效选择并退出旧路由，等待自动发现或用户选择。
替代设备探测失败不得写入本机选择；原设备仍有效的普通手动切换失败则继续使用原设备。
每个会话必须携带并持久化其创建时的 Mac `device_id`（按 Hermes GO 账号 + profile + 会话 ID
隔离）。切换默认 Mac 只改变会话列表、搜索和后续新会话的目标；从列表、搜索、启动恢复、分享入口
或通知打开旧会话时，历史、元数据、运行态、通知动作和 WebSocket 都回到该会话原来的 Mac，不得
因为当前默认设备不同而串机。同一会话 ID 出现在两台 Mac 时必须仍视为两个独立会话/通知身份。
返回 Chats 页后恢复默认 Mac 的传输路由。原 Mac 的共享权限被撤销时，聊天空态显示
`HR-BIND-011` 双语说明，不得尝试到当前默认 Mac 查找同名会话。
正式切换前，现有 Relay URL / App Token / QR 流程仍是已发布版本的实现契约；切换时保留在
“远程设备 > 旧版连接”兼容入口，并按迁移测试门禁逐步退场。

#### 5.1a 主题弹层（`ui/settings/ThemeOptions.kt`，照 Stitch 基线-卡片页/主题设置 / 暗夜 2026-09-11）

从卡片页「主题」行拉起的 `ModalBottomSheet`。抓手仍是全局 `SheetCloseHandle`（32×4dp，点击与下拉
都关闭，§5.8）；稿画的 36×6 抓手与自绘手势导航条都不采纳 —— 前者是全局共用组件，后者是稿子对系统
导航条的模拟。

- **提交语义：选择是暂态**（产品裁决 2026-09-11，**推翻**原先的「点一下即时生效并自动关闭」）。
  点选项只移动弹层内的待提交选择；**按底部「保存」才写库并关闭**；✕、抓手、遮罩、返回手势一律
  取消，什么都不写。因此单选点与徽标各说各的一件事：
  - **单选点** = 待提交的选择；
  - **「当前使用」徽标** = 此刻真正生效的主题。
  两者在没改动时落在同一行、改动后分开，徽标不是单选点的复述。浅色稿没画这枚徽标（标题右侧留成
  空 span），判为漏画，两版都加。
  按钮文案写**「保存 / Save」**而不是稿上的「完成」：按下才生效时，「完成」是不诚实的标签。这是
  本轮唯一一处主动改稿上的字。
- **设置→外观用同一套选项卡，但不是暂态**：那是一张页面、没有可等的按钮、也没有可取消回去的状态，
  点即写库，且不显徽标（在那里徽标只会复述旁边的单选点）。**同一套呈现、两套提交语义**，这一句是
  刻意的，别在其中一处"顺手对齐"另一处。
- **几何**（浅色稿为真源，1 CSS px = 1 dp）：弹层上圆角 28、底色 `cardThemeSheetColor()`；标题行
  左右内距 24、上下 8，「外观与主题」`CardThemeTitle`，右侧 32dp 圆形关闭钮（底 `cardIconTileColor()`，
  16dp ✕，**暗色加 1px 描边、浅色不加** —— 暗色用描边代替阴影，与卡片页同一手法）；选项列表左右 20、
  上下 12、卡间距 8；每张卡圆角 16、内距 14、1px `cardThemeBorderColor()` 描边，内部
  `[40dp 图标章（圆角 12、1px 描边、内嵌 20dp 图标）] 14 [标题 (+徽标) / 说明] → 12 [20dp 单选点]`；
  页脚左右 24、上 16、下 24，按钮通栏高 48、圆角 12。
- **字**：标题 `CardThemeTitle` 18/600/−0.45；选项名 `CardThemeOptionTitle` 14/600/0（**不是**
  `CardNodeTitle`，那档带 tracking-tight）；说明副行复用 `CardIdentitySub` 12/400；徽标
  `CardThemeBadge` 10/600；按钮 `CardThemeCta` 14/500（暗色稿是 600 + tracking-wide，几何取浅色）。
- **层级**：浅色弹层与选项卡同为纯白、靠 1px 发丝线划界；暗色选项卡比弹层低一阶。一句话统一：
  **选项卡永不高于弹层，边界由发丝线承担**。这与 §2.3「卡比底亮」不同，也不必相同 —— 弹层本身
  已经是抬起层，卡在其内没有再抬起的余地。
- **强调色是近黑 / 近白**（`cardThemeAccentColor()` `#181C24` / `#E2E0DB`），用于选中单选点与保存
  按钮底。这是 §1 原则3「chrome 一律品牌色」的**第二个例外**，第一个是 FAB（`Tiles.kt`
  `FabContainerLight`），理由同源：挑主题不是运行态，一块品牌蓝在满是蓝色状态信号的界面里会被读成
  又一个状态。浅档与 FAB 同值但单列成 token —— 两者语义无关，动一个不该拖着另一个。
- **单选点画法取暗色稿**：环 + 点。浅色稿把 20dp 圆整个填成强调色再 inset 一圈 4px 白，在白卡上
  渲染出来是一个没有外环的实心点 —— 判为该背景下的渲染副产物，不是第二种画法。这是全库**唯一**
  一处几何不以浅色稿为准，已记进锁文件 `specChanges` 与 `pairs`。
- **图标着色取暗色稿的规则**：未选 `onSurfaceVariant`、选中 `onSurface`，浅暗同一条。浅色稿给三枚

  月亮由卡片页私有提升进公共 `StrokeIcons.kt`，因为它现在有两个消费者。
- **只有主题弹层是这种带说明的选项卡列表**。`PersonaSheet` / `ModelSelector` / `ProjectPickerSheet`
  仍是朴素 `ListItem` + 行尾对勾，它们没有稿。别拿这一张去推平其余选择弹层。
- **三处命名收敛**：卡片页原本说「随系统」、设置→外观说「跟随系统」，现在两处都走
  `ui/settings/ThemeOptions.kt` 的 `themeLabel()`。设置→外观的颜色模式也因此不再是三段胶囊 ——
  `SegmentedCapsule` 是 `maxLines = 1` 省略号，英文 `Obsidian dark` 在 `fontScale 1.3` 下必截断。

  单选点分离）/ `.en-fs13`（英文 + 大字号）；设置页侧 `settings.appearance.color-mode` / `-dark`。

### 5.2 会话列表（`SessionsScreen.kt`）
- 顶栏 `[头像32] 居中标题 [搜索][更多]`（决策 2026-09-09；尺寸 2026-09-12 照第六次拉取）：
  **内容行高 48dp**（`h-12`，覆盖 M3 的 64dp 默认值），头像 32dp，两个动作按钮的字形各 20dp，
  标题 16sp（`SessionsTopBarTitle`，专用样式，不是 `titleLarge` 的 20sp —— 稿子只为这一屏说话）。
  头像即卡片页入口；**搜索留在顶栏**，因为它是「想不起来在哪个会话」时的全局出口，收进菜单省不了
  任何空间、只多一次点击；「更多」里是项目与已归档（§5.16）。`CenterAlignedTopAppBar` 实测标题仍
  居中，由 `ScreenshotTest` 的 `chats-topbar-zh` / `chats-topbar-en-fs13` 两张钉死。

  **必须用 `expandedHeight` 而不是 `Modifier.height`**：栏把状态栏内边距画在自己容器里，约束整个
  可组合项会让大半高度花在 inset 上、内容行被压扁（HONOR CLK-AN00 上标题竖向裁切、贴着首个组头）。
  稿子也是这么分的 —— `h-12` 是内容行，`pt-safe` 另算。48dp 内容行正好容得下 48dp 触控区。

  **按钮不做成 32dp。** 稿子的 `w-8 h-8` 只在 `hover:bg-stone-200/50` 时才画底，静止态完全透明，
  那 32px 在 Android 上不可见，可见的只有 20px 字形；把按钮缩到 32dp 等于什么也没换来却丢掉触控区。
  `IconButton` 保持默认 48dp 触控。不记为偏离 —— 差的只是涟漪直径。
  （2026-09-11 曾按 `w-9` 把按钮做成 36dp 并记为「照稿的代价」，那条理解现已作废。）
- 分段**0 段或 2 段**（会话 / [机器人]，§5.16）：没配渠道时**整行不渲染**，会话页就是一条列表。
- **分段是下沉胶囊**（决策 2026-09-10，取代 M3 `SingleChoiceSegmentedButtonRow`）。
  **全 App 唯一形态，组件在 `ui/components/SegmentedCapsule.kt`**：改之前有六个屏各自复制了一份
  M3 分段（会话、用量、外观页两处、身份编辑、消息渠道），其中消息渠道的注释还写着"与会话页
  分段保持一致"—— 手抄的一致性正是它会漂的原因，会话页一改它就不一样了。现在是同一个组件，
  漂不了。**新增分段一律用它，禁止再写 `SingleChoiceSegmentedButtonRow`。**
  - **例外只有定时任务编辑页**：那里是 5 段（每小时/每天/每周/每月/高级），胶囊在 fontScale 1.3
    下装不下 5 格；M3 的描边行在格子变窄时降级得更好。**胶囊只适用于 2–3 段。**
  - **外观页的颜色模式已离开胶囊**（2026-09-11，§5.1a）：主题改名后 `黑曜石深色` /
    `Obsidian dark` 在 `maxLines = 1` 的格子里会被省略号截断，那一处换成了主题选项卡列表。
    外观页剩下的「工具调用显示」仍是 2 段胶囊。截图用例 `segments-3-zh-fs13` 因此变成**合成**
    用例 —— 它守的是组件的三段上限，不再对应任何一个屏。
  - **图标只有会话页有**：那是首页的主导航，图标是路标；其余几处都在设置类表单里，图标是装饰。
  形态细节：
  `surfaceContainer` 轨道 + 1dp `outlineVariant` 边 + 12dp 圆角 + 4dp 内边距；选中段是**浮起片**
  （8dp 圆角 + `tileShadow()`），未选段透明、文字降到 `onSurfaceVariant`。
  - 换掉 M3 的理由：它把选中段填满 `primary`，等于在首页顶部放一整块 40dp 高的品牌蓝，而
    同屏其他每一个强调色（未读点、琥珀立柱）都在报告运行状态。改成"浮起"后选中靠层次表达，
    不靠颜色，高度也从 48dp 收到 40dp。
  - **浮起片的颜色相对轨道取，不相对页面取**：浅色 `surfaceContainerLowest`、深色
    `surfaceContainerHighest`（对轨道 1.16:1 / 1.18:1）。**不要用 `tileColor()`** —— 它是相对
    `surface` 抬一档的淡卡填充，落在这条轨道上深色只有 1.01:1，选中段会消失。由
    `SegmentPillTest` 钉死。
  - **图标回归**（18dp `ChatBubbleStrokeIcon` / `BotStrokeIcon`，§4.2）。2026-09-01 禁图标的理由是
    四段时每格仅 91.5dp；两段每格约 183dp，该前提已不成立。**打勾仍然不要** —— 那条是因为
    打勾出现/消失会左右推移标签，与格宽无关。
  - 片高用 `heightIn(min = 32dp)` 而非固定值，fontScale 1.3 下标签才有地方长；内层 Row
    **禁止 `fillMaxSize()`**，否则高度会被父级可用空间撑满（截图测试里会拉满整屏）。
- 分组顺序：需要你处理 → 已置顶 → **今天 → 前 7 天 → 更早**。
  - 时间桶（`groupByRecency`，决策 2026-09-01）：滚动窗口，精确区间 —
    今天 = `[今日零点, now]`；前 7 天 = `[今日零点 − 7×24h, 今日零点)`；其余（含无
    时间戳）= 更早。本地时区；clock/zone 注入可测。选滚动而非自然周，避免周初
    "本周"组瞬间清空（ChatGPT 同款约定）。
  - **组头文字与立柱不同色，琥珀分两档**（决策 2026-09-11，取代 09-10 的"同色"）：
    需要你处理的**立柱与圆点**用亮琥珀 `warnGraphicColor()`（`#D97706` / `#F59E0B`），
    **标签与状态句**用深琥珀 `statusColor(WARN)`（`#B45309` / `#FBBF24`）。这是设计源自己的
    区分 —— 看的标记和读的词不是一回事。其余三个状态的标记与文字仍同色。
    已置顶与时间桶的**文字**用 `onSurfaceVariant`、**立柱**用 `outline`（已置顶）与
    `outlineVariant`（时间桶）。计数 chip 跟标签同源。
  - 立柱尺寸 **3dp × 12dp、全圆角**（决策 2026-09-11 照稿改；09-10 记的 3×14dp 与 2dp 圆角是
    把稿子的 `h-3 rounded-full` 读错了）。
  - **四个分组的立柱各有自己的颜色**（决策 2026-09-11，推翻同日早些时候「只有需要你处理带色」
    的复核结论 —— 产品负责人看过全灰的真机图后要求恢复彩色）。取值全部照稿，定义在 `Tiles.kt`：

    | 分组 | 立柱 | 浅色 | 深色 |
    |---|---|---|---|
    | 需要你处理 | `warnGraphicColor()` | `#D97706` | `#F59E0B` |
    | 已置顶 | `pillarPinnedColor()` | `#2563EB` | `#3B82F6` |
    | 今天 | `pillarTodayColor()` | `#059669` | `#34D399` |
    | 前 7 天 / 更早 | `pillarOlderColor()` | `#94A3B8` | `#64748B` |

    - **只有立柱上色。** 组头文字与计数 chip 除「需要你处理」外一律 `onSurfaceVariant` 中性 ——
      四个彩色标签会互相抢，而"这组要我动手"必须是屏幕上最响的一件事。
    - `SectionTone` 因此从三档拆成四档（`TIME` → `TODAY` / `OLDER`）：稿子给今天绿、给前 7 天
      石板灰，一个 TIME 档表达不了。
    - **已知且接受的撞色**：深色下今天的立柱 `#34D399` 与 `StatusTone.GOOD` 深色档完全同色，
      也就是和「已完成」的圆点同色。稿子自己就是这么画的；2026-09-11 恢复彩色时接受了这一点。
    - 亮琥珀 `#D97706` 在纸面上 3.02:1，压在旧的图形下限上 —— 该下限已于 2026-09-11 废除（§7 第 8 条）。
    - 四档并排的样子由 `ScreenshotTest` 的 `section-header-tones` / `-dark` 两张钉死。
  - **计数是 chip 不是裸数字**（圆角 6dp、内边距 8·2dp、10.5sp 等宽）：需要你处理用
    `statusColor(WARN)` 12% 底 + 同色字 + 600 字重，其余用 `surfaceContainerHigh` 底 +
    `onSurfaceVariant` 字 + 500。裸数字让四组同权重。
  - 组头可折叠（`SectionHeader`：`SessionGroupHeader` 11sp 等宽大写 + 计数常显 + 17dp 箭头），
    行内边距 16·2dp（稿子的 `px-4 py-0.5`；第六次拉取前竖向是 8dp），折叠态 `rememberSaveable`，
    **不跨启动持久化**；空组不渲染；组内新→旧。组头因此只有约 22dp 高，纵向是个薄点击区 ——
    它整行宽，横向很好点，照稿保留。
- 行 = **自绘 `Row`**（坐在 surface 暖纸上，§2.1），**无行间分隔线**（搜索结果页除外）。为什么不再是 `ListItem`，见下面那条。
- **列表底部不留 FAB 空位**（产品裁决 2026-09-12）。稿子的 `<main>` 有 `pb-20`（80dp），本仓的 `LazyColumn` 一直没有 `contentPadding`，这次确认为规范。**代价写明：滚到底时 FAB 会盖住最后一条会话。**有意偏离，记在 `stitch.lock.json`。
- **行内三档字号是专用样式，不走 M3 槽位**（决策 2026-09-10，2026-09-11 补齐行高与状态行；
  `Type.kt` 的 `SessionRowTitle` / `SessionRowSubline` / `SessionRowStatus`）：

  | 档 | 字号 | 字重 | 行高 | 字距 | 字族 |
  |---|---|---|---|---|---|
  | 标题（未读）`SessionRowTitle` | 14.5sp | 600 | 19.575sp | −0.145sp | 系统 |
  | 标题（已读）`SessionRowTitleRead` | 14.5sp | 500 | 19.575sp | −0.145sp | 系统 |
  | 副行 `SessionRowSubline` | 11.5sp | 400 | 15.525sp | 0 | **JetBrains Mono** |
  | 状态行 `SessionRowStatus` | 11.5sp | 500 | 15.525sp | −0.2875sp | 系统 |
  | 运行中状态行 `SessionRowStatusRunning` | 同上 | 同上 | 同上 | 同上 | **JetBrains Mono** |

  **字重按未读态区分**（决策 2026-09-11，已落地）：稿子里 600 的两行恰好都在「需要你处理」组，
  但设计师最新的设计系统把两档命名为 `session-title-unread` / `session-title-normal`，产品负责人
  裁定按未读态 —— 与聊天类 app 惯例一致；未读圆点继续保留，字重是第二重信号。

  **只有「正在使用 X 工具」那一条状态行是等宽**，其余状态句（已完成 / 运行失败 / 已中断）是散文 ——
  稿子就是这么分的。副行整体等宽，而它的内容是仓库名与模型名，所以等宽在那里是真的看得见的。

  副行距标题 2dp、状态行距副行 2dp（稿子的 `mt-0.5` / `mt-0.5`；第六次拉取前后者是 `mt-1`=4dp）。

  **行高来自稿子行容器的 `leading-[1.35]`**（第六次拉取前是 1.45）：稿里这几档都不自带 `leading`，
  全部继承它，14.5×1.35=19.575、11.5×1.35=15.525。按精确值写，不取整到整数 sp —— 取整就得在一致性
  fixture 里写一条「我们四舍五入了」的免责说明，而这类说明正是当初让偏差混过去的东西。倍数在
  `Type.kt` 里是一个具名常量 `SessionRowLeading`，三档由它推导：稿子把它当一根杠杆调（1.45→1.35），
  写成三个字面量迟早会只改其中两个。

  **`lineHeight` 在 Compose 里默认不等于行框高度。** 默认的 `LineHeightStyle` 会把首行上方与末行
  下方的行距裁掉，而行内这三档全是单行文本，于是行框退化成字体自身的 ascent+descent，`lineHeight`
  形同虚设 —— 实测行高 43.05dp 而不是算出来的 49.1。`Type.kt` 的 `ExactLineBox`
  （`Trim.None` + `Alignment.Center` + `includeFontPadding=false`）把行框恢复成 CSS `line-height`
  的语义。这两项曾在查 A-05 时试过并被记为「无效」，那时确实无效：行高被 `ListItem` 的下限接管，
  文字怎么量都撑不动它。行自绘之后它们是承重的。

  **稿与设计系统矛盾时以稿为准**（决策 2026-09-11）：设计系统的 `title-md` token 写的是
  15px/500/20px/**0em**，稿子的 `<h2>` 是 15.5px/600/−0.01em。这条矛盾记在
  `design-conformance.json` 的 `note` 字段里，不参与断言，但保证下一个读它的人知道这是选过的。

  **状态行以前借 `labelMedium`**（12sp/600/+0.48sp）—— 字重与字距方向都跟稿相反。分组头也不再
  借它，而是有了自己的 `SessionGroupHeader`（11sp 等宽大写）—— 一个 token 服务不了两个方向。

  Material 的 `ListItem` 默认给
  它们 `bodyLarge`(16sp) 与 `bodyMedium`(14sp) —— 副行只比标题小 1sp，次要信息与主要信息抢
  注意力。这条改动买到的是**主次层级**（副行从只比标题小 1sp 变成小 3sp）。

- **会话行不再用 `ListItem`，改为自绘**（决策 2026-09-12，第六次拉取）。

  2026-09-11 这里写过「设计源的 ≈65px 用 `ListItem` 达不到……未做，也不建议为 7dp 去做」。
  第六次拉取把差距从 7dp 变成 **23dp**：稿子的两行行是 **49.1dp**，而 `ListItem` 的下限是
  一行 56 / 两行 72 / 三行 88 —— 新目标比**一行**的下限还低。外层强设高度能越过下限（真机验过
  58dp 生效），但 `ListItem` 内部固定 8+8 内边距，49dp 只剩 33dp 装 37.1dp 的内容，会裁字。
  所以这条路是封死的，不是不划算。

  自绘之后行的结构就是稿子本身：`Row(px 16, py 6, gap 12) { Column(weight 1f){标题;2dp;副行;2dp;状态行}; Box(28dp){尾部} }`，
  `verticalAlignment = CenterVertically`。**行高不写死**，是内边距加内容算出来的 —— 稿子就是这个
  模型，字体缩放与中文换行才不会裁字。尾部那个 28dp 空列即使没有指示器也保留（稿子的
  `<div class="w-7 shrink-0">`），这样每一行的标题都在同一个 x 截断。

  **同一条下限造成的三个症状一起消失**：① A-05 —— 中文项目名让副行换行、把行顶进三行档，
  行高从 72 跳到 88dp；② 三行项是顶对齐，于是副行下方空出一块；③ 运行中的转圈跟着顶对齐，
  不在行的竖直中心（产品负责人 2026-09-12 真机发现）。

  容器色不需要补：`ListItem` 默认用 `surface`，而本主题浅暗两套的 `background` 与 `surface`
  是同一个值，行本来就和页面同一张纸。

  **中文行有 1.5dp 的残差，这是有意偏离。** 实测 411dp/420dpi：纯拉丁行 49.52dp，命中稿子；
  每有一行中文 +1.52dp（中文标题 51.05、中文标题加中文项目名 52.57）。1.35 是按拉丁字形推的，
  中文回退字体需要的 ascent+descent 超过 `字号×1.35`，行框只能长到字体要求的高度。对照落地前
  A-05 的 16dp，这是一个数量级的改善。`SessionRowTuningTest` 在 `@GraphicsMode(NATIVE)` 下钉住
  这些数 —— **Robolectric 默认的桩字体会让中英文测出一样高**，那个数是假的。

  **标题单行截断**（稿子的 `truncate`）。此前没有 `maxLines`，长标题折两行，行高随标题长度变化；
  截断之后两行行恒定。
  之所以不改全局 token：`bodyLarge` 是聊天阅读档，`bodyMedium` 有 78 处在用。
  **副行的 12sp 由 `SessionSubline` 组件自己持有**，不在各 `ListItem` 上分别设 —— 共有四个
  消费者（会话列表、搜索结果、项目钻入、已归档），副行在一个列表里 12sp、另一个里 14sp
  比统一用哪个都糟。
- **副行统一组件** `SessionSubline`（决策 2026-09-02，方案 A「副行前缀」）：
  `[14dp 文件夹] 项目名 · 模型名`。项目名 = git 仓库根的 basename，缺失退到 cwd 的 basename；
  项目段最多占副行 60% 后省略号，模型名保持可见。**默认项目不显示项目段**（缺省即默认，
  不写「无项目」占位）。图标用 onSurfaceVariant 中性色，不用品牌蓝。会话列表、已归档、搜索
  标题匹配三处共用；项目内钻入行改为 `[分支图标] 分支 · 模型`（项目名由页头承担）。
  搜索的消息匹配行不显示模型（见下「搜索页」）。
- **置顶标记在副行**（决策 2026-09-02；图钉形态 2026-09-12 改版）：
  `[13dp 双色实心图钉] [文件夹] 项目 · 模型`，图钉是副行第一个前缀。

  图钉从单色描边（`PinStrokeIcon` + `colorScheme.primary`）换成自绘双色实心
  （`ui/components/PinIcon.kt`）。Stitch 稿画的是 **emoji 📌**，产品负责人 2026-09-12 裁定不照搬：
  emoji 字形由系统字体决定，各家 ROM 不同；无法着色、无法随暗色模式调整；TalkBack 会读 emoji
  自己的名字。稿子的意图是「一个彩色小物件而不是一根线」，这一点照做，形由我们控制。头部**不取
  emoji 的红** —— 红在 §2.1 已经是「运行失败」，同一行右侧就可能有红点；改用已置顶分组立柱那个蓝，
  针尖取中性色。这是 §4 描边体系的**唯一填充彩色例外**，因为彩色图标不能走 `Icon(tint=)`，
  它用 `Image` 画，无障碍描述由 `semantics` 显式给。**不再用 ListItem 的
  leading 槽**：旧版 Material 实心图钉在三行项里顶对齐、两行项里居中，且把标题推到 52dp，
  与其他行不在一条竖线上。分组头「已置顶 · 仅此设备」仍是主要表达，副行图钉负责折叠 / 搜索等
  看不到分组头的场景。TalkBack 由图钉的「已置顶」描述承担。
- **置顶分区的插入不得把内容推出视口**（决策 2026-09-06，HG-11）：pin 存在设备本地，读盘晚于
  首帧就会让「已置顶」段在列表渲染之后才被插到最前面；LazyColumn 锚定原先的首个可见项，于是
  整段新内容落到视口上方，用户以为置顶没生效（实际要自己往回拉才看得到）。两条硬规则：
  ① **pin 未加载完不得渲染出「没有置顶」的形态**——首帧前先拿到 pin 集合（本地读盘，列表本来
  就要等一次网络往返，不增加等待）；② 用户手动置顶 / 取消置顶后，列表要主动把该会话的新位置
  带进视口，让用户看见它去了哪里，而不是从当前位置消失。
- **列表行不出现身份文字**（原则 3 的落地）：多身份时旧版曾在副行拼「身份：xxx」，
  2026-09-02 随副行组件一并删除。

- **状态行的开关看文字，不看 phase**（决策 2026-09-10，`sessionStatusLine`）。
  `Text("")` **照样占满一个行框**：一个空标签会把行从两行高度（72dp）推到三行高度（88dp），
  而三行项是**顶对齐**、两行项是**居中**，于是副行下方凭空空出 40dp。真机上表现为"每隔几行就
  多一块没有内容的空白"，而那几行恰恰是**看不到任何状态文字**的行 —— 这正是它难查的原因。
  旧写法问 phase「要不要画」，现在问最终字符串「有没有东西可画」，空白一律不渲染。
  由 `SessionStatusLineTest` 钉死（遍历全部 phase × 双语，断言只会返回 null 或非空白），
  并由截图 `row-height-probe` 把四种内容形态的实际行高一并钉住。

- **终态显示与清除**（决策 2026-09-02，`SessionRuntimeStore.isTerminalVerdict`）：
  - 「已完成 / 已中断 / 运行失败」是**待查看的结论**：会话不在眼前时保留在行内，**打开会话即清除**
    （三者走同一条 `markRead` 路径；回到前台时对正打开的会话同样清除）。
  - **本机按停止键的中断不显示任何状态**：用户自己做的事不需要提醒，运行时直接回空闲，
    只有聊天页时间线留「已中断」注记。远端 / 未知原因的中断才显示「已中断」。
  - 会话正被查看（前台 + 可见）时发生的中断或失败也不留结论，与「已完成」规则一致。
  - 行尾圆点只给「已完成」（绿）与未读；「已中断」「运行失败」**只留文字不留圆点**——
    终态灰点与未读圆点只差 1dp，曾被误读为未读。
- **运行状态跨进程存活**（决策 2026-09-12，HG-31，`SessionPhaseStore`）：杀掉 App 冷启动后，
  行内第三行与「需要你处理」分组必须还在。此前它们随进程消失，而**同一行的未读圆点却活着**
  （`SessionReadStore` 一直是持久的）——一个字段活着、解释它的那个字段死了，就是这条 bug。
  清除终态的 `markRead` 本身就是持久的，所以**终态结论不设过期**：让文字过期而圆点不过期只会
  把同一个不一致换个方向再犯一次。
  - **运行中的相位恢复成「正在恢复连接…」，不原样恢复**：没有 socket、没有句柄、没有任何东西
    正在到达，此时说「思考中」与 HG-6/7 立起 `normalized()` 时反对的是同一类谎言。「正在输出…」
    尤其站不住——消息故意不落盘，原样恢复会配上一个永远不增长的空气泡。RECONNECTING 是字面属实
    且自愈的：首次连上就走 `resumeRunningSessions()`，`restoredPhaseAfterReconnect()` 回落到存下的相位。
  - **等待态 30 分钟未更新即丢弃，而不是标「已中断」**：`markUnconfirmed` 敢写结论是因为它握着
    证据（静默超上限**且**连续两次探测失败）；冷启动一份证据都没有，凭时间戳判中断是发明结论。
  - **审批卡不从磁盘复活**：`approval.respond` 只按 session 寻址、不带请求 id、无返回值，恢复出的
    卡会指向 Hermes 此刻在等的**任意**一条审批——可能是用户从未见过的命令，而「本次会话允许」
    还会把这次误授权固化进 pattern 白名单，且没有任何一层能发现。提问卡（clarify）带 `request_id`、
    服务端会回 `expired`，因此可以恢复。差别写死在 `SessionPhaseStore` 的 KDoc 与
    `ColdStartPhaseRestoreTest` 里。进会话时若在等审批却无卡，给 `HR-APPROVAL-002` 的说明。
  - **恢复出的相位在被实时证据确认前不贴通知**（`SessionRuntimeStore.restoredKeys`）：行内展示是
    诚实的，而高优先级通知宣称的紧急程度是本进程尚未验证的。与此配套，冷启动的
    `cancelSessionCards()` 只清 ongoing 卡，**保留「需要你处理」卡**——它不需要被更新，只需要能被点，
    而通知栏是审批唯一能熬过划掉 App 的地方。
- **Stitch 不覆盖清单**（决策 2026-09-11）：下列行为代码里有、Stitch 稿（`docs/design/stitch/sessions.*`）
  里没画。它们是**保留项** —— 对稿实现时不得为了「和稿一样」把它们删掉；稿子若要改它们，先在 Stitch
  里画出来、进基线，再动代码。清单：「需要你处理」跳转药丸（`NeedsYouReveal.kt`）；长按菜单与
  「移动到项目…」；归档二次确认；刷新中的顶部进度线；置顶分区的视口规则；终态清除规则；
  空态 / 加载 / 错误三态；英文文案；fontScale 1.3 与 360dp 窄屏下的截断。稿里画了而本仓已实现的
  「机器人」段与「更多」菜单见 §5.16。

### 5.3 项目 / 已归档

**都是全屏页**（决策 2026-09-09）：从会话页右上角「更多」进入，`projects` / `archived` 两个路由。
它们是**管理**动作而不是浏览动作，低频，且新建/更名/删除需要菜单与对话框——分段里放不下。

- **项目页只有一个路由**：钻入用页内状态，返回先退到总览、再退才离开页面。项目 id 在派生模型
  里就是文件系统路径，塞进路由要编码，还要处理「进程重建恢复到一个树尚未加载的项目」。
- **钻入状态不跨启动持久化**：冷启动后首次进「项目」看总览。本次运行内仍然记住（VM 挂在存活的
  会话页 entry 上），所以离开再回来还在那个项目里。
- **从项目页/归档页打开的会话，返回回到那一页**：会话页是「打开它的那个枢纽页」的叶子，而不是
  只认会话首页。在一个项目里连着看几个会话时不会每次被弹回首页。

#### 项目管理（决策 2026-09-09）

**两个数据源，由身份决定。** 上游的 `projects.*` 全都不接受 `profile` 参数，永远解析网关进程
自己 HERMES_HOME 下的 `projects.db`，也就是 `/api/profiles` 标了 `is_default` 的那个身份。
所以：**只有默认身份读服务端项目树并可管理**；其余身份继续用客户端按 `gitRepoRoot ?: cwd` 现推的
派生列表，**只读**。判据写在 `ProjectsUiState.managed`，UI 的所有管理入口都挂在它上面。
在非默认身份下读服务端树会出现「一个身份的文件夹套着另一个身份的会话」，所以这不是保守，是必须。

- **上游的 `__no_project__` 进来时改名成本 App 的「默认项目」**：同一个概念两个名字没有意义，
  而且改名后既有的全部约定（永远排第一、房子图标、FAB 无 cwd 新建、选项目单标「当前」）原样生效。
- **能改的只有六样**：名称、图标、颜色、文件夹集合（增/删/设主）。`slug` 上游创建后不可改，
  `primary_path` 只能通过「设为主」间接换。**项目级配置（模型/权限/MCP/记忆）在上游根本不存在**，
  所以项目设置页里不要放这些。
- **叫「移除分组」，不叫「删除」**：上游 `projects.delete` 只删 projects 表那一行和它的文件夹行，
  **会话不动、磁盘不动**，那个 git 根下一秒就作为自动项目回到列表。写「删除」是撒谎。确认框必须
  把这件事说明白。破坏性红色仍然用（§5.5），因为分组本身确实没了。
- **项目级归档不做**：上游只是把它从树里摘掉，会话照样以自动项目冒出来，用户看不出区别。
- **只有服务端项目行能长按**：派生项目和默认项目桶没有可编辑的行，长按不出菜单
  （`ProjectOverview.onManageProject` 对 `isAuto` / 默认项目返回 null）。

#### 一份项目列表，四个界面共用（决策 2026-09-09）

**项目名和「可移入的项目」只有一个来源**：`ProjectCatalog`（单例，带缓存）。会话列表行、归档页、
搜索结果、聊天页顶栏副标题、以及两处「移动到项目」选项单，全部读它。

由来：0.1.112 发出去之后立刻暴露的问题——项目页已经读服务端了，显示真实项目名和图标颜色，
而两处选项单和所有会话行还在各自用 `deriveProjectsFromSessions` 现推，于是同一个项目在项目页
叫「赫尔墨斯远程」、在会话行叫 `hermes-remote`，选项单里还混进了 `/Users` 这种网关会过滤、
派生不会过滤的垃圾根目录。**各自推导就是它们必然分叉的原因**，所以改成一份。

- **会话归属按最长前缀匹配**（`ProjectCatalog.nameFor`）：先看 git 根、再看 cwd，对每个项目的
  **全部文件夹**（上游项目可以跨多个文件夹，只看 `path` 会漏）。这和网关的分组规则一致，
  所以一行的项目名和它在项目页里被列在哪一组，永远说的是同一件事。
- **必须是路径边界**：`/a/hermes-remote` 不属于项目 `/a/hermes`，只是名字前缀像。
- **缓存冷/没有项目认领时回退到文件夹名**，也就是这套机制上线前的行为——一行不会因为在等请求
  就丢掉副标题。
- 副行的名字经 `LocalProjectNames` 这个 CompositionLocal 下发，而不是逐层传参：否则四个屏的
  ViewModel 每个都得持有一份项目列表，那正是它们当初分叉的方式。

#### 项目图标与颜色

- **图标名用上游的 codicon 名**（`folder-library` / `repo` / `rocket` / `beaker` / `star-full` /
  `terminal` / `globe` / `package`），不是我们自己的命名。Hermes 原样存这个字符串、桌面端按
  codicon 渲染，所以手机上设的图标必须能在桌面正确显示。上游有 28 个，本 App 画了在 24dp 下仍
  清晰的 8 个；**桌面设了本子集之外的名字时回退到文件夹字形**，不能什么都不画。
- **图标必须是 §4 的 1.7dp 描边手绘 ImageVector**（`ProjectIcons.kt`）。填充版 Material 图标在
  项目行的 leading 槽里会读成实心色块，和旁边的描边文件夹不是一套。
- **颜色 12 档，写成桌面端的 `hsl(H 68% 58%)` 记法**（H 每 30° 一档），存进上游 `color` 列。
  解析同时接受 `hsl()` 和 `#RRGGBB`——早期/手工设的行是十六进制。解析不出来就回退品牌色，不报错。

#### 选择文件夹

手机没有自己的文件系统可浏览，**新建项目和添加文件夹都走 `GET /api/fs/list` 逐层浏览 Mac**
（桌面端的远程选择器用的是同一个接口）。页内状态，不是路由：返回键先收起选择器、再退钻入、
最后才离开项目页。

- **只列目录、只有一个动作**：「选择此文件夹」。上游那个接口**没有目录囚笼**，所以这一页刻意不做
  成通用文件浏览器——不打开、不读取、不下载、不删除任何东西。
- 起点是 `GET /api/fs/default-cwd`（网关自己的工作目录）；进入某个目录时用
  `GET /api/fs/git-root` 提示「这是一个 Git 仓库」。
- 目录读不出来时上游不抛错、而是在响应体里给 `error`，客户端映射成 `HR-SESS-012`。
- **零文件夹的项目不允许建**：上游允许，但那样的项目永远 `sessionCount=0` 且没法用
  `session.workspace.move` 移会话进去，是个死行。所以「保存」在没选文件夹时禁用。
- **默认项目**（决策 2026-09-02）：网关启动目录是一个真实项目，名为「默认项目」，永远排在
  项目页第一位（即使 0 个会话），leading 用 HomeFolderStrokeIcon + onSurfaceVariant；
  副行「网关启动目录 · N 个会话 · 最近活跃」。术语只用「默认项目」，不再出现「无项目」
  「未关联」「无工作区」。
- **新建规则一句话**：会话页（及项目总览、默认项目内）新建 = 默认项目；钻入某个项目后
  新建 = 该项目（`session.create` 带该项目 path 作为 cwd）。不推断、不记忆、不弹单。
  首次进入某个项目时出一次性 snackbar「在这里新建的会话会归入 <项目>」（设备本地记录，
  每项目一次）。请求的文件夹在 Mac 上已不存在时网关静默退回默认目录，客户端比对返回的
  `info.cwd` 并以 `HR-SESS-006` 提示。
- 默认项目的路径由一次顶层 `session.create` 的 `info.cwd` 学到并本地保存；派生时把落在
  该目录的会话并入默认项目，选项目单也因此能把会话移回默认项目（路径未知时默认项目只在
  「当前」时出现）。
- 项目行：leading 描边文件夹 24dp，项目色着**线条**；副行「N 个会话 · 最近活跃」；行尾
  ThinChevronIcon 20dp（入口行范式）；随当前身份过滤，无身份标。项目按最近活跃排序。
- 钻入页：页面标题即项目名，返回由顶栏承担（**列表里不再有返回行**——一页一个返回入口）；
  首行是路径行（labelMedium，默认项目写「网关启动目录 · 会话页新建的会话都在这里」），
  行副行「分支 · 模型」。路径行不做成顶栏副标题：那个 Text 没有 `maxLines`，长路径会撑高顶栏。
- **选项目底部单** `ProjectPickerSheet` 只有一张，标题「移动到项目」左对齐；默认项目固定
  第一项并标「当前」勾选；其余按最近活跃排序，副行是路径。长按菜单与聊天页副标题共用，
  调用 `session.workspace.move`。
- 归档行：leading 描边归档盒 24dp（`onSurfaceVariant`）+ 标题/模型副行；无分隔线、无
  trailing 按钮；点击打开，**长按**出菜单（取消归档 / 删除+确认）。

### 5.4 聊天页（`ChatScreen.kt` / `ChatComponents.kt`，本轮确认值）
- 顶栏与正文同底（`background` 色）、裸图标：返回 / 标题块 / 搜索 / 更多。**顶栏不再有
  身份头像**（早前已从代码移除，本文 2026-09-02 修正）；身份只在列表页头像上承载。
- **工作区副标题**（决策 2026-09-02，`WorkspaceSubtitle`）：标题下一行 labelMedium
  onSurfaceVariant：`[文件夹 12dp] 项目 · [分支图标 12dp] 分支 ▾`，默认项目写「默认项目」+
  房子文件夹。整行可点，打开选项目单；末尾 12dp 向下小箭头表示可点，会话运行中隐藏箭头并
  置灰 60%。数据来自打开时的会话元数据与网关 `session.info` 事件（cwd/branch）。**当前身份
  一个派生项目都没有时整行不渲染**，标题回到单行。
- 用户气泡：`surfaceVariant @78%`、圆角 22/22/**7**/22（右下小尾角）、内边距 16×11、
  正文 17sp/25；宽度上限 ≈ 屏宽 82%。助手回复**无气泡**纯排版。
- **消息内渲染顺序**（决策 2026-09-05）：助手消息为 **图片 → 正文 → 文件附件 → 操作行**；
  用户气泡保持 **图片 → 文件附件 → 正文**（与用户组织消息的顺序一致，且用户消息短）。
  理由：助手的文件是正文交付的产物，而经营报告类正文常达上千字，附件放顶部会随正文滚出
  视野——实测中用户因此判定「没收到文件」并向助手追责。图片不下移：助手生成的图片本身
  就是内容，不是正文的附产物。
- **文件附件卡整卡可点 = 打开**（决策 2026-09-06，HG-12）：卡片原先只有右侧「打开」「分享」
  两枚图标按钮可点，卡片主体点了没有任何反应。改为**整卡可点执行打开**（涟漪覆盖整卡），右侧
  **只保留「分享」**——同一个动作不给两个入口。仅 `READY` 且有 `remotePath` 或 `localPath` 时
  可点；上传中 / 失败态不可点（宁可没有涟漪，也不要点了没反应）。这是入口行「可点必有箭头」
  范式的一处显式例外：文件名 + 类型/大小本身就表达了「这是一个可打开的东西」，卡片不再加箭头。
- **用户气泡投递三态**（决策 2026-09-02，设计稿
  <https://claude.ai/code/artifact/045c178d-b682-4346-92bf-19c257d00da8>）：
  - 已发送 = 现状样式。信号是 `prompt.submit` 的 RPC 应答（Mac 端 Hermes 已收到），不是
    `message.start`；历史重排后的消息天然已发送。
  - 发送中：填充 `surfaceVariant` 从 @78% 降到 @50%，正文 70% 不透明度；尾角处 18dp 背景色
    底盘 + 12dp 描边圆环，透明度 0.35↔1 呼吸，周期 1200ms，正文不动。**延迟 250ms 才淡入**
    （200ms），快的发送看不到变化；成功后 190ms 颜色动画回到实心。不做扫光。
  - 未发送：保持降暗，尾角换成 error 色感叹圆，气泡下 labelMedium「未发送 · 点按重试」
    （error 色）+ 紧凑错误码「SESS-007」（onSurfaceVariant，即去掉 `HR-` 前缀的
    `AppErrorCode.compact`，决策 2026-09-02）；点按气泡或该行 = 原消息（含附件）重发；
    长按菜单多一项「复制诊断信息」（诊断里仍是全码）。
    替代旧的单独红色「消息发送失败」错误行。TalkBack 只播报未发送，不播报发送中。
  - 无法送达（决策 2026-09-11，HG-29）：上游已经把这个会话回收掉、且它带着历史无法静默重建时，
    气泡看起来和未发送一样（降暗 + error 感叹圆），但文案换成「会话不存在或已被删除」+ 紧凑码
    「SESS-001」，**且不提供点按重试**：气泡不吃点击，那一行也不吃点击。可重试与不可重试必须
    长得不一样 —— 给一个永远不会成功的重试按钮，比不给更糟，用户会一直点下去。
    空会话（新建且没有任何已落库轮次）不会走到这里：它被静默换成一个新会话，消息照常送达，
    用户无感。
  - 发送失败时会话回到 IDLE（不是运行失败），列表页不标"运行失败"，失败只由气泡承载。
- **助手正文排版**（决策 2026-09-04，设计稿 `docs/design/chat-markdown-typography.html`，
  `AssistantMarkdownBlock`）：助手回复是纯 Markdown 排版，没有气泡，所以**间距就是全部的结构**。
  取值集中在 `ChatComponents.kt` 顶部的 `MD_*` 常量，改版先改常量、再录 golden。
  - **为什么必须显式给间距**：Compose 会裁掉每个 `Text` 首行上方、末行下方的半行距。正文
    `lineHeight = 29sp` 只在**一个段落/列表项内部**买到空气，**两项之间一点都没有**。本次改动之前
    列表项间距 = `listItemTop 2` + `listItemBottom 2` + 字体升降部 ≈ 11dp，而同一项折行是 12.6dp
    —— **项边界比行边界还弱**，「1、2、3 点」因此塌成一堵信息墙。靠调行高解决不了这个问题。
  - **正文** bodyLarge 17sp/29，`letterSpacing = 0`（跟随系统字体缩放，§3.1）。
  - **间距**（实测纯空白）：段内换行 12.6dp 是基准线，任何**块之间**的间距都必须明显大于它。
    `block` 5dp（段↔段 ≈17.6dp）；`listItemTop/Bottom` 各 5dp（**项间 ≈17dp**）；`list` 4dp
    （列表整体上下，再大会在列表和邻居之间打洞）；`listIndent` 20dp/层；引用块上下 8dp；
    分隔线上下 16dp；代码块与表格卡外边距各 8dp。
  - **标题**：上方留白开章、下方留白断句，**两侧都要给**。旧值 h2 上 6dp、下 0，标题读起来像
    段落的第一行。现为 h1 22/8、h2 20/8、h3 16/6、h4 14/6（上/下）。字号 h1 24、h2 22、
    h3 18.5、**h4 17 Bold、h5/h6 15.5 Bold**。**标题字号一律不小于正文**：旧的 h5 = 13sp 比
    17sp 正文还小一大截，层级是倒挂的；h4 以下靠**字重**承担层级，不靠缩小。
  - **列表标记**：有序与无序共用 **28dp 定宽标记列**，两种列表的文字左缘对齐。28dp 是按
    17sp 下两位数 `10.` 的宽度定的 —— 标记列自适应时，列表跑到第 10 条文字左缘会整体右移。
    项目符号**画出来而不是排字**（`MarkdownBullet`）：`•` 字形位于拉丁 x-height，在 CJK 行里
    看着浮在上面，且库还给标记挂了 `listItemBottom` 内边距。改为在「恰好一行高」的盒子里居中
    绘制，任何字体缩放下都落在首行光学中心；三层依次为 5dp 实心圆 / 5.5dp 空心环 / 4.5dp 方块。
  - **链接**：`primary` 色 + 细下划线 + **前置 13dp 外链图标**（`ExternalLinkIcon`，§4 描边体系，
    小尺寸补偿 2.4 描边）。三重编码是刻意的：中文正文里「加粗 + 下划线」和 `**加粗**` 几乎分不出来，
    而只靠颜色区分不满足无障碍。图标经 `MarkdownAnnotator` + `InlineTextContent` 插入，后面必须跟
    一个 `U+2060 WORD JOINER` —— 否则断行器把图标当独立单词，会把它留在上一行行尾、和链接分家。
  - **任务清单**用 M3 复选框。给 `Markdown()` 传自定义 `components` 会覆盖掉 m3 默认注入的
    `checkbox`，漏传时 `- [ ]` 会渲染成字面文本 `[ ]`，必须显式带上。
  - **表格**正文 15sp/23。
  - **链接点击**（`ui/components/AppLinks.kt`，全 app 共用）：正文里的地址是模型输出，不可信。渲染器在构建链接注解时就
    捕获 `LocalUriHandler`，所以受控 handler 必须包在 `Markdown()` 外层，而不是点击处。
    只放行 `http/https/mailto/tel`（`intent:` 能指定任意组件、`file:` 能指向本地存储），
    无 scheme 的 `www.` 自动链接补 `https://`，其余拒绝 → `HR-LINK-002`。系统无法打开时
    （设备没有浏览器，Compose 默认 handler 会把 `ActivityNotFoundException` 重抛成
    `IllegalArgumentException` 直接崩）→ 复制链接到剪贴板 + `HR-LINK-001`。
  - **待办**（未立项）：超长无空格 URL 不做中间断行。
  - **验证**：`MarkdownTypographyScreenshotTest` 三张 golden（浅色 / 深色 / 边界情况）覆盖上述
    全部取值，改动后用 `-Proborazzi.test.record=true` 重录并肉眼比对。
- 输入区：浮动 `Surface`，圆角 30（聚焦 28）、tonal 1dp + shadow 7dp、最小高 60dp；
  内含麦克风、无边框输入框、48dp 圆形发送键 —— 发送键用 **theme primary**（明确决策：
  核心全局控件不随身份变色）。
- 新建会话入口：列表页 FAB，**外加聊天页顶栏的 `＋`**（决策 2026-09-06，HG-5，覆盖原「入口唯一」
  规则）。原规则是为了删掉顶栏那个**语音**建会话入口——它和输入区的语音重复且语义不清；那条理由
  不适用于一个普通的「新建对话」按钮。真实用法是：答案看完就想接着开下一个，此时人在聊天页，

  那一个动作，聊天内搜索**移入「更多」菜单**并置于首项。菜单顺序：搜索对话 → 我的提问 → 刷新对话
  → 复制对话 → 分享对话 → 归档对话 → 切换人格（导航在前、动作在后，离场动作垫底）。

  没有项目作用域可言）。创建中按钮转  并禁用，避免连点建出两个会话。
- **上一组对话胶囊**（决策 2026-09-02，设计稿
  <https://claude.ai/code/artifact/557258a0-61bf-4e27-b7f9-65b680cc9933>，`TurnJump.kt`）：
  - **上下文压缩脚手架不是用户说的话**（决策 2026-09-06，HG-16）：Hermes 压缩上下文时会注入
    `[Your active task list was preserved across context compression]` 与随后的
    `[Skills pruned during compression — …]`，两者都以 `role=user` 上线，此前被原样画成用户气泡。
    **注意它不总是独占一条消息**——上游把快照 append 到末尾那条 user turn 上（见
    `docs/HERMES_CONTRACT.md`），所以处理方式是**从标记处截断**该消息、保住用户真正说的话；截完
    为空才整条降级为一行安静的「上下文已压缩」备注（可展开看原文）。只按前缀匹配整条隐藏是错的：
    那会让「用户的话 + 脚手架」整条消失，比不处理更糟。
  - 分组规则只有一条：每条**真实用户消息**开一组（注入的时间线注记如模型切换、委派汇总不算），
    直到下一条用户消息；首条用户消息之前的内容算「会话开始」组，锚点是会话顶部。
  - **内容**按状态判断、不看滑动方向：视口顶部所在组的锚点（用户气泡）不在屏内 → 有内容；
    气泡进入屏幕 → 无；列表贴底跟随流式输出（index 0 / offset 0）→ 无。
  - **显隐**加一条计时规则（决策 2026-09-02，覆盖 2026-09-02 早先「有内容即常驻」的决定）：
    胶囊是滚动指示器，不是常驻控件。列表在动 → 显示；手停、列表静止 **1.5 秒**
    （`TURN_PILL_IDLE_HIDE_MS`）→ 淡出；再滑动**立即**重新出现；淡出前可点，点按照旧跳回提问。
    分段胶囊的列表段与胶囊同进同出。理由：常驻的胶囊被当成必须处理的控件，旧规则要滑到底才能
    摆脱它。150ms 淡入淡出，悬浮在消息列表容器顶部居中、距顶 10dp，**不占布局**；搜索打开时
    随列表下移，不做避让。
  - 样式复用 §5.2 的「需要你处理」pill：primaryContainer / onPrimaryContainer、圆角 18、阴影 4dp、
    labelLarge 单行省略、宽度上限列表宽 70%。图标**前置**、「箭头抵线」（`ArrowToTopIcon`）
    18dp，不带时间。摘要 = 用户消息首个非空行；纯附件消息显示「文件：名」/「图片 ×N」。
  - 点按：把该组用户气泡顶边对齐到列表顶部（倒序列表需用 item 高度换算偏移；可见时动画，
    不可见时直接定位），不是搜索高亮那种对齐底部。TalkBack 播报「回到这条提问：…」。
    **对齐循环三条规则**（决策 2026-09-03，两次真机复现后定稿）：① 逐帧修正一律用绝对定位
    `scrollToItem(index, offset)`，禁止相对 `scrollBy`；目标被下方内容顶出屏幕时，用它上次的尺寸
    重新绝对定位，**禁止**退回裸 `scrollToItem(index)`——那会把下方刚组合、正在异步解析 Markdown 的
    消息卸载并重置高度，0.1.83 因此每帧弹跳 3 秒，0.1.84 因"只重锚一次"停在了底部；② 列表夹在
    所需方向的尽头时最多再等 `TURN_JUMP_CLAMPED_FRAMES`（24 帧）让下方内容长高，之后即停，最近一组的
    提问顶不到顶部就停在底端；③ 用户拖动即取消。
  - **分段胶囊**（决策 2026-09-03，覆盖 09-02 的"倒数第三组才出现"）：对话满 **3 组**
    （`TURN_PILL_LIST_MIN_GROUPS`）胶囊就常带列表段（1dp 分隔线 + `PromptListIcon`），点按打开
    「我的提问」；长按胶囊主体同样打开。旧规则前两组永远看不到入口，用户不知道有这个功能。
    第一版**不加**上一组 / 下一组箭头。
  - **落地反馈**（决策 2026-09-03，设计稿 `docs/design/landing-feedback-options.html` 方向 3，
    用户否决了外发光与蒙层）：跳到的气泡**只加 1.5dp 品牌色描边、不加底色**，**对齐完成后**先以全强度停 `TURN_JUMP_FLASH_HOLD_MS`（0.3s）再线性淡出（弹层收起加滚动本身近 1 秒，点击即淡的版本落地时已看不见；真机上一出现就淡的 1.5dp 描边也容易错过）
    `TURN_JUMP_FLASH_MS`（1.2s），无硬切；再次跳到同一条则重新开始。搜索命中仍是"蒙层 + 描边"
    的常亮样式，两者不共用（`landingAlpha` 与 `highlighted` 是两个参数）。
- **我的提问**（决策 2026-09-03 v2，设计稿 `docs/design/prompt-list-redesign.html` 方案 A，
  覆盖 09-02 版）：入口 = 顶栏更多菜单第一项、胶囊列表段、长按胶囊。底部弹层内容多高弹多高。
  - **用户任务**：十轮以上的对话里两步内回到任意一轮，并知道自己在哪一轮。旧版失败的原因：
    **序号是主坐标，时间只是补充。**（此处原写「网关历史没有 `created_at`」并把补时间列为需要动

    时间、只有本次实时流过的消息带本地戳——这就是 HG-4「新的提问有时间、旧的反而没有」的由来。）
  - 头部：标题「我的提问」居中，副标题「N 条」（labelMedium 次要色），右侧文字钮「回到最新」
    （关闭弹层并滚到底）。与模型选择弹层同一范式（§5.8），是底部弹层"左对齐标题"惯例的例外。
  - 行 = 26dp 序号圆（surfaceContainerHighest 底，labelMedium SemiBold）→ 14dp → 提问首行
    （bodyLarge，≤2 行）+ 仅当消息有时间戳时的副行时间（labelMedium）→ 12dp → 20dp `ThinChevronIcon`。
    行上下 13dp；行间发丝线（surfaceContainerHigh）从文字左缘 64dp 起画，不从屏幕边缘起。
  - 当前行：primaryContainer 圆角 14dp 整块（左右各内缩 8dp），序号圆反白（primary 底 onPrimary 字），
    箭头与时间用 primary；**不写「当前位置」文字**（色块 + 反白序号已足够，第三遍是噪音），
    改为 TalkBack `stateDescription`「当前位置」；相邻发丝线省略。打开时把当前行放到视野中部
    （上方留 `PROMPT_LIST_ROWS_ABOVE_CURRENT = 2` 行）。
  - 「会话开始」段：灰字、无序号（留同宽空位对齐）、无时间。点行 = 关闭弹层并按胶囊同一规则跳到
    该组起点，气泡落地高亮 1.5s。英文 Your prompts / N prompts / Latest / You are here / Start of chat。

- **聊天内搜索**（决策 2026-09-03，`ChatSearchBar.kt` / `ChatSearchHighlight.kt`）：
  - 搜索条**替换顶栏位置**（同一高度，`Scaffold.topBar` 二选一），消息列表不位移；行 =
    `SearchField` + 计数 `n/m`（0 时中性色）+ ↑ ↓ + ×；返回键先关搜索条。下一行三选一：当前命中的
    来源标签（正文 / 思考 / 工具）+ 片段（命中词高亮）；历史未加载完「正在加载对话…」；
    0 命中且 ≥ 2 字「此会话中没有匹配」+ 「在全部会话中搜索」（导航到搜索页 `search?q=`）。
  - **子串高亮**：正文经 Markdown 渲染器的 `annotator` 在 TEXT token 内加背景色 span；用户气泡、
    思考、工具输出是纯文本，直接 `AnnotatedString`。当前命中所在回合的标记 primary@38%，其余
    回合 primary@16%；整回合描边高亮（§5.4 既有）保留。多词查询按「整句优先，其次每个 ≥2 字
    的词」标记，因为 Markdown 行内文本按空白 / 标点切 token，整句很少落在同一 token 里。
  - **自动展开**：当前命中来源是思考 / 工具时，该回合内含查询词的思考卡 / 工具卡自动展开
    （`shouldAutoExpand`）；关闭搜索不强制收回。
  - **手动刷新 = 用户发起的验真**（决策 2026-09-05，覆盖 0.1.70「运行中排队等完成」）：刷新钮
    与列表下拉在运行中**不再排队**——"看起来不对"恰恰是 App 对运行状态的认知可能过期的时刻。顺序：
    先 `session.resume` 探测（Hermes 回 `session.info{running}`，最多等 1.5s），再拉历史按对账规则
    接受，最后三选一反馈：「已同步 · 运行已结束」（状态过期已纠正）/「已同步 · 仍在运行 · 已运行 N 分钟」
    /「当前对话已刷新」。视觉仍是顶部 `TopProgressLine`（§5.6），不新增指示物。同一探测函数也由
    前台唤醒与看门狗自动调用（`SessionRuntimeStore.probe`）。
  - **工具时间线的折叠**（决策 2026-09-05）：回合**进行中**时间线全铺开——它是进度。回合**已完成**
    后时间线顶部多一行摘要「N 次工具调用 · 总耗时 · M 次失败」+ 箭头；**首次以已完成状态进入视图的
    卡默认折叠**，只留摘要行。运行中看着它跑完的卡保持展开，不在完成瞬间收起——收起会让钉在底部的
    视口跳一下。展开态按回合记住（`rememberSaveable`）；搜索命中在工具里时自动展开（同上一条）。
    依据：0.1.93 首次把完成后的时间线保留下来，25 行常驻在完整回答上方，读起来是噪音而不是信息
    （用户反馈）。
  - **两次及以上就并成一组**（决策 2026-09-06，HG-3，`timelineThreshold = 2`）：原先要连续 3 次
    才并组，两次调用被画成两张各自带边框的卡，读起来就是「两件独立的事」，而它们其实是同一个回合
    里连着做的两步。**只有一次调用仍保持独立卡片**——那时没有「组」可言。与上一条叠加后，两次
    调用在回合完成时折成一行「2 次工具调用」灰字，正是本条要的效果。
  - **完成后的摘要是一行安静文字，不是卡片**（决策 2026-09-06，HG-15）：折叠只解决了长度，没解决
    重量。0.1.94 把完成后的时间线折成一行摘要，但容器仍是 `Surface` + 1dp 描边 + 16dp 圆角、文字
    labelLarge SemiBold，「查看思考过程」也仍是 M3 `AssistChip` —— 一个几乎不会被展开的控件用着
    卡片级重量，还占着答案的开场位置，读起来仍是噪音。回合**已完成**时：思考与工具摘要合并为**一行**
    `labelMedium` / `onSurfaceVariant` 文字 + 12dp 细箭头，**无描边、无填充、无 chip 形体**；
    **点击与自动展开行为一字不改**。工具时间线**进行中**不受此条约束——那时它是进度，该看得见，
    展开态仍用带描边的卡片承载明细。**思考开关两种状态都用安静样式**：它从来不显示进度（运行中的
    思考由 `RunningStatusLine` 表达），永远只是一个折叠开关，按状态换样式只会在完成那一刻闪一下。
    位置保持在正文之上（决策 2026-09-06 明确否掉「完成后挪到正文下方」：内容换位会在完成那一刻
    让钉底视口跳一下，正是上一条为之保留展开态所要避免的）。
  - **任务清单卡不得在回合结束后仍自称「进行中」**（决策 2026-09-06，HG-16）：卡片画的是 Hermes
    最后一次 `todo` 结果，而 Hermes 常常跑完就不再更新，于是一个 `in_progress` 条目会永久地假装
    还在做。回合结束后该条目**中性化**：去掉加粗与实心进行中标记，按普通未完成项渲染。**不标注
    「未完成」**——App 无从知道它是真没做完还是做完没回报，写死结论会冤枉它。卡片头部的状态方块
    同样必须跟随真实进度，不得写死 `in_progress`（3/3 也显示进行中是旧写法的 bug）。
  - **带词打开**：`ChatLaunch.initialQuery` 非空时进入即展开搜索条并填词，历史加载完后由既有
    的匹配 / 高亮流程定位第一处；每次进入只消费一次（`rememberSaveable`），旋转或返回不重开。

### 5.5 长按菜单与底部弹出框范式
统一 `ModalBottomSheet`：标题（≤2 行）+ `ListItem` 操作项（leading 图标）；破坏性操作
红色（error）且必须 `AlertDialog` 二次确认。
- **标题一律左对齐**（决策 2026-09-02）：titleMedium，与列表项文字共用 24dp 左基线。
  理由：会话名标题常折两行，居中后第二行短、与下方左对齐的操作项错位；短标题居中的收益
  小于长标题的代价，一套规范只选一个。模型选择器原先的居中标题已改为左对齐，右侧刷新钮
  保留。
- **聊天消息长按 = 开操作菜单，不是进选中态**（决策 2026-09-09）。这与 GPT/Claude 相反，是
  有意的取舍：
  - **为什么**：① 助手正文是 `markdownRenderBlocks` 切块后的多个 Composable，里面有可点链接、
    横向滚动的代码块（`CodeWithCopy`）、点击进全屏的表格（`ChatTableCard`）；`SelectionContainer`
    罩上去会与这些手势互抢。② 长按腾给菜单，历史消息就不必每条挂一排常驻图标 —— 常驻操作行
    只留在**最新一条**助手回答下。③ 会话是反向 `LazyColumn`，表项会被回收，**跨消息连选在任何
    方案下都不成立**，所以「像 GPT 那样」能拿到的上限也只是单条消息内选择。
  - **划词走全屏选择页**（`TextSelectionDialog`）：关闭钮 + 标题「选择文本」+ 右侧文字钮切换视图，
    正文是 `SelectionContainer` 包一个纯 `Text`。
  - **默认给正文，不给源码**（决策 2026-09-09）：进入时展示 `readableText()` 处理过的可读正文
    —— 标记去掉、结构留下（代码块逐字保留、空行保留、列表缩进保留）。来这里的常见动机是摘一句
    话发给别人，`**加粗**` 和 `| --- |` 不是读者看到的东西。右上「显示原文」一键切回 Markdown
    源码，旋转不丢（`rememberSaveable`）。链接在正文视图下只留文字，要 URL 就切原文。
  - **「选择文本」在菜单里固定第 2 位**，紧跟「复制」：它是复制的同族操作、粒度更小，也是进入
    选择的唯一入口；排在「换个模型重试」「朗读」后面等于藏起来。用户消息与助手回答同一规则。

### 5.6 动效与加载态（`ui/theme/Motion.kt`、`ui/components/BrandLoader.kt`）
- 导航转场：120–190ms tween + 轻微横向位移（chat 进出场见 `HermesNav.kt`）；
  折叠/列表项用 `animateItem()`；节制使用 —— 新动效先对齐这些时长再谈新曲线。

**加载动效体系（决策 2026-09-04，设计稿 `docs/design/loading-motion.html`）**
全 App 的"不确定等待"由启动图标推导：图标是四色四象限的折面 H，明暗只由单一光源决定，
所以我们的加载语汇是**光在转、形不动**，不是转盘在转。三条硬规则：

1. **多彩只属于品牌时刻，页面内一律单色 primary。** 依据 §1 原则 3 与 §2.1：加载动效里出现
   绿色会与 `StatusColors` 的"已完成 / 已连接"抢语义。多彩形态**只**留在启动门（§5.11），页面内
   没有例外：更新下载条也是单色 primary 的 M3 进度条。（早期草案想让确定进度也走三色渐变，
   砍掉了 —— 多一条例外就多一处会漂移的边界。）
2. **一个周期 `Motion.LoopPeriod = 1200ms`，一个延迟门 `Motion.RevealDelay = 250ms`
   + `Motion.RevealFade = 200ms`。** 1200ms 已是发送呼吸环与启动流光的周期；
   250ms 内结束的等待**什么加载物都不出现**（同 §5.4 气泡呼吸、§5.11 启动状态）。
   延迟门只管**占位型**加载 —— 在空白处新插入的加载物（`LoadingState` / `ListLoadingState`）。
   **原地替换一个已有图标**的行内标记（顶栏刷新钮、行尾切换态、上传图标）不加门：它不是多出来的
   家具，是同一位置的状态切换，用户刚点完就该立刻有反馈。
   聊天历史骨架原本自带 1350ms，已并入本 token。
3. **标记只替换"转盘形态"。** 进度条是另一个家族：页面刷新用顶部细线，下载 / 检查更新这类
   **卡内进度**继续用 M3 `LinearProgressIndicator`（有百分比是确定态，没有是不确定态）。
   永不显示假进度。`reduceMotion()`
   （系统"关闭动画"）下所有循环停在最亮一帧的 60%，静态可读，不留空框。

形态与场景对照（权威见 `BrandLoader.kt`）：

| 场景 | 形态 | 尺寸 |
|---|---|---|
| 行形状已知的列表首载（会话 / 项目 / 已归档 / 搜索） | `ListLoadingState` = 骨架行 | 照真实行，封顶 `SKELETON_MAX_ROWS = 5` |
| 行形状未知的页面首载（用量 / 模型 / MCP / 记忆 / 工具） | `LoadingState` = `HermesMark` | 32dp |
| 已有内容的刷新 / 加载更多 | `TopProgressLine` | 2dp 全宽，置顶不遮挡 |
| 聊天运行中（尚无内容 / 生成中 / 思考 / 跑工具） | `RunningStatusLine` = 标记 + 状态文字 | 14dp |
| 行内等待（刷新、切换身份、上传、图片加载、横幅） | `HermesMark` | 14–24dp，跟随原尺寸 |
| 下载 / 检查更新（卡内进度） | M3 `LinearProgressIndicator`，单色 | 全宽 |

- **标记**：H 静止，一束锥形亮光绕横梁中心（图标四色的交汇点）顺时针转；暗部 `DIM_ALPHA = 0.30`
  保证任何相位下 H 都读得出来。比例 14:15 取自图标本身。**不做**旋转形状、不做四象限跳闪。
- **骨架**：全页是**一条**斜向高光扫过（`rememberSkeletonSweep`），不是每块各闪；
  底色与高光 (`skeletonBaseColor` / `skeletonHighlightColor`) 与聊天历史骨架同一套。
  行形状不稳定的页面**禁止**画骨架 —— 猜错的骨架比转盘更差，内容一到就重排。
- **聊天页只有一个指示物**（决策 2026-09-04）：删除三点跳动 `TypingIndicator`。

**4. 手上有内容就不许盖骨架（决策 2026-09-07）。** 骨架只属于**冷开**——本机一个字都没有的那一次。
   一旦本地缓存能给出这条会话的历史，进入会话就**直接显示内容**，后台刷新走上表的
   `TopProgressLine`，不再把 alpha 压到 0 用骨架蒙住。
   在此之前，磁盘上没有历史，`markHistoryLoading` 期间 `historyLoading=true` 会把
   `initialPresentationReady` 摁回 false，于是**即使内存里已有这条会话的消息，用户看到的仍是骨架**，
   要一直等到网络回来 —— 内存缓存只省了布局，没省等待。真正的判据不是"有没有在刷新"，而是
   "**有没有东西可给用户看**"。
   保留的那一半是对的、不能删：揭示前仍要等 LazyColumn 连续几帧坐标稳定
   （`INITIAL_PRESENTATION_STABLE_FRAMES`），否则首帧是几条用户气泡、下一帧才吸附到助手尾部。
   命中缓存时这只是几帧，不是一个网络往返。
   缓存落在 `filesDir/transcript-history/`（gzip 的原始 REST 报文）：**不能放 `cacheDir`** ——
   `file_paths.xml` 的 `<cache-path name="captures" path="."/>` 把整个 `cacheDir` 交给了
   FileProvider，而 transcript 是用户的全部对话内容。备份侧已由 `allowBackup=false` 挡住。
- **指示物属于会话的这一轮运行，不属于某个气泡**（决策 2026-09-05，HG-8）：运行中而尚无
  assistant 气泡在流式（Relay 先观测到 `run.started`、`message.start` 还没到；或一次历史对账把
  进行中的行换掉了）时，同一个 `RunningStatusLine` 以"只有标记"的形态渲染在列表的**常驻底部槽位**
  （`bottom-edge`，与后台进程卡同槽），不新插 item——条件性插入会把钉在底部的视口顶起来。
  列表行说"思考中"、聊天页却一片空白，是这条规则缺席时的形态。
  它是 IM 的"对方正在输入"，而这里发生的是"你的 Mac 在干活"（启动页 0.1.81 删跳动省略号同一理由）。
  首个 token 之前**只有标记、不给文字**（「正在准备」只会被读一次就被真状态替换）；
  文字出现后标记不动、行高不变，48dp 页脚高度契约不变（§5.4 尾跳保护）。
  状态文字不再随呼吸变透明度 —— 一次只有一个东西在动。
- **审批 / 提问卡只活在等待它的那一轮运行里**（决策 2026-09-06，模拟器验 0.1.98 发现）：阶段一离开
  活动集（完成、失败、中断、观测到 `run.completed`），`pendingApproval` / `pendingClarify` 随
  `isGenerating` 一起在 `normalized()` 里清掉，不靠某个写入方记得。Hermes 对没人答的审批会超时
  自行拒绝再往下走，且不通知客户端；卡片若活过运行，重开已结束的会话就会再弹一张返回键关不掉的
  「需要审批」，答一次还把会话打成幻影「思考中」。断线（RECONNECTING）仍属活动，卡片保留（HG-8）。
  对已看到终态的运行再作答不重启它（`continueAfterInput`），从未见过终态的新进程仍乐观进入思考中。
  验证：`StalePendingCardTest`。**进程死亡是比断线更长的一次中断**：提问卡随相位一起跨进程恢复
  （HG-31，§5.2），审批卡不恢复，理由同上。
  验证：`ColdStartPhaseRestoreTest`。
- **仍然用 M3 转盘的三种情况**（决策 2026-09-04，逐处在代码里写明原因）：① 按钮 / FAB 内部
  （新建会话），② 画在照片或头像上（全屏图保存、身份换头像）—— 这两种的底色不可预知，单色标记
  没有对比度保证；③ 颜色承载**状态语义**的指示器（会话行 `RuntimeIndicator` 走 `StatusColors`），
  染成品牌色会把两套色彩系统搅在一起。除此之外页面内不应再出现转盘。
- 验证：`BrandLoaderTest`（延迟门、行数封顶、关闭动画仍可见）、`RunningRowTest`（三态只有一个指示物）、
  截图 `status-preparing / loading-mark / loading-skeleton / loading-skeleton-dark`。

### 5.7 无障碍

- 纯装饰图标 `contentDescription = null`；可操作图标必须给双语描述。

### 5.9 检查更新页（决策 2026-09-02，覆盖 2026-09-01 版）
- 页面仍是**单一推荐更新**界面：只有 manifest 的 `latestVersionCode` 可下载/安装。
  「版本记录」**常驻**推荐卡之下：最近 10 条直接铺开（一行摘要=首条说明，点击展开全部；
  当前版本带绿色「当前」徽标），更早的收进「更早版本（N）」显式展开。旧版本永不直接安装
  （Android 禁止覆盖降级）；**保留最近 5 个版本的 APK** 作回滚材料，更早的在每次检查时清理。
  APK 尚存的旧版本行提供「导出安装包」（复制到公共下载目录，导出前重新校验哈希）与
  「如何回滚？」说明（导出→卸载→安装→重新配置；渠道级回滚走 docs/APP_UPDATE.md 的
  roll-forward runbook）。
- 顶栏左对齐（二级页规范），「重新检查」为顶栏右侧刷新图标按钮，检查中原位转圈。
  当前版本区显示相对时间（刚刚/N 分钟前/今天·昨天 HH:mm/完整日期）。
- 状态色只出现在标题前的 8dp 圆点与徽标上（StatusColors 契约），标题一律正文色。
- 下载态压缩为一行：`已下载/总量` 左、百分比右、进度条下方，并明示「可离开本页，
  后台继续」。推荐卡说明超过 6 条折叠为「展开全部」。
- **分场景自动安装**：更新页处于前台（RESUMED）时下载校验完成→自动拉起系统安装器
  （每个任务只自动拉起一次）；页面不在前台→发「新版本已就绪」通知（activity 渠道，
  固定 id，点击回到本页），绝不从后台弹安装器。安装始终由系统安装器要求用户确认。
- 「我的」页入口行：索引预检（每小时最多一次、失败沿用旧值）发现新版时，行尾显示
  「新版本 x.x.x」与 7dp error 色圆点；升级完成后自然消失。
- **版本记录不排除当前版本**（决策 2026-09-06，HG-13）：只有当某个版本正**作为可下载更新**
  呈现在上面那张推荐卡里时，才从版本记录中省略它（同页不重复同一份说明）。已是最新时，当前
  版本必须留在版本记录第一条并带「当前」徽标——否则你正在用的这一版，它的更新说明在 App 里
  无处可读（0.1.98 实测：版本记录从 0.1.96 起，装着的 0.1.98 与漏发的 0.1.97 都读不到）。
- 索引超过 100 条时客户端取最新 100 而非整体拒收（字节上限 1 MiB 仍 fail-closed）。
- 进入页面即自动检查，同时独立恢复本地下载任务；断网或索引失败不得隐藏已下载、可安装
  的任务。下载可取消、失败可重试；暂停原因、下载错误和安全校验失败使用各自的双语错误码
  与恢复动作，技术原因仅在脱敏详情中显示。
- TalkBack 只播报阶段变化，不逐百分比播报；版本标题与「版本记录」使用 heading 语义，
  历史行播报「点击展开更新内容」；所有按钮保持 48dp（历史行内操作 40dp）最小触达区。

### 5.10 通知（决策 2026-09-02，设计图「Hermes GO 通知栏方案」）

- **一个会话一张卡。** 账号模式下通知 id 由设备 ID + profile + 持久会话 ID 共同决定，旧版模式仍由
  profile + 持久会话 ID 决定（`notificationIdFor`）；运行中 → 需要审批 →
  已完成是同一张卡的状态更新，绝不按事件类型堆卡。WebSocket、Relay 收件箱、未来的 FCM 都先归约进
  `SessionRuntimeStore`，再由 `SessionNotificationProjector` 投影出卡片；不存在第二条出卡路径。
- **账号收件箱属于手机安装，不属于当前 Mac。** 账号模式的 `/api/mobile/events`、送达确认和读取
  状态必须直接使用手机会话 Bearer 访问 Relay 自有端点，不得加 `/v2/devices/{id}` 前缀、转发到
  Connector 或回退携带旧版 App Token。持久游标按 Gateway + 账号 + 手机安装隔离并用哈希键存储；
  旧版连接继续沿用原游标。同步期间账号发生变化时，本批不得消费、确认或推进另一安装的游标。
- **卡片各位置只放一种信息**：小图标永远是 App 的 H 字形单色图标，`setColor` 用头像色
  （`avatarColorArgb(profile)`），部分国产 ROM 会用启动图标替换，所以颜色只是辅助；header 副文本 =
  「身份名 · 状态词」（单身份用户省略身份名），时间用事件真实发生时间（`setWhen`），运行中用
  计时器；标题 = 会话标题（无则「新会话」）；正文 = 该状态的具体内容；`setSubText` 放错误码或用时；
  动作最多 3 个，只放能在通知栏内完成的事。
- **语义色只出现在状态词与「拒绝」按钮**（设计图层面；Android 通知模板本身不支持给状态词着色，
  由系统渲染）。
- **状态与渠道**：运行中 / 重连中 → `run_progress`（LOW，静默常驻，`onlyAlertOnce`，有待办计数时显示
  进度条与「第 n/m 步」）；需要审批 / 需要你的回答 / 等待处理 → `attention`（HIGH，横幅 + 声音）；
  已完成 → `completed`（DEFAULT）；运行失败 / 需要检查 → `failures`（DEFAULT，独立渠道以便单独关闭）；
  后台连接 → `service`（MIN）；新版本 → `updates`（DEFAULT）。设置页四个开关分别对应前四个渠道；
  `service` 与 `updates` 没有开关。
- **连接状态的视觉分级**（决策 2026-09-04）：聊天页顶部横幅分三档，判据是「用户需不需要做点什么」。
  ① **不说**——中断短于 **2.5 秒**的一律不出横幅，也不出「连接已恢复」提示。切走再切回造成的
  socket 抖动对正在跑的任务毫无影响，为它闪一下横幅只会让人以为坏了。计时从**连接首次丢失**
  那一刻起算，不是从最近一次状态变化起算——重连退避会在 Reconnecting → Connecting 之间来回跳，
  按每次变化重新计时会让真正的长时间断线永远不显示。计时**只在聊天页可见时走**：App 在后台时
  空闲连接本来就是被主动关掉的，若让宽限期在后台跑完，切回来第一帧就成了「已中断」，接着又为
  一次用户从未看见的断开播报「已恢复」。用户看不见的时间不算打扰。
  ② **进度档**（`secondaryContainer` + 转圈）——`Connecting` / `Reconnecting` / `Disconnected`。
  中断会自行恢复（回到前台的一方立即重连），所以它是「带错误码的进度」而不是故障；文案仍写明
  `HR-CONN-004`，「详情」入口保留，便于复制诊断信息。
  ③ **故障档**（`errorContainer` + 详情 + 重试）——只留给 `ConnectionState.Error`，即 Relay 真的
  拒绝了我们（`HR-CONN-002`）。
  「连接已恢复」提示只在①之外出现：没告诉过用户断了，就不必告诉他修好了。
- **「后台监控方式」不随通知开关置灰**（决策 2026-09-04）：这组选项现在同时决定「任务运行时是否
  保持连接」，而「省电」是唯一能关掉保活的开关。跟着通知总开关一起禁用，等于让关掉通知的用户
  完全失去控制权——恰恰是最需要这个开关的那批人。其下四个按渠道的开关仍然跟随总开关禁用，
  因为它们确实只影响通知。

- **后台连接卡的出现条件**（决策 2026-09-04，修正 2026-09-02 的隐含规则）：`service` 渠道那张
  MIN 静默卡跟随前台服务，而前台服务的开启条件是「这台手机负责的任务还在跑」——手机自己发起的，
  或当前正打开着其聊天页的。**它不再受通知总开关约束**：通知开关回答的是「能不能打扰我」，
  连接保活回答的是「这个任务还要不要继续跟」，两者绑在一起会让关掉通知的用户（这是默认值）
  在任务跑到一半时被断连。因此关掉全部通知开关后，任务运行期间仍可能看到这张 MIN 卡；
  这是保住连接的必要代价，设置页的通知说明需要写明。**「省电」策略仍然压过这条规则**——
  那是用户明确要求停止后台工作，不是顺带的偏好。任务结束后卡片随服务一起消失。

- **审批卡**：正文 = 描述或「要运行命令」+ 命令；标准档动作「允许一次 · 本会话允许 · 拒绝」，高风险档
  「拒绝 · 打开查看」。**回答卡**：选项 ≤ 2 且非多选时选项直接做按钮 + 「回复…」；否则正文列编号
  选项，动作「回复… · 打开」。**已完成卡**：正文 = 最后一条回复前 140 字（无则「点击查看结果」），
  副文本 = 用时。**失败卡**：本地化短说明，副文本 = 错误码，动作「查看详情」；**需要检查卡**
  （已停止未确认）同渠道，动作「打开检查」。通知栏内不做「重试」，重发走聊天页的发送链路。
- **抑制规则**：正看着该会话的聊天页（App 前台且该会话可见）→ 不发；App 前台但在别处 → 静默发
  （`setSilent`）；后台 → 按渠道提醒。同一 kind 的刷新（工具切换、进度）永不重新提醒。
- **消失规则**：审批 / 提问被任一端回应 → 卡片随状态变为运行中；运行结束 → 同一张卡变已完成 /
  失败；进入该会话聊天页 → 取消；用户划掉的卡在状态种类不变前不再出现；已在聊天页看过的终态卡
  离开后也不再出现。
- **动作反馈**：按下后卡片变「处理中…」并撤下按钮；成功后随状态更新；失败时按钮回来，正文追加
  「发送失败，请重试」，副文本 `HR-NOTIF-001`。
- **锁屏脱敏版**（`setPublicVersion`）只保留图标、状态词、会话标题；命令、问题、回复内容不上锁屏。
- **多会话**：两张以上时发分组摘要「Hermes GO · N 个等待处理 · M 个运行中 · K 个已结束」；排序
  等待处理 > 失败 > 已完成 > 运行中。

### 5.11 开屏 / 启动门（`ui/startup/StartupScreen.kt`，决策 2026-09-02，设计稿 `docs/design/startup-redesign.html`）
- **层级**：字标是主角，图标是陪衬。图标 144dp（自适应前景层，可见 H 约 96dp）→ 12dp →
  字标 `HERMES GO` 32sp/Bold/字距 0.16em（`colorScheme.onSurface`）→ 8dp → 英文标语 14sp 次要色。
  取消旧版 250dp 图标与 8% 透明度光晕（近白底上不可见，等于白画）。
- **位置**：品牌组不再固定 -48dp 居中，图标顶边锚在屏高 **22.5%**（视觉中心约 42%），
  随屏幕高度按比例；**加载态与失败态图标、字标位置完全一致**，失败时不跳位。
- **状态归入品牌组**：标语下 44dp 放状态文字（13sp 次要色）+ 12dp + 进度条；进度条
  **144dp × 3dp** 与图标同宽，蓝→绿→黄渐变**锚定整条宽度**、用 clip 露出进度（旧版随填充
  拉伸，右端永远是黄）。屏幕底部只留版本行 `0.1.81 · DEBUG`（labelSmall，导航栏内边距外 32dp），
  测试渠道靠它对版本。
- **快启动不解释**：状态文字与进度条延迟 `STATUS_REVEAL_DELAY_MS = 700ms` 才淡入；若在此之前
  已到 READY，则**整段始终不出现**——快的启动只看到一次淡入，不看到流水账。文案从六段合并为：
  连接前四阶段共用「正在连接」（恢复场景「正在恢复连接」）、「正在准备会话」（恢复「正在恢复当前页面」）、
  「连接就绪」。阶段粒度仍驱动进度条。删除省略号跳动，进度条流光是唯一持续动效，READY 后停止。
- **入场 / 退场**：冷启动图标从系统 splash 落点（屏幕中心、**2×**——系统 splash 容器 288dp 对
  我们的 144dp，真机实测 118dp:58dp；2026-09-03 由 1.5× 修正）缩放平移到位（320ms，Standard），
  字标与标语延迟向上淡入 12dp；就绪后整屏 `fadeOut + scaleOut(0.98)`（`Motion.DurationMedium`），
  首页同时 `fadeIn + 上浮 16dp`（`MainActivity`）。失败态无 splash 可承接，改为 150ms 淡入。
- **热恢复静默**（决策 2026-09-03，取代「热恢复遮罩 150ms 淡入」）：**只有冷启动和真正的失败态
  可以占屏**。`CONNECTION_RECOVERY` 的加载态一律不渲染门 —— 会话页留在原位，继续显示它已经提交的
  内容，socket 由 `HermesGatewayClient` 自己的 500ms→10s 退避重连恢复。恢复失败才升起失败态门
  （它带错误码和「重新连接」/「检查连接设置」两个动作，是可操作的）。同时 `HOT_START_DEBOUNCE_MS`
  200ms → **3s**：先让退避重连自愈，抖动一次不再触发探测与首屏数据恢复。
  由来：旧规则下任何一次掉线都把全屏门盖到聊天页上，实测 2026-09-03 单日 55 次重连 = 几十次
  「被弹回启动页」，用户读作 App 崩了；同一次恢复还会把 0.5 MB 的 transcript 重复下载 7 次。
- **深浅**：由生效主题判定（§2.2）。底色是全 App 唯一必须与 window 资源一致的颜色
  （`@color/startup_background` 浅 `#F8FAFD` / `values-night` 深 `#0D141B` = surfaceContainerLowest dark），

  多彩图标两种模式不变，字标走 `onSurface`，错误色走 `colorScheme.error`。已知限制：系统 splash
  只跟随 OS 夜间模式，「系统浅色而应用选深色」时 splash→门有一次颜色切换。
- **失败态**：进度条**隐藏**（半截彩条与红色错误文案打架）；错误摘要 bodyMedium 错误色、最宽 280dp；
  错误码 `HR-*` 从括号里拿出来**单独一行**等宽 labelSmall 次要色；「重新连接」实心钮 240dp × 44dp
  居中，「检查连接设置」文字钮同宽，不再通栏。账号启动探测必须保留结构化原因：只有
  `HR-AUTH-003/004/005` 进入重新登录；`HR-AUTH-007` 保持可重试限流，`HR-CONN-005` 明确提示启动
  Desktop，`HR-ACCOUNT-001` 明确提示账号不可用，`HR-ACCOUNT-002` 保持账号服务重试，不得全部折叠为
  登录失效或通用 `HR-CONN-002`。持久化重新登录门禁在冷/热启动都直接进入 `HR-AUTH-003` 修复态，
  不得探测或连接仍留存的旧版凭据。
- **紧凑（横屏 / 高度 < 560dp）**：图标 96dp 与字标（24sp）横排、左对齐，品牌组顶边 10% 屏高，
  状态与失败态仍在其下方居中。
- 验证：`StartupScreenTest`（延迟揭示、READY 早到不揭示、文案合并、失败态结构、版本行、
  热恢复不占屏、热恢复失败仍占屏）、`StartupCopyTest`，截图
  `startup-loading / startup-loading-dark / startup-failed`。

### 5.12 底部主操作按钮（决策 2026-09-02，首例 `ui/profiles/ProfileEditScreen.kt`）
- **适用**：页面有一个明确的提交类主操作（保存 / 连接 / 创建）且内容可能超过一屏。
- **形态**：Scaffold `bottomBar`，实心 `Button` 52dp 高、左右 16dp、上 8dp、下 16dp，再加导航栏
  内边距（`navigationBarsPadding`）；键盘弹出时随键盘上移（`imePadding`）；内容在其下方滚动，
  列末留 16dp。不加分隔线或底色，靠留白与内容分离。
- **不适用**：表单很短、主操作不需要随时可达的页面（定时任务编辑）用跟随内容的普通按钮，
  顶部 16dp；对话框内按钮按 M3 默认。
- 历史：身份设置页曾把 52dp 通栏按钮放在滚动列末尾，高屏留一大截空白、矮屏又随内容滚走，
  两头不靠——这是本条的由来。

### 5.10 新会话空态（决策 2026-09-03）
- 本地新建且无任何消息的会话渲染**居中问候组**：身份头像（48/64dp）＋时间问候＋固定副行
  ＋**纯展示**状态胶囊（`模型 · 推理档位` 前置 6dp 连接点，绿=已连接/琥珀=连接中）。
  组置于光学中心（垂直 bias −0.12）；IME 弹起时整组缩一档（头像 48dp、标题 19sp、副行隐藏）。
- 问候按时间五段（5–8 早上好 / 9–13 上午好 / 14–18 下午好 / 19–23 晚上好 / 其余 夜深了）；
  名字取身份自定义 displayName，未设置则省略（不显示占位名）。断连时副行换
  「连接恢复后就能开始」、胶囊换「等待连接…」——**新会话任何情况下不显示"历史消息暂时
  无法加载"**（isNewSession 独立分支）。
- 空态组无任何可点元素：模型/推理切换保持在输入框原位，胶囊只随其实时镜像；加号、发送、
  语音的位置与交互不因空态改版发生变动。首条消息出现，整组 150ms 淡出。
- TalkBack：整组一个语义节点，播报「新会话。{问候}。{副行} 当前 {胶囊}」。
- 未来的智能建议（服务端推荐/历史提炼）在胶囊下方追加，不改本节既有元素。

### 5.13 分享对话（决策 2026-09-02）
- 「更多 › 分享对话」**先弹格式选择层**（三项：文字 / Markdown 文件 / 长图），选定后才跳系统
  分享盘。每项一行说明，讲清各自适用场景，不让用户猜。
- **文字**：`EXTRA_TEXT` 直发，适合短对话直接粘贴。
- **Markdown 文件**：写入 `cacheDir/transcripts/`，经 FileProvider 以 `text/markdown` 分享。
  文件名 `HermesGO-<标题>-<时间戳>.md`，标题必须过 `transcriptFileBaseName` 清洗（路径分隔符、
  保留字符、换行、超长一律处理）。正文原样保留 Markdown，代码块与表格必须无损。
- **长图**：离屏 GraphicsLayer 渲染（`OffscreenTranscriptExporter`），三条硬规则 ——
  ① **固定浅色**渲染，无论 App 当前主题（深色长图在他人聊天里过重，且更扛不住二次压缩）；
  ② 底部**页脚**标注会话标题与导出时间 + Hermes GO；
  ③ **限长策略 A**：渲染前用 `transcriptImageFitsBudget` 预估，超出
  `TRANSCRIPT_IMAGE_MAX_HEIGHT_PX`（12000px，GPU 纹理与内存的安全线）**直接拒绝出图**并引导改用
  Markdown 文件 —— 宁可不出，也不给用户一张残缺或渲染失败的图。
- 长图中的图片附件：**已缓存的正常渲染，未缓存的画占位框**；导出绝不触发下载，分享动作不得
  阻塞在网络上。
- **导出必须记录文件附件**（决策 2026-09-05）：Markdown 与长图此前都只输出 `text`，文件附件
  在导出件里完全消失。用户拿导出的对话记录核对交付时，会把一次成功的附件投递误判为失败
  （2026-09-05 实际发生）。两种导出都要在该条消息末尾补一行 `附件：<文件名>`；长图同样只
  写文本行，**不下载文件**，与上一条的不阻塞原则一致。

### 5.14 用量页（`ui/usage/`，决策 2026-09-03 定位 / 2026-09-04 结构）

> 小节编号说明：本文 §5 的编号已被并发追加撞号（现存三个 5.10、两个 5.8、一个 5.13）。此处取
> 下一个未使用的号，不重排既有小节，以免与他人正在编辑的段落冲突。

- **定位：活动量优先，成本弱化为参考**（决策 2026-09-03）。主指标是 token 体量、会话数、调用数、
  模型占比；金额降级为带口径标注的次要信息。理由：Hermes 只统计成功返回用量的主对话调用，静默
  漏掉全部辅助调用与服务商侧重试，上游自己在面板里**默认隐藏**该数字，因为"看起来精确到可以和
  账单比"比不显示更糟。我们不重复这个错误。
- **三块必须对得上账**（决策 2026-09-04）。上游给的是两本互不相交的账：`daily`/`totals` 出自
  sessions 表、**只含主对话**；`by_model` 已把辅助调用合并进去。因此：
  - 顶部总量 = 主对话 + 辅助，且**显式写出这个拆分**；
  - 「按模型」标注**含辅助调用**，其逐行之和大于主对话是正确的，反过来才是回归；
  - 「按辅助任务」是同一笔辅助量的另一种切分，不额外计入总量。
- **每日图只能画主对话**（上游硬约束，不是取舍）。辅助用量按 `(model, task)` 聚合，**不带日期
  维度**，客户端补不出来。图表标题必须如实标注，不得把辅助量摊进日线。
- **范围分段 7 / 30 / 90 天，默认 30**（决策 2026-09-03），走 `days` 查询参数（上游钳制 1–365）。
  选择存设备本地，不上行、不跨设备同步 —— 它是查看偏好，不是身份数据。
- **稀疏行必须先补齐日历再取窗口**。上游对无会话的日子不发行，直接消费原始行会让「本周」变成
  「最近 7 个**有活跃**的日子」（稀疏使用时可跨月），也会让图表把不等间隔画成等距。
- **页面结构**（自上而下）：主指标卡 → 每日趋势 → 按模型 → 按辅助任务 → 成本 → 口径脚注。
  容器一律走淡卡语言（§2.3），列表行**无分隔线**（§5.2 同规），下拉刷新。
- **趋势图规范**：真实日期轴（两端 + 中点标注）、Y 轴三档刻度、点选某天打开当日明细弹层。
  禁止无坐标、无日期、不可点的纯色块 —— 那样的图只能看出"有起伏"，看不出任何一天。
- **成本区块**：独立成块并常驻一枚 ⓘ，点开说明口径（本机估算 / 不含辅助调用与重试 / 缓存写入
  不计 / 实际账单通常更高）。金额**不给两位小数**（`≈$4.2` 而非 `$4.23`），伪精度即误导。
  若上游 `dashboard.show_token_analytics` 为 false，则**跟随隐藏**成本区块（经 `/api/config` 读取，
  不需要改上游）。
- **空态与错误态必须可区分**：无用量 → 空态文案；取数失败 → `ErrorState` + 错误码 + 重试。
  历史：旧版两种情况都显示 `0 / 0 / $0.00`，用户无法分辨是没用过还是连不上。
- **口径脚注常驻**：统计窗口 N 天 · 按会话开始日归集 · 日界为 UTC。三条都是上游行为，写出来
  比让用户自己发现好。UTC 日界对 UTC+8 用户意味着凌晨 0–8 点的会话记在前一天 —— 这是已知偏差，
  改它需要动上游 SQL，属独立立项。
- **不属于用量的指标不放这里**：「会话总数 / 已归档 / 消息数」是被删除的 session-admin 页遗留，
  量纲与用量不同，已于 2026-09-04 移出。
- **入口在设置页**（「记忆与预算」之后，决策 2026-09-11）：卡片页的统计格随 Stitch 基线-卡片页
  合成了单一「远程节点」卡，本周用量格不再存在（§5.1）。历史：抽屉统计格副行曾 = 会话数，不是金额（决策 2026-09-03），
  因为半格可用文字宽仅约 95–107dp，放不下两段信息。

### 5.14b 启动门的阻塞规则（决策 2026-09-05）

启动门的职责是**在没有界面可显示时占位**，不是报告故障。一旦背后有可用界面，它就该让位。
**阻塞与否由 `reason` 决定，不由 `failure` 决定**：

| 场景 | 规则 | 理由 |
|---|---|---|
| 冷启动 / 首次配置 | 全屏 + 重试 | 背后什么都没有，阻塞是唯一诚实的选择 |
| 热启动 + 可自愈失败（`HR-CONN-001/002/005`、`HR-RPC-001`）| **隐藏启动门** | 界面早已渲染，用户上一秒还在看。交回给健康条（可达性）、聊天页横幅（socket）、页面自身刷新（数据）——它们都能报告而不夺走整个 App |
| 配置 / 鉴权（`HR-CONFIG-001/003`、`HR-AUTH-001`）| 冷热都接管 | App 真的没法工作，必须让用户去修。走 `RepairRequired`，不经过上面这条 |

- **完成动效只属于冷启动**。热启动就绪后立即隐藏，不再多停 `SUCCESS_COMPLETION_MS`——背后本来
  就是可用画面，多出的半秒是「无缘无故闪了下启动页」而不是仪式感。
- **首屏恢复的成功判据是历史对齐，不是拿到 live handle**。跑完的会话本来就没有 handle，把它
  当失败会让一次完全正常的返回变成全屏报错（HG-1）。

### 5.15 诊断页（`ui/settings/DiagnosticsScreen.kt`，决策 2026-09-05）

- **release 构建默认关闭，debug 构建默认开启**（决策 2026-09-08）。开关文案必须同时讲清三件事：
  记什么、令牌不记、记录存哪里存多久。少任何一条，用户就无法判断该不该开、开了要不要关。
  由来：默认关闭意味着一次故障只有在用户**事先**打开过开关时才留得下证据，于是首次发生的那一次
  必然查不了——HG-27 之所以只能停在「现有日志无法判定」，一半原因在此。当前所有交付给测试者的
  APK 都是 debug 构建（`scripts/package-debug-apk.sh` → `Hermes-Remote-<版本>-debug.apk`），
  所以这条实际等于「日常在用的这个 App 一直在记」。release 保持关闭，隐私决定不变。
  **用户的显式选择在两个方向上都压过默认值**：在 debug 构建里关掉它，重启后必须仍然是关的。
- **记录跨进程存活**（`data/diagnostics/DiagnosticLogStore.kt`）。开启后条目除了进内存环形缓冲
  （500 条），还滚动落盘到应用私有目录（两个文件轮换，各 256KB，保留 7 天），下次启动读回。
  理由：最值得看的那些运行——崩溃、息屏后被系统杀——恰恰是内存缓冲活不下来的那些。
- **上一次运行的条目必须标出来**。恢复的条目时间戳与本次运行同一时钟，光看时间分不清，所以
  行首标签追加「· 上次运行」并改用 `onSurfaceVariant`（本次运行为 primary）。**禁止**只靠
  时间戳暗示来源。
- **分享导出磁盘全量，且必须是文件**（决策 2026-09-05）。页面列表仍只显示最近 500 条（滚动
  性能），但分享出去的是整个滚动文件——内存那 500 条在会话活跃时只覆盖几分钟，通常短于"遇到
  问题→走到设置"这段路，导出封顶等于把现场丢掉。载体是 `FileProvider` 附件而不是
  `EXTRA_TEXT`：几百 KB 的 Intent extra 会撞 Binder 事务上限，侥幸没撞的接收方也常自行截断，
  截掉的正是让全量导出有意义的那前半段。读盘必须离开主线程。
- **每次开启写一条会话头**（`session` 频道）：版本号、versionCode、pid、系统与机型。导出既然
  按一条流读回，per-entry 的"上次运行"标记无法再表达进程边界，改由会话头承担；顺带补上截图
  永远带不出来的构建信息。
- **「标记现场」按钮**：往日志插一条显眼分隔。否则读一份分享来的日志第一步永远是猜哪一分钟
  才是现场——而末尾那几行通常是用户走到设置页的导航，不是故障本身。
- **轮询噪音必须压住**。收件箱轮询在前台每 2 秒一次；请求与响应各记一行时，基线约 1 行/秒，
  500 条缓冲约 8 分钟就被挤空。快速成功的轮询不记（它说不出 `lifecycle` 频道没说过的事），
  慢的或失败的照记；传输层异常也必须记——只有开头没有结果，读起来和"请求再没回来"一模一样。
  **同一条规则适用于所有轮询**（2026-09-08 扩充）：`process.list`（每个活跃运行 5 秒一次）、
  `/api/profiles/sessions` 与 `/api/messaging/platforms` 的刷新。HG-27 那份报告里这四类占了
  500 条环形缓冲的 30%，与解释故障的行争抢同一份字节预算（磁盘上限是 2×256KB，实测 460KB
  只买到 31 小时，所以"加日志"必须同时"减噪音"）。
  **`/api/status` 是明确的例外，永远照记。**「REST 一路 200 而 socket 卡死」这个对比正是
  HG-27 能被读懂的原因；健康探针改为只在**档位**变化时出声之后（`Healthy` 带着 `latencyMs`，
  按值比较时每次探针都算"变化"，那条去重从来没生效过），它是唯一还承载这个信号的行。
  流式增量同理：`message.delta` / `reasoning.delta` / `thinking.delta` 一律不记——
  `thinking.delta` 曾漏在过滤器之外，占了 HG-27 缓冲的 5%。
- **连接快照**（决策 2026-09-08）。横幅升起的那一刻、以及提交反馈报告的那一刻，往 `ws` 频道写
  一行 `snapshot`：连接状态、socket 代号、`manuallyClosed`、就绪门是否完成、握手看门狗是否还活着、
  socket 是否存在、已经处在 `Connecting` 多久、距上次 `gateway.ready` 多久。
  由来：HG-27 的现场散在十几行里，而**恰好该说话的几处一行都没有**，结论只能停在"无法判定"。
  一行全量读数比十行散点更能回答"它当时到底卡在哪一步"。健康时这两个时刻都不会到来，
  所以字节成本接近零。**票据与令牌永不进入这一行**——WS URL 把单次票据带在查询参数里。
- **兜底路径不许静默**（决策 2026-09-08）。看门狗放弃、退避重连被丢弃、App 主动关闭连接、
  票据环节失败——这些"什么都没发生"的分支必须各自留一行，并写明**是哪一条 guard、哪一个调用方**。
  恢复机制的失败在日志里的样子就是"没有样子"，静默的提前返回等于没有兜底。
- **清除即彻底清除**：内存与磁盘一起清，不留"看不见但还在"的副本。
- **按会话筛选与导出**（决策 2026-09-05）：日志里出现过的会话 id 各成一枚 `FilterChip`（最近提到的在前，
  首枚「全部」）；选中后列表与「分享」都只包含提到该会话的行（`s=<id>` / `session=<id>`），分享主题
  带上 id。用户报告问题时交出的是**那一条会话**的证据，不是一周的全部活动。状态机的 `[phase]` 行、
  对账的 `[history]` 行、观测事件的 `[lifecycle]` 行都带 `s=<id>`，是这个筛选成立的前提。
- 崩溃报告（`data/diagnostics/CrashReporter.kt`）在面包屑之后、堆栈之前附带诊断日志，空区块
  不出现空标题。堆栈永远在最后一段——读的人滚到底就是崩溃点。


### 5.16 消息渠道与机器人会话（决策 2026-09-06，设计稿见上方画布索引第三条）

Hermes 可以接进钉钉、Slack、飞书等 33 个平台。这带来两类内容，**性质不同，位置也不同**：

| | 会话（内容） | 渠道管理（配置） |
|---|---|---|
| 位置 | 主屏分段第 2 位「**机器人**」 | 设置 → 消息渠道 |
| 出现条件 | **配过 ≥1 个渠道、或有渠道历史时才出现**；最后一个渠道移除后让开 | 常驻 |

**为什么是分段而不是一级页**（论证修订 2026-09-09）：分段承载「**看哪一批会话**」，「更多」承载
「**怎么组织会话**」。机器人是另一批会话，所以留在分段；项目是分组维度、归档是状态管理，所以
进「更多」+ 全屏页。原来的论证是「『已归档』是先例，同样并进分段」——那条先例已经作废，是这次
反过来把归档搬走的。诚实记一笔：这条线也参考了实际使用频率，项目与归档确实低频。
**为什么不直接混进「会话」段**：机器人流量会淹没交互式列表。分段是隔开的，不淹没任何东西。
**为什么配置必须留在设置里**：条件分段没渠道时不存在，「添加第一个渠道」需要一个常驻入口。

- **段名叫「机器人」**，不叫「渠道」。它说清了对面是谁在跟 Hermes 说话；而「渠道」在公司语境里
  容易读成销售渠道。英文 `Bots`。
- **没有机器人时整行不渲染**：只剩一批会话就没有可切换的东西，留一个孤零零的「会话」段是噪声。
- **四段的 91.5dp 宽度硬约束已经作废**（2026-09-09）。英文归档标签因此从被挤出来的 `Archive`
  改回更准确的 `Archived`；`Chats · Bots` 两段在 fontScale 1.3 下不再有截断风险。由
  `ScreenshotTest` 的 `segments-2-zh` / `segments-2-en-fs13-dark` 两张钉死（原来是五张）。
- **段内按渠道分组**，组头带状态点；不用会话列表的时间桶——这里的问题是「Hermes 在钉钉上干了什么」。
- **本段不显示 FAB**。这些对话由对方在那边发起。

#### 机器人会话就是聊天页，不存在第二条渲染路径（决策 2026-09-09，取代 09-06 的只读页）

**硬规则**：点开一条机器人会话，打开的**就是聊天页**。没有第二个界面，也就没有第二套判断。

由来是一份账：曾经的 `BotTranscriptScreen` 是同一份历史的第二条渲染路径，它先后漏掉了聊天页
早就处理好的四类东西——上下文压缩交接、服务端注入的脚手架（`[ASYNC DELEGATION COMPLETE …]`
被画成一个带对方署名的气泡，仿佛是本人打的字）、Markdown 渲染、时间线注记分类。
09-06 的对策是「分类转调聊天页」，那只堵住了「这一行算不算一次对话」；**第五次是时间戳**——
聊天页早有 `showsTimeSeparator`，那一页却一个时间都不显示。补丁挡不住，所以把页删了。

有一处可见差异是对齐而非回归：被脚手架剥空、又没有附件的轮次，旧页直接隐藏，
聊天页保留它并渲染成一行安静的时间线注记（`ChatUiState.organizedForDisplay` 是故意的）。

#### 机器人会话可以输入，代价是一次性弹窗（决策 2026-09-09）

09-06 写的只读理由是**错的**：那句「从这里发出的任何内容都会以机器人名义出现」描述的是
「把消息送进钉钉」，而那件事根本没发生，也不可能发生——出站绑在适配器上，只活在
`hermes gateway run` 进程内；手机连的 dashboard 进程**不加载适配器**（详见
`docs/HERMES_CONTRACT.md` 的出站边界一节）。上游自己的 Web 聊天页从不区分会话来源，一直给
输入框，走的是同一个 `prompt.submit`。**能力一直都在，是我们自己关掉的。**（2026-09-09 由用户
在钉钉本体实测确认：从桌面端发出的消息，钉钉收不到。）

真正的代价在别处，**这才是要告诉用户的**：那一轮写进同一份 `state.db`，对方下次在那个平台找
Hermes 时，Hermes 会带着这句他没见过的话回答。

- **怎么说**：`AlertDialog`，**按渠道一次**，确认后不再提（`BotSendNoticeStore`）。
  文案按 `source` 生成（`botSendNoticeTitle` / `botSendNoticeBody`）——同一个页面也承载 Slack 和
  飞书的会话，不能写死钉钉。
- **为什么不是输入框上方常驻一行**：输入框下方已经常驻「内容由 AI 生成」，上下各一行灰字等于
  把一个控件夹在中间。弹窗换来平时界面完全干净。
- **动作全保留，只去掉 handoff**：它只有「本地会话 → 平台」一个方向，对已经在平台上的会话
  无意义，服务端也会直接拒（4025 / 4026）。
- **来源写在顶栏副标题**（占 workspace 那一行的位置），不用全宽横幅：那条横幅归瞬时连接状态
  所有，来源是身份不是告警，常驻一条会永久下推正文、并在视觉上压过它不该压过的东西。
- **模型芯片有第三态**：机器人会话没有已知模型时显示「模型未知」，**不得退化成「默认模型」**。
  那是本机 profile 的设置，不是对面那一轮用的模型；旧代码还把它写进了会话状态。
- **打开不 resume，第一次发送才 resume**：`bindLiveHandle` 会连带开启进程轮询，浏览一份别的
  进程拥有的记录不该在 Mac 上物化一个 runtime。代价是首次发送前 `@` 路径补全不可用、
  思考档位显示「默认」。

气泡归属沿用 §5.4：**说话的人拿气泡，Hermes 无气泡**。但输入框一开，右侧同一列就有了两个
说话人——对方的话和你在这里打的字。所以每条用户气泡都署名（`userTurnLabel`）：本机发的署
「你」，其余署对方。复制 / 分享 / 导出 / 提问列表同理，**不能把对方说的话署成「你」**。

#### 渠道状态：一律取服务端 `state`，禁止自算

服务端返回 `connected` / `pending_restart` / `startup_failed` / `gateway_stopped` /
`not_configured` / `disabled`。历史教训：客户端曾用 `enabled && gateway_running` 自算，
而这个组合**分辨不出「已连接」和「已保存但网关没重启」**，于是刚配好的渠道和启动失败的渠道
都显示成绿色「已连接」，而机器人一声不吭。

- 字段缺失或值未知时退化到「未配置 / 已停用 / 状态未知」，**永不退化成「已连接」**。
- `pending_restart` 是「一步没做完」而不是故障：用**中性淡卡**承载并带「重启网关」动作，
  不占用 `errorContainer` 警示条。重启会中断所有渠道当前的对话，必须 `AlertDialog` 二次确认（§5.5）。
- 状态色只走 `StatusColors`，且只出现在圆点上；`not_configured` / `disabled` 的灰
  **借用 `outline`**（`StatusColors` 只有 GOOD/WARN/BAD 三档，未新增第四档）。
- 平台标识用**中性圆容器 + 按类别的线性图标**（聊天 / 邮件 / 短信 / 通知 / 程序化），身份靠名字。
  不用品牌字形：破坏 §4.1 且涉及商标。
- 列表默认只显示**已配置**的；全目录在第二个分段里。

#### 一个告警槽位，根因优先

主屏顶部只有**一个**告警条，消息渠道与定时任务共用，位置在顶栏（以及分段行，若有）之下。

渠道断线时，投递到它的定时任务失败**不计进定时任务徽标**，改写进渠道条文案
（「Slack 未连接 · 3 个定时任务受影响」），点进去是渠道——修在那儿。
自身原因失败的任务保留自己的告警。归并要求任务的 `deliver` **明确指名**该平台；
`origin` 解析不出具体平台，保留独立告警——**没归属的失败好过归错的失败**。

#### 三张列表共用的骨架（决策 2026-09-08）

会话 / 机器人 / 定时任务 / 消息渠道的列表页共用同一副骨架：

```
固定分段（不随列表滚动）
↓  可点的告警条（带箭头）
↓  分组列表
↓  右下 extended FAB（新建 / 添加）
```

**行尾一律是细箭头，整行可点**（§5.1「可点必有箭头」）。测试连接、启用开关这类操作放在详情页，
不塞进行尾——一行里三个可点区域，用户无法预判点下去会发生什么。
**顶栏不放「+」**：新建统一走 FAB，与会话列表既有范式一致。

渠道列表是唯一保留 leading 图标的：33 个平台需要区分。图标表达的是**类别**（聊天 / 邮件 /
短信 / 推送 / 程序化，`MessagingCategory`），不是品牌——品牌标志是填充式、多色且涉及商标，
三样都与 §4.1 冲突。未分类的平台落到「聊天」：绝大多数确实是，而给 webhook 画个对话气泡，
比给对话画个 webhook 图标错得轻。

#### 定时任务列表与本段同构（决策 2026-09-07）

三张列表（会话 / 机器人 / 定时任务）共用一套行文法与分组：

```
[名称] [状态点]                    [⋮]
副行：节奏或落点 · 上次结果
```

**健康的行不说「上次成功」**——那会让唯一失败的那行淹没在一片成功里。副行由纯函数生成
（定时任务是 `cronSublineText`），由测试钉住，而不是各画各的。

**行尾是溢出菜单，不是时间。**「下次运行」的精确时间在列表里帮不上判断（「每 10 分钟」加
「上次失败」才是决定要不要点进去的依据），留给详情页；而暂停 / 立即运行 / 编辑 / 删除
必须有入口。

分组一律 **需要你处理 → 正常 → 非活动**。定时任务列表因此去掉了 leading 图标
（原为 Material 填充图标，§4.1 禁止），状态改由标题行尾的圆点承载并走 `StatusColors`
（原先用 `colorScheme.primary` 当成功色，是 §2.1 那笔旧账的重演）。
唯一差别：**渠道列表保留 leading 类别图标**，因为 33 个平台需要区分。

#### 转到消息渠道（handoff）

入口在**聊天页的「更多」菜单**，作用对象是**自己的会话**，不是机器人会话。
只列出真的会被接受的渠道（已启用、已配置、设过落点）。

不可逆，所以确认框在点击前列出全部后果：目标渠道当前那条对话会结束、这条对话会从手机列表消失
（source 变成该渠道）、搬过去拉不回来。成功后退回列表，失败留在原地。

#### 通知

**只报渠道故障**，渠道里的新消息不提醒——钉钉已经响过一次了。独立通知分类，可单独静音。
检查搭在通知回退本来就有的十五分钟唤醒上，**不单开定时器**。
断线的渠道只提醒一次，恢复后再断才会再提醒。

### 5.17 模型选择（`ui/models/ModelSelector.kt`；照 Stitch 基线-模型选择 / 暗夜 重做 2026-09-12）

聊天输入区的模型芯片打开的弹层，与 设置→模型 页共用同一套卡片与行。两处的区别只有一处：
弹层改的是**这一次对话**的模型，模型页改的是**个人资料默认值**，所以模型页不显示推理强度、
不显示「恢复默认」，状态卡的作用域写「当前默认」。

弹层本身照 §5.8 全局硬规则：`hermesSheetState()`、`sheetGesturesEnabled = false`、
`SheetCloseHandle`、16dp 圆角。稿子把弹层画满整屏并给了 32px 上圆角 —— 那是稿子模拟的手机边框
（同一个容器里还画着状态栏），不是弹层，不采纳。抓手同理保持全局的 32×4dp，不为单张稿分叉。

**自上而下的结构**

1. **标题栏**：「选择模型」左对齐（`ModelSheetTitle`），右侧刷新图标 + 32dp 圆形 ✕，下缘一条
   `model.divider`。刷新中图标位换 `RunSpinner(18dp)`。✕ 用的是主题弹层那一套写法
   （`model.inset` 底、暗色才加描边、16dp Close），不是新部件。
2. **当前状态卡**：`model.card` 白卡 + `model.card.border` 描边 + `modelCardShadow()`，16dp 圆角，
   **左缘 6dp `model.accent` 竖条**。首行 = 模型名（`ModelCardName`）+「当前使用」徽标 +
   右侧「恢复默认」；次行 = 提供商（`ModelCardProvider` / `model.ink.faint`）。
   `model.divider` 之下是**推理强度行**：`model.inset` 凹槽 + 图标 +「推理强度」+ 右侧下拉钮
   （`model.accent` 圆点 + 当前档位 + chevron）。模型与强度仍是**一张卡**，禁止拆成两个并列框。
3. **快捷切换**：小标题「快捷切换」；切换进行中时右侧出现「正在切换至 X」。下面一排横向滚动 chip，
   内容是**本机记录的最近使用模型**（设备本地偏好，与收藏同层，上限 5，去重前置）。
   切换中：目标 chip 蓝底蓝边 + 旋转标，其余 chip 降透明并禁用。
4. **目录**：每个分组一张卡（同状态卡的填充/描边/阴影）。卡头 `model.bar` 底 + 下缘 `model.divider`：
   收藏卡是琥珀星 +「收藏模型 (N)」+ 右侧「固定顶部」；提供商卡是名称 +「N 项」
   （`ModelGroupCount`，本屏唯一的 mono 步）+ 折叠 chevron。卡内每行之间一条 `model.divider`
   —— 这是本屏对「列表行不画分隔线」的**有意例外**，因为行被收进了卡里。

   **「N 项」与 chevron 是一根贯穿所有卡的右对齐轴**（HG-32）。给标题**一个**填充式
   `weight(1f)` 让它吃掉全部余量，标题过长就省略；**不要**给标题 `weight(1f, fill = false)`
   再跟一个 `Spacer(weight(1f))` —— 那样两个权重把余量对半分、标题又能缩进自己那一半，
   剩下的留白卡在右边，卡与卡之间就按标题长短错开。同理，收藏卡的「固定顶部」靠的是
   标题**不带**权重、由单个 Spacer 吃掉余量。

**行的四种态**（稿子只画了「切换进行中」，其余三种由同一套规则推出）

| 态 | 呈现 |
|---|---|
| 普通 | 名称 `model.ink.muted` + 提供商副行 `model.ink.faint` + 行尾星标 |
| 当前生效 | `model.current.fill` 底 + `model.current.border` 描边，名称 600 + `model.accent.ink`，**无徽标**（状态卡已经说了「当前使用」），**无勾选**——高亮本身就是勾选 |
| 切换中（目标行） | 同上，另加「切换中…」徽标（`model.switch.chip` 底）与行尾旋转标 |
| 切换中（原当前行） | 退回中性底，加中性「前次生效」徽标 |

星标与旋转标**同时在场**，不再互相顶替（旧实现切换中星标会消失）。星标视觉 19dp，触达区 32dp ——
稿子只给了 `p-0.5`，在一整行可点的行尾放一个 23dp 的靶子会误触，这一处加大不改变任何像素。

**两种等待标，分工是硬规则**（裁决 2026-09-12，§5.6 的第四个形状）：

| 标 | 用在哪 | 为什么 |
|---|---|---|
| `RunSpinner`（蓝弧 + 25% 淡轨道环，`ui/components/BrandLoader.kt`） | **某个具体对象正在工作**：刷新按钮取目录、正在切换过去的模型行与 chip、推理强度下拉提交中 | 稿子这几处画的都是 `progress_activity` 转圈。会话列表的运行标本来就是这一个，只是过去以四个字面量内联在 `SessionsScreen.kt` 里，现在抽成共用组件 |
| `HermesMark`（品牌 H） | **整页还没有内容**：首次加载「正在加载模型列表…」的 32dp 标 | 它回答的是「app 正在取你要等的东西，屏幕上还没有别的」。把品牌标放到行级等待上，等于在说「加载中」而稿子说的是「这一个在工作」，而且看上去像一枚乱入的 logo |

设置 → 模型 页的顶栏刷新是同一个动作，用同一个 `RunSpinner`。聊天页顶栏与身份选择页不在本节范围内，
仍用 `HermesMark`。

**与稿子的有意偏离**（同样记在 `docs/design/stitch/stitch.lock.json` 的 notes 里）

1. **分组保留折叠**。稿子画的是全展开、无 chevron。搜索被删之后，折叠是长目录里唯一的收敛手段。
   默认展开当前模型所在分组，其余折叠；折叠态用 `rememberSaveable`，不跨启动持久化。
2. **标题栏补回刷新图标**。稿子的刷新按钮有 `aria-label` 却没有图标，渲染出来是空的，判为漏画。
3. **搜索整块删除**（产品裁决 2026-09-12），两处都删。这不是稿子的疏漏，是稿子里 SearchBar 区块
   被清空的结果，照办。
4. **浅色中性色暖化**。稿子的浅色中性取自 Tailwind 冷灰 neutral 阶，§2.1 禁止暖纸上用冷中性；
   逐档换成等明度暖阶，映射表写在 `ui/theme/Tiles.kt` 的 `Model*` 段，逐行记在一致性表里。
   蓝色不参与暖化 —— 禁的是冷中性，品牌蓝就是品牌色。
5. **加载 / 空 / 失败态稿子没画**，沿用既有实现重新着色，不凭空造 UI：首次加载 = `HermesMark` 32dp +
   「正在加载模型列表…」；空 =「暂无可用模型」；目录失败 = `HR-RPC-003` + 重试；
   会话切换失败 = `HR-RPC-004`，弹层不关；设默认失败 = `HR-RPC-005`；改强度失败 = `HR-RPC-006`，回滚。

- 「切换身份」专指 profile；聊天内 Persona 选择叫「切换人格」，不得混用（决策 2026-09-01）。
- 所有用户可见文案走 `localized(language, zh, en)` 双语；错误提示遵循
  `ERROR_HANDLING.md` 的 `HR-<AREA>-<NNN>` 规范。
- **界面语言默认跟随系统**（决策 2026-09-06，实现 2026-09-08）。语言页三项：跟随系统 /
  简体中文 / English，默认选中「跟随系统」。解析规则：系统语言码为 `zh` 用简体中文，
  **其余一律英语**——不是回落到产品第一语言。繁体（zh-TW / zh-HK）按语言码匹配，暂落简体中文；
  繁体翻译另立条目，落地时是在这条规则里加一个分支，不是改这条规则。

  **类型上分两层，不要合并。** `LanguagePreference{SYSTEM,ZH,EN}` 是用户的选择，
  `AppLanguage{ZH,EN}` 是解析后真正用来绘制的语言，约 1000 处 `localized(language, zh, en)`
  只认后者。这与主题同构：`ThemeMode` 有 SYSTEM 档，而 UI 读的是它解析出的布尔值。
  把 SYSTEM 塞进 `AppLanguage` 会给每一个调用点留下一个它处理不了的分支。

  已安装用户中**从未打开过语言页的**（DataStore 无该键）升级后一并转为跟随系统，不写迁移；
  英文手机上的老用户因此会看到界面由中文变为英文，这是有意为之的一次性变化。
  显式选过语言的用户保持原选择。

## 7. UI 改动验证补充（在 `AGENTS.md` 基线之上）

`AGENTS.md` 的测试基线（单测 + assembleDebug + 交接检查）照常执行；UI 改动**额外**要求：

验证分三层，**互不替代**（层级定义见 `AGENTS.md` 的 Android 小节）：L1 JVM+Roborazzi、
L2 真机、L3 模拟器。开工前先问本机具备哪几层，不要假设：

```bash
./scripts/dev/android-capabilities.sh
```

1. 纯函数逻辑（分组、排序、缩字边界）注入 clock/zone 单测钉死边界。
2. **双主题截图（L1 为默认途径）**：浅色 + **系统浅色而应用选深色**（§2.2 的历史 bug 组合）。
   优先用 Roborazzi 在 JVM 内完成 —— 无需设备、CI 亦可跑。原 §7 把这条记为「结构性替代
   （待立项）：扩充覆盖卡片页与会话列表」，实际早已落地（`android/app/screenshots/` 的 golden
   已覆盖卡片页、会话列表、双主题组合与 `fontScale 1.3`），故自本次修订起转为常规途径。
   仅当截图尚未覆盖到该页面时才退回 L3，且须经 `scripts/dev/emulator.sh start` 启动。
   该脚本的稳定规程仍然有效，但**内存档位、是否停 Gradle 守护、构建与启动是否分时不再是固定
   常量**：它们由 `android-capabilities.sh` 按本机内存分档在运行时决定（2026-09-01 定下的那套
   限内存 2048、分时构建的规程，源自当时低内存主机的 QEMU 挂死排障，现作为低配档保留）。
   与主机无关、任何机器都适用的硬规则：禁快照；只用 Pixel 官方镜像（**HONOR 折叠屏 AVD 已整体
   弃用，任何场景不再启动**）；见 "hanging thread" 立即杀掉重来；所有 adb 调用必须显式 `-s`
   指定目标（真机常驻时，裸 `adb` 既会因多设备而失败，也可能把真机的 `boot_completed=1`
   误当成模拟器已就绪）。
3. `fontScale 1.3` 下受限宽度文本完整（长设备名场景，§3.3）。
4. 图标改动：SVG 渲染目检形状（§4.3）。
5. **观感裁决以真机（L2）为准**（§3.1 的 118dp:58dp 实测、跳转气泡描边的淡出时长，都是真机上
   才发现的）；真机验收后才可声称设备验证。两点补充：
   **`targetSdk` 盲区** —— 真机系统版本低于 `targetSdk` 时，`targetSdk` 门控的平台新行为在该机上
   根本不会触发，此时「真机已验」不覆盖这部分，须走 L3 或明示未验。判据是**整个设备集合**：
   只要有**任意一台**达到 `targetSdk` 就不算盲区，与其余几台跑什么无关；`android-capabilities.sh`
   会自动比对并给出 GAP 提示。
   **多台真机时必须写明是在哪台上验的**（写品牌型号与 SDK，不要只写 serial —— 读的人认不出
   serial），笼统一句「真机已验」在多机环境下是有害的含糊。**该在几台上验，按改动性质定**：
   视觉/布局/文案**一台即可**（主题、字号、密度组合 L1 已经覆盖，真机在这里是做最终观感裁决，
   不是充当矩阵）；**通知投递、后台存活、省电清理、权限弹窗必须每个厂商 ROM 都验** —— 荣耀上
   正常推不出小米上正常，这正是多备一台真机的意义；`targetSdk` 门控的平台行为**只需一台达到
   `targetSdk` 的设备**（那是平台行为不是厂商行为，一台达标即覆盖）。
   `ANDROID_SERIAL=<serial>` 指定工具链默认作用的设备。
   **任何一层不可用**（模拟器未装、无真机、主机档位受限）都须在提交信息与交付说明中明示
   （惯例见 0.1.67 提交）。
6. **配色与排版跟设计源的一致性由测试保证，不靠人记**（决策 2026-09-10，排版档 2026-09-11 并入；
   `DesignConformanceTest` + `test/resources/design-conformance.json`）。fixture 分两段：
   `roles` 是颜色（浅/暗两值），`type` 是排版档（字号/字重/行高/字距四元组）。
   测试强制四件事：代码不得偏离自己的记录（颜色与排版各一条）；`design` 与 `impl` 不同的行
   **必须写理由**（偏离允许 —— 对比度下限、CJK 可读性经常逼着偏离 —— 但不许无声偏离）；
   **每个 `StatusTone` 都必须在 fixture 里出现**，新增状态色却没跟设计源对过会直接红。
   起因两次，同一种病：颜色是「正在使用工具」长期解析成 `onSurfaceVariant`，与旁边副行同一个灰，
   正在跑的会话和静止的会话看起来一模一样；排版是行标题的行高、以及状态行借来的 `labelMedium`
   字重字距都跟稿反向 —— 两次都没有任何测试失败，都是用户看出来的。
   **改设计时先改 fixture**，那份 diff 就是这次改动的评审记录。
7. **自动化覆盖不到的用例写进 `docs/ANDROID_SMOKE.md`**（决策 2026-09-10）。判定标准是两条同时
   成立：JVM 测试与 Roborazzi 都够不着（需要真实数据、真实网关状态，或本地 mock 造不出的运行时
   相位），且**验不到会让人误判**（结论已经写进本文档，却从未在屏幕上确认过）。
   每条必须写明"为什么自动化不了" —— 没有理由的条目会退化成永远不做的待办。
   "还没写测试"不属于此列，那种情况去写测试。
8. **Stitch 基线与拉取规程**（决策 2026-09-11，`docs/design/stitch/`）。第 6 条的 fixture 记的是转录值，
   转录会过期而不自知；本条给它一个可以核对的原件，并规定原件怎么更新。
   - **Stitch 是工作台，仓库是合同。** 代理对 Stitch **只读**；写入（改稿、推设计系统）只在用户明确
     要求时做，且**每次写入前把内容给用户过目**。
   - **设计系统反向同步是一条有测试的链**（决策 2026-09-11）：载体是 `docs/design/stitch/design-system.md`
     （Stitch 的 designMd 格式：front matter 放浅色角色与排版档，正文放浅暗双档角色表、状态色表与
     硬规则 —— 被否定的方案在这里写成「应当如何」的正向规则）。`DesignSystemExportTest` 钉住它与
     `Color.kt` / `StatusColors.kt` / `Tiles.kt` / `Type.kt` 逐值相等，漂了构建就红；
     `scripts/design/stitch-design-system.mjs` 把它确定性地转成 MCP 载荷（`--summary` 给人看、
     `--payload` / `--base64` 给机器用、`--rules` 取正文、`--check` 核对锁文件）。推送**只创建新的设计
     系统、不覆盖设计师已有的**，推送后把 assetId 与哈希记进锁文件 `designSystem`。
   - **这条通道只承载 token，正文规则进不去**（实测 2026-09-11，首次推送后逐字回读，证据在锁文件的
     `designSystem.pushFidelity`）。`create_design_system_from_design_md` 保住了 13 档排版与
     front matter 原文，但**把 123 行正文规则整段丢弃**，把 `theme.spacing` 换成通用七档，把名字英译成
     「Warehouse Baseline」，丢掉 `overrideNeutralColor`（暖纸就是它给的），还前置了一段自己按种子色
     重推的 M3 YAML、改掉 7 个角色值。`update_design_system` 对每一个载荷（含最小载荷）都返回
     invalid argument，**无法据此修正**。两条推论写进规程：
     ① 漂移检查只比 front matter 的哈希（`frontMatterSha256`），改正文不算漂移 —— 它本来就没出过门；
     ② **组件硬规则随每次生成的 prompt 传入**，用 `--rules` 取（它会剥掉面向仓库的那几段），
