# 登录流程：全屏登录页、失效重登与切换账号

> 状态：把已经能跑的邮箱验证码登录做成完整产品流程的需求整理，供产品、设计和开发使用。
> 范围：Android `com.hermes.remote` 的登录页、登录后的选 Mac 页，以及「设置 > Hermes GO 账号」
> 里的退出与切换账号。中文为默认语言，所有文案需具备中英文版本。
> 本文**不授权**改变 Gateway 的任何 REST 契约、`AccountApi.kt` / `AccountDtos.kt` 的请求响应结构，
> 也不新增 `HR-*` 错误码。视觉以 `docs/DESIGN.md` §5.19 为准，行为约束以 §5.0 为准；
> 本文与两者冲突时，以 `DESIGN.md` 和代码为准。

## 1. 目标与边界

邮箱验证码登录（`POST /v2/auth/email/challenges` → `/exchange`）在 0.1.x 已经可用，用户不再需要
填 Relay 地址和 App Token。但**登录作为一个产品流程还没成型**，缺的是三件事：

1. **登录界面不是一个页面。** 它是 `ui/account/AccountDevicesScreen.kt` 里的一段
   `SignInContent`，和「选择 Mac」「兼容连接 / 旧版 Relay·App Token」「打开诊断」挤在同一个
   可滚动列里。同一个 Composable 靠 `onBack == null` 和 `accountOnly` 两个布尔开关，兼任首次
   登录、设置-账号、远程设备三种角色。没有品牌区，没有 §5.12 的底部主按钮。
2. **「从未登录」和「登录失效」长得一模一样。** 失效原因在 `AccountSessionManager` 里被用来做
   判断（`INVALID_SESSION_CODES`），但**没有被保存下来**——落盘的只有一个布尔
   `account_reauthentication_required`。所以重新登录时，App 知道"要重登"，却说不出"为什么"。
3. **设置-账号只能退出，不能切换。** `startNewAccountSignIn()` 这个方法已经存在，但只接在
   "账号已删除"的终态页上。

目标是补齐这三件，并把入口收敛成一句话：**打开 App 就检查，失效就全屏挡住，设置里能主动重来。**

**明确不做**（详见 §9）：多账号并存、Google/Apple 登录、改动任何服务端契约、新增错误码、
重构 `AccountDevicesViewModel` 的状态机。

## 2. 一条贯穿全文的分界：意外失效 vs 主动退出

这两者在技术上都是"本地没有可用会话了"，但对用户是两件完全不同的事，所以**呈现方式必须不同**：

| | 意外失效 | 主动退出 / 切换账号 |
|---|---|---|
| 起因 | 服务端拒绝（过期、撤销、凭据重放） | 用户自己点的 |
| 用户是否知情 | 不知道，需要被告知原因 | 知道，不需要解释 |
| 是否显示原因横幅 | **是** | **否** |
| 导航栈 | **保留**，登录成功后回到失效前那一页 | 清空，登录成功后走完整首次流程 |

实现上这条分界**不需要额外的状态机**：它正好等于"加密落盘的重登门禁里有没有原因码"。
意外失效路径写入原因码，显式 `signOut()` 不写。下文 §4 和 §5 都建立在这条分界上。

## 3. 入口与呈现

### 3.1 入口表

| 入口 | 触发条件 | 呈现方式 | 登录成功后去向 |
|---|---|---|---|
| 冷启动 · 从未登录 | 无账号会话、无重登门禁、无旧版配置 | 起始导航目的地 | 选 Mac → 会话列表 |
| 冷启动 · 登录已失效 | 加密门禁「需要重新登录」为真 | 修复目的地，**带原因横幅** | 选 Mac → 回原页面 |
| 运行中失效 | 传输层判定需要重新登录 | 压在当前栈上的修复目的地，**保留导航栈**，带原因横幅 | 选 Mac → **回失效前那一页** |
| 设置-账号 · 退出这台手机 | 用户主动 | 导航目的地，清栈，**无**横幅 | 选 Mac → 会话列表 |
| 设置-账号 · 切换账号 | 用户主动 | 同上 | 同上 |

### 3.2 保留导航栈的机制已经存在，不要再造一个

这一条在动工时查证后更正过。**现有代码并不像预想的那样在会话失效时清栈**：

- `shouldReplaceStackWithSetup(...)` 里的 `popUpTo(0)` 带着 `!accountRepairRequested` 这个前提，
  账号失效时它返回 false，根本不会执行——现成的单测就叫
  `accountRepairPreservesTheCurrentNavigationStack`。
- 账号修复走的是另一条路：`nav.navigate("setup") { launchSingleTop = true }` 压栈，修复完成后
  `nav.popBackStack("setup", inclusive = true)` 弹回被打断的那一页。

这正是 §5.0 要求的「原页面上的临时目的地」。所以**本轮不新增覆盖层**：再加一层全屏遮罩等于给
同一件事造第二套机制，还会和已经压栈的登录页同时出现。清栈只保留给它本来就该管的那件事——
用户主动退出（那时 `accountRepairRequested` 为假，栈该清空）。

判断「显不显示原因横幅」因此不依赖任何导航状态，只依赖一件事：门禁里有没有原因码。
见 §4。

### 3.3 旧版 Relay 与诊断去哪了

登录页上不再有「兼容连接」分区。这两个入口降级为页脚的一行次要文字入口（「其他连接方式」），
点开后才出现旧版 Relay / App Token 与诊断。理由：它们是迁移期的兼容出口和排障出口，不是登录
流程的一部分，放在主路径上会让第一次用的人以为自己得在两种登录方式之间做选择。

但**不能删掉**。`DESIGN.md` §5.0 规定旧版连接保留在「远程设备 > 旧版连接」兼容入口，按迁移
测试门禁逐步退场；而且登录失败时，老用户需要一个当场自救的口子。

`legacy_setup` 与 `settings_connection` 两条路由本轮不动。

## 4. 登录失效的原因说明

### 4.1 四个码到横幅文案

文案**全部取自现有 `accountErrorText()`**，不新造，也不新增错误码：

| 码 | 服务端条件 | 中文 | English |
|---|---|---|---|
| `HR-AUTH-003` | 会话过期且无法刷新（refresh 绝对有效期 30 天到期），或令牌无法识别 | 登录已过期，请重新登录。 | Your session expired. Sign in again. |
| `HR-AUTH-004` | 会话或 refresh 家族被撤销（别处退出、撤销该安装、revoke-all） | 这台手机的登录已被撤销，请重新登录。 | This phone's session was revoked. Sign in again. |
| `HR-AUTH-005` | 轮换后的 refresh 被重放，整个家族已吊销 | 为保护账号，这台手机已安全退出。 | This phone was signed out for account safety. |
| `HR-BIND-004` | 这台手机的 installation 被撤销 | 同 `HR-AUTH-004` | 同上 |

服务端把「过期」和「令牌无法识别」**故意合并**成 `HR-AUTH-003`（不给令牌探测留探针），所以
客户端也不去区分——横幅只说"登录已过期"。

WebSocket 握手被拒时只有 HTTP 状态码、没有错误码体；`401` 按 `HR-AUTH-003` 记。

### 4.2 横幅的样子与行为

- 位置：品牌组下方、邮箱输入框上方。**中性容器 `surfaceContainer` + `colorScheme.error` 文字**，
  不是填充的 `errorContainer`——那是给用户刚刚操作失败准备的，而这条说的是用户没做错、也无法
  在此处补救的状态；深色下整块饱和红对着一个只需要重填邮箱的人，是在喊。§5.11 的失败态早就
  为同类消息定了这个形状。
- 错误码 `HR-*` **单独一行**，`labelSmall`，次要色——与 §5.11 失败态同一条规矩。
- **横幅没有重试按钮。** 这四个码在 `docs/ERROR_HANDLING.md` 里全部登记为不可重试，
  §5.0 规定不可重试错误不显示可执行的重试入口。横幅只是说明"你为什么在这一页"，
  用户要做的事就是下面那个表单。
- 横幅在**这次登录成功后消失**，不因为切页、切换邮箱或重发验证码而提前消失——它描述的是
  上一段会话怎么结束的，不是当前这次操作的结果。
- 操作失败产生的错误（发码失败、验证码错）仍然走**现有的错误卡**，位置在表单下方，与横幅
  并存且互不替代。两者语义不同：一个是"你为什么被登出"，一个是"你刚才这一下没成功"。

### 4.3 什么不写原因

- 显式 `signOut()`（退出这台手机、切换账号）——用户自己点的，不解释。
- `HR-AUTH-006`（敏感操作需要近期验证）——§5.0 明确它不是会话失效，不得清除账号登录，
  自然也不进这个门禁。
- `HR-BIND-011`（这台 Mac 不可用）——是设备路由问题，走选 Mac 页，不是登录问题。
- `HR-ACCOUNT-012`（账号正在永久删除）——已有独立终态页（`ACCOUNT_DELETION_COMMITTED`），
  行为不变。

## 5. 登录页

### 5.1 页面状态

| 状态 | 必须呈现 | 恢复行为（进程重建 / 重新进入） |
|---|---|---|
| 能力发现中 | 加载行「正在检查账号服务…」 | 重新发现 |
| 输入邮箱 | 品牌组、（可选）原因横幅、邮箱输入框、底部「发送验证码」 | 邮箱输入可保留 |
| 已发码 | 上述 + 6 位验证码框 + 到期倒计时 + 重发（带冷却）+「更换邮箱」；底部按钮变「验证并登录」 | 只恢复**尚未到期**的加密挑战；**始终清空验证码输入**；倒计时按绝对时间重算 |
| 服务不可用 | `HR-AUTH-011` 说明，「发送验证码」禁用，页脚兼容入口仍可用 | 重新发现 |
| 账号删除终态 | 现有 `ACCOUNT_DELETION_COMMITTED` 页，含「使用其他邮箱账号」 | 不变 |

这张表里除了品牌组、横幅和底部按钮，其余全部是 `AccountDevicesViewModel` 已有并已测的行为
（`AccountStage`、`codeExpiresInSeconds`、`resendInSeconds`、`startOver()`、`resendCode()`）。
**本轮只搬 Composable，不动这个状态机**——它承载着挑战绝对时间、交换幂等键和重试动作分发，
拆它的风险远大于收益。

### 5.2 沿用 §5.0 的硬约束（此处只作提醒，权威在 DESIGN.md）

- 倒计时只在页面可见时运行，重新进入按绝对时间重算；客户端倒计时只是交互门禁，服务端才是
  到期、冷却、尝试次数和重放的最终权威。
- 「更换邮箱」与「重新发送验证码」是**两个独立操作**，前者清除当前挑战。
- 挑战到期或时间字段无效 → 立即清除挑战并显示 `HR-AUTH-009`，不得提交已知过期的验证码。
- 验证码只存在输入状态，**不得进入日志或诊断**；挑战、幂等键、令牌、安装实例 ID 进加密存储。
- 错误卡的「重试」必须重做**实际失败的那个操作**，不得退化为刷新页面。

### 5.3 服务端行为决定的两个细节

- **重发冷却期内再点，服务端返回的是同一个挑战**（`EMAIL_OTP_RESEND_COOLDOWN_MS = 60s`，
  冷却内不会真的再发一封信）。所以冷却结束前重发按钮必须**禁用**，不能让用户点一下、
  拿到 202、然后等一封永远不来的信。
- **所有验证码失败都是 `HR-AUTH-009`**：格式错、不匹配、已过期、已用过、投递失效、
  尝试次数用尽（上限 5 次），服务端一律返回同一个码。所以登录页**说不出**"你输错太多次了"
  和"验证码过期了"的区别，只能用本地的 `expiresAt` 提前把过期挡掉。这是服务端刻意的设计，
  不要试图在客户端猜。

### 5.4 邮箱格式

沿用现有 `AccountDevicesViewModel.looksLikeEmail()` 作为按钮可用性门禁。服务端对语法非法的
邮箱返回 `400 HR-ACCOUNT-004`（"invalid account request"），语义很宽，直接展示对用户没有帮助
——所以本地门禁要挡在前面。**本轮不为此新增错误码。**

## 6. 选 Mac 页

从登录页拆出，成为登录成功后的独立页面。行为**完全沿用**现有 `DeviceContent` / `DeviceCard`：
空态引导、页面可见时每 5 秒自动发现、发现唯一可用 Mac 自动选择并端到端探测、多台时等待用户
选择、`HR-BIND-011` 清除失效选择。

`DESIGN.md` §5.0 规定「手机端不新增"连接与设备"入口」——卡片页的「远程节点」卡是唯一的绑定
入口，设置页不重复显示远程设备。所以拆出来的这个页面是**同一份内容的两个宿主**：登录流程里的
一步，和「远程节点」详情页。不是第三个入口。

## 7. 设置 > Hermes GO 账号

页面结构（`accountOnly` 分支）：

```
┌──────────────────────────┐
│ 账号卡                    │
│   显示名 / 邮箱           │
│   本机：<安装名>          │
├──────────────────────────┤
│ [切换账号]        ← 新增  │
│ [退出这台手机]            │
├──────────────────────────┤
│ 危险操作（能力门控）       │
│   永久删除账号            │
└──────────────────────────┘
```

- **切换账号 = 先退出，再登录。** 复用现有 `vm.signOut(onFinished)`，完成后清栈进登录页，
  不带原因横幅。本地只保留一套令牌。二次确认弹窗必须说清"会先退出当前账号"，不能让用户
  以为是无损切换。
- **退出这台手机** 行为不变，弹窗文案不变（"只会撤销这台手机的登录。其他手机、Desktop 和
  Mac 连接不会受影响。"）。
- 危险区（永久删除账号）行为、文案、能力门控**全部不变**。
- **未登录时进入本页**（还留着可用旧版连接的手机就能走到这里）显示一张「还没有登录 Hermes GO
  账号」的卡片加一个「登录」按钮，跳到登录页。设置页**不得再长出第二个邮箱表单**——全 App 只有
  一个登录页。

**一个已知隐患，本轮不修但记在这里**：`AccountApi.signOut()` 打的是
`DELETE /v2/installations/current`，它在 Gateway 侧受 `ACCOUNT_BINDING_ENABLED` 门控，
关闭时返回 `503 HR-BIND-008`；而 `POST /v2/auth/sign-out` 不受该门控。也就是说在只开了
`ACCOUNT_AUTH_ENABLED`、没开 binding 的部署上，退出和切换账号都会失败。换端点属于契约面改动
（`docs/INTEGRATION.md` 🟡），需要同分支交代 Gateway 与 Desktop 两侧，不在本轮范围。

## 8. 错误码

**一个都不新增。** 复用并全部已在 `docs/ERROR_HANDLING.md` 登记：

| 代码 | 本文用在哪 |
|---|---|
| `HR-AUTH-003` | 失效原因横幅（过期 / 令牌不可识别 / WS 握手 401） |
| `HR-AUTH-004` | 失效原因横幅（被撤销） |
| `HR-AUTH-005` | 失效原因横幅（凭据重放） |
| `HR-BIND-004` | 失效原因横幅（本机安装被撤销） |
| `HR-AUTH-009` | 验证码无效/过期（错误卡，非横幅） |
| `HR-AUTH-010` | 登录邮件发送失败（错误卡，可重试） |
| `HR-AUTH-011` | 此 Relay 未启用邮箱登录（服务不可用态） |
| `HR-ACCOUNT-002` | 账号服务不可用（错误卡，可重试） |
| `HR-ACCOUNT-012` | 账号删除终态页 |
| `HR-BIND-011` | 选 Mac 页，设备不可用 |

已知的两个表达缺口，**本轮接受，不补码**：邮箱语法非法（服务端只给 `HR-ACCOUNT-004`，靠本地
`looksLikeEmail()` 挡）、验证码尝试次数用尽（服务端刻意折叠进 `HR-AUTH-009`）。

## 9. 验证

### L1（JVM + Roborazzi，必跑）

- **`shouldOverlaySignIn` 逐条单测**——三个布尔的八种组合。这是本文最容易实现走样的地方：
  少一位就会变成"冷启动失效也盖覆盖层"（底下是空导航树）或"主动退出也盖覆盖层"。
- **原因码落盘**：四条失效路径（refresh 失败、REST 401/`INVALID_SESSION_CODES`、WS 握手 401、
  `HR-BIND-004`）各自写入正确的码；**显式 `signOut()` 不写**。
- **导航**：运行中失效不清栈；主动退出清栈；`legacy_setup` / `settings_connection` 路由未受影响。
- **`shouldReplaceStackWithSetup` 既有断言保持绿**——它是"主动退出清栈、账号修复不清栈"这条
  分界的唯一守门人。
- **截图 golden**（`SignInScreenshotTest`，落在 `app/screenshots/`）：`signin.default.{light,dark}`、
  `signin.code-sent.light`、`signin.expired-banner.light`、`signin.revoked-banner.dark-fs13`、
  `signin.unavailable.light`、`signin.code-sent.en-fs13`。其中深色金图在浅色 Robolectric
  qualifier 下渲染，正是 §7 要求的「系统浅色 + 应用深色」组合。
- **`fontScale 1.3`**：横幅两行文案 + 错误码行、底部按钮文字、「更换邮箱」/「重新发送」两个
  并列动作——这三处最容易在放大后挤爆，`signin.revoked-banner.dark-fs13` 一张图同时覆盖。
- `DesignConformanceTest` 只记录 `Color.kt` / `StatusColors.kt` / `Type.kt` 的取值，本轮没有新增
  主题字面量，**不需要动** `design-conformance.json`。

### L2（真机，必跑，且必须写明是哪台）

`DESIGN.md` 规定观感争议在真机上定，不在模拟器上定。最少走通：

1. 全新安装 → 登录页 → 收码 → 登录 → 选 Mac → 会话列表。
2. 设置-账号 → 退出这台手机 → 确认走清栈路径、**无**原因横幅。
3. 设置-账号 → 切换账号 → 换一个邮箱登录 → 确认旧账号数据不串。
4. 在聊天页时从另一端撤销这台手机的登录 → 确认登录页**压在栈上、带原因横幅**，重新登录并选完
   Mac 后**回到那个聊天页**，而不是会话列表。
5. 页脚「其他连接方式」→ 旧版 Relay 与诊断仍可达。
6. 深浅两色下看登录页最终观感。
