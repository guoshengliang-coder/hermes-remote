# Desktop 组件化安装计划

> **历史设计记录。** 2026-09-22 起，新 v2 发布固定为 `node_runtime` + `connector`；Hermes
> 使用本机标准安装。捆绑 Python/Hermes、按需组件运行时、补丁集与 schema drift 检查已退役。
> `installPhase` / `onDemandTrigger` 等字段只为严格解码和验签已发布的 0.4.0/0.4.1 清单而保留，
> 不再驱动安装或界面。删除实现的提交见本次 HG-97/HG-98/HG-99 PR 的实现提交（合并前由
> 后续记录补入确切 hash）。下文 C1–C5 设计保留作历史依据，不代表当前发布拓扑。

## 目标

Desktop 在安装 Hermes Server 与 Connector 前先完成环境预检。已存在且通过身份与健康验证的
组件直接复用；缺失的基础组件自动下载；浏览器、语音和文档能力在首次使用时再下载。目标体积为：

- Desktop 引导程序约 2 MB；
- 已有完全匹配环境的机器，首次额外下载不超过 20 MB；
- 全新机器达到基础聊天可用，首次额外下载不超过 100 MB；
- 后续 Server 与 Connector 常规升级控制在 20 MB 以内。

这些数字是设计预算，不是发布声明。必须以候选包的实际字节数和安装后占用作为放行依据。

## 为什么不能只检查版本号

Homebrew、pyenv 和用户虚拟环境均可在 Desktop 之外被修改。`Python 3.11.15` 只能说明解释器
版本，不能证明 ABI、原生库、Python 包或补丁内容与发布版本一致。组件复用分为两类：

1. **精确内容复用**：Python、Node、Hermes 核心和 Connector 必须匹配签名清单中的内容身份，
   并通过最小运行探针；
2. **兼容合同复用**：系统浏览器等外部能力必须匹配清单声明的兼容合同，并通过受限健康探针。

每个可下载组件始终带有受管内容 SHA-256。兼容合同只增加外部环境的复用途径，不替代下载后
组件的精确身份；因此系统浏览器不兼容或不存在时，受管浏览器仍可按同一需求下载并精确复用。

检测到但无法证明兼容的用户环境只用于说明本机状态，不作为安装输入，也不修改它。

## 目标布局

```text
~/Library/Application Support/Hermes Go/Managed/
├── components/
│   └── <component>/<content-identity>/
├── releases/
│   └── <release>/
├── references/
├── capability-references/
│   └── <release>/<optional-component>.json
├── state/
├── secrets/
└── current
```

组件目录不可变并按内容身份寻址。版本目录只包含轻量业务代码、入口包装器和指向已验证组件的
引用。激活仍通过现有 `current` 原子切换；迁移日志同时记录版本与组件身份，回滚因此不会依赖
当前 PATH、Homebrew 状态或后来下载的功能包。

## 安装顺序

1. 下载并验证签名清单，不创建进程、不写凭据；
2. 读取受管组件收据，并对允许复用的外部能力运行受限探针；
3. 展示复用项、缺失项、首次下载字节数和以后按需下载字节数；
4. 下载缺失的基础组件，逐个校验大小、SHA-256、归档边界和内容身份；
5. 以不可变目录提交组件收据，再组装轻量 Server/Connector 版本目录；
6. 进入现有的二次确认、Hermes-first 启动、绑定、端到端验证和回滚事务；
7. 首次调用可选能力时，再走同一套签名、下载、校验和原子提交流程。

自动下载必须在界面上提前展示总字节数、进度和失败恢复动作。取消或失败只能删除当前 UUID
工作区，不能删除正在被当前版本或回滚版本引用的组件。

## 签名清单 v2

现行 schema v1 恰好包含 `hermes_server` 与 `connector` 两个完整归档，继续保留用于已发布的
0.3.x 回滚。v2 增加独立组件条目，每项至少签名固定：

- 组件种类、语义版本、架构和安装阶段；
- 下载 URL、文件名、压缩字节数、SHA-256 与解压内容身份；
- `exact_content` 或 `verified_compatibility` 复用政策；
- 兼容合同标识、入口点和依赖的组件身份；
- 是否为基础启动必需，以及按需触发能力。

Desktop 对未知字段、未知组件、重复组件、循环依赖和未签名的复用政策继续 fail closed。Cloud
能力声明需要增加对应运行合同；生产仍保持 v1，直到 v2 候选通过完整门禁。

## 分阶段实施

### C1：预检决策核心

- 建立组件需求、候选、复用政策和安装阶段模型；
- 只有精确内容身份或明确兼容合同加健康探针可以复用；
- 计算首次下载与以后按需下载字节数；
- 保持现有 v1 下载、安装和生产能力不变。

### C2：组件探测与受管仓库

- owner-only 收据、不可变组件目录和引用计数；
- 受管组件精确身份检查；
- 系统浏览器兼容探针；
- 损坏收据、符号链接、架构错误和并发安装回归。

C2 的第一批只读实现已经定义规范化内容身份：相对路径、文件字节和可执行位共同进入
SHA-256；符号链接、特殊文件、越界树、非 owner 安全收据、摘要篡改和失败健康探针都不能成为
可复用候选。每个内容身份目录将 `content/` 与 `receipt.json` 一起原子提交，版本引用另以 owner-only
文件幂等记录，避免断电后出现只有组件或只有收据的可见状态。垃圾回收与系统浏览器探针仍留在
C2 后续批次。

外部环境扫描只读取固定路径。Python 与 Node 的版本结果用于说明本机状态，不能代替完整内容身份；
Homebrew 的 Python/Node 符号链接只解析到安全目标做状态报告，不因此获得复用资格。系统
Chrome/Chromium 只有在常规文件、owner、权限、架构、输出有界的版本探针、签名清单兼容合同和
Desktop 明确实现的兼容健康探针全部匹配时才成为复用候选；健康探针未接入或未知合同默认拒绝。

垃圾回收的第一步只生成快照计划，不删除文件。计划严格验证全部引用、组件路径、owner、权限、
收据和实际内容身份；当前版本与回滚版本的引用缺失时整体拒绝。未知组件、损坏引用或引用指向
缺失组件同样整体拒绝。后续删除器必须持有安装操作锁，并在删除精确候选路径前重算出相同快照。

### C3：签名清单 v2 与下载器

- 发布器、独立验证器、Desktop 验签和下载器同时采用 v2；
- 支持断点恢复，但最终文件仍需完整大小与 SHA-256 校验；
- v1 只用于已安装版本观察与回滚，新 v2 与旧 v1 不混装。

C3 的本地合同实现已经加入独立的 v2 发布与验证命令。每个条目签名压缩包摘要、解压内容身份、
启动/按需阶段、复用合同、入口点和按内容身份固定的依赖；发布器和独立验证器都会安全解压候选并用
与 Desktop 组件仓库相同的路径、文件字节和可执行位算法重算内容身份。Desktop 验签后直接生成 C1
预检需求，并拒绝未知字段/组件、重复组件、依赖身份错配、循环依赖和不一致的阶段或复用合同。
组件下载器只接受同源验签后的 HTTPS URL；中断留下 owner-only 部分文件，下次用精确 Range 继续，
最终仍重新读取完整文件校验签名字节数和 SHA-256 后才暴露正式文件名。以上入口保持 default-inert，
没有替换生产 v1 清单、现行安装事务或任何线上能力。

### C4：轻量 Server/Connector

- Hermes 核心代码与 Python 运行时/依赖分离；
- Connector 构建为无需外置 Node 的原生或单文件产物；
- Playwright、语音/ONNX、PDF/文档依赖改为延迟加载；
- 缺少按需组件时返回结构化错误和安装动作，不暴露原始异常。

C4 第一批本地构建合同已经把原来的两个整体归档拆成四个 schema-v2 输入：
`python_runtime` 独占 CPython 与基础 `site-packages`，`hermes_core` 只保留上游源码、启动器和私有
会话令牌读取器，`node_runtime` 只保留经过版本/架构核验的 Node 可执行文件，`connector` 只保留
生产 JavaScript、Protocol 和 `ws`。Hermes 与 Connector 启动器从 Desktop 激活配置取得绝对的
运行时组件根目录，组件仓库本身保持只读；Python 的 `.pth` 通过激活时的核心根目录恢复子进程导入，
继续覆盖 HG-28。构建结果直接给出每包压缩大小、压缩 SHA-256、规范化内容 SHA-256 和依赖边，能直接
填入 C3 清单。这个入口仍为本地 default-inert 候选，不改变 v1 安装器。

第一批刻意完整保留现有基础 Python 依赖。浏览器、语音/ONNX、PDF/文档依赖必须先建立启动期和首次
调用回归测试，再从 `python_runtime` 移入按需组件；仅凭包名裁剪会把隐式导入故障推迟到用户会话中。

2026-09-13 用当前受管 0.3.4 的完整 Python/Node 输入、Hermes `f159e581` 和本分支 Connector
进行了一次未签名、未发布的 arm64 实测：Python 运行时 267,275,980 bytes（254.89 MiB），Hermes
核心 17,762,189 bytes（16.94 MiB），Node 36,999,103 bytes（35.29 MiB），Connector 57,789 bytes
（0.06 MiB），基础合计 322,095,061 bytes（307.17 MiB）。这证明常规 Hermes/Connector 更新已经能
只下载约 17 MiB/56 KiB，也证明完整 Python 输入仍混入 Playwright、语音/ONNX、Google 与文档树，
必须完成下一批按需拆分才能达到全新机器基础聊天不超过 100 MB 的目标。

同日从同一 Hermes commit 的锁文件重新生成“无 extras、无 dev”的 62 包核心环境后，Python 归档降为
48,062,721 bytes（45.84 MiB），四个基础归档合计 102,881,798 bytes（98.12 MiB）。解压后的组合候选
通过了 `hermes --help`、OpenAI/FastAPI/Hermes 核心导入、清除 `PYTHONPATH` 后的子进程
`tui_gateway` 导入、自包含 Node 启动、Connector 模块加载，以及真实 `hermes serve --skip-build`
启动与 `/api/status` 请求；服务报告 `HERMES_BACKEND_READY` 和版本 0.21.0。由此首装体积目标已在
arm64 本地候选上成立。Playwright、语音/ONNX、Google 等 extras 后续进入各自的签名按需组件，不能
重新混入基础环境；PDF 提取当前仍是上游核心依赖，移出前需要上游调用边界配合。

C4 第二批把四包从构建产物推进到 Desktop 的只读激活计划。Desktop 只从签名清单指定的
`components/<kind>/<content-sha>/content` 解析入口；计划生成前重新核对 owner-only 收据、整树内容
身份、入口的普通文件/owner/权限/可执行位和调用方健康探针。基础拓扑固定为 Python 与 Node 无依赖、
Hermes 精确依赖 Python、Connector 精确依赖 Hermes 与 Node，缺包、额外基础包或依赖身份偏离都会
整体拒绝。生成的 LaunchAgent 为 Hermes 注入精确的 `HERMES_PYTHON_RUNTIME_ROOT`，为 Connector
注入精确的 `HERMES_NODE_RUNTIME_ROOT`；v1 写入器拒绝这两个 v2 字段，v2 写入器也会再次确认路径
确实位于当前受管根的内容身份目录，并在落盘 LaunchAgent 前再次重算相关组件身份。该入口仍未接到
现行安装按钮或启动事务。

C4 第三批把上述原语串成默认关闭的本地安装事务。安装入口只接受严格 Ed25519 验签器产生、调用方
无法自行构造的清单令牌；按 Python、Node、Hermes、Connector 的依赖顺序逐项精确复用或下载，继续
复用同一套 tar 越界/链接/特殊文件检查，再将内容与收据原子提交。四项全部重新核验并形成激活计划
后才写版本引用；中途失败只留下已提交但未引用、可由后续 GC 处理的内容。普通失败清理本次 UUID
工作区；只有网络传输中断保留 partial 和 owner-only `install.json`，同一 UUID 只有在规范化签名清单
身份完全相同时才能续传。完成后仍只返回激活计划，不写凭据、不切 `current`、不操作 launchd。
取消重试可通过同一安装器的受限清理入口删除带有效 marker 的精确 UUID 工作区。

C4 第四批为首次使用下载补上不可变引用合同。可选组件只有在所属基础版本引用已经存在、受管内容
重新核验通过后，才能写入 `capability-references/<release>/<kind>.json`；每个版本与组件种类只能
绑定一个内容身份，重复写入必须完全相同。垃圾回收把基础引用和按需引用一并纳入只读快照，允许
多个版本共享同一内容，并对孤立版本目录、未知组件种类、非 owner 安全文件、损坏 JSON 或缺失内容
整体 fail closed。该批只建立后续按需安装器所需的持久化与回收边界，不触发下载或激活。

C4 第五批完成默认关闭的首次使用安装事务。入口只接受严格验签产生的 v2 令牌和签名清单中的
`onDemandTrigger`；任何外部扫描、工作区写入或网络请求前，先要求对应基础版本引用存在，并通过
GC 快照和激活计划重新核验四个基础组件。触发项及其按需依赖按拓扑顺序处理：健康的精确受管内容
直接复用，系统浏览器必须再次通过固定扫描结果及路径、owner、权限、架构和兼容探针验证，其余项
沿用断点下载、安全解压、内容身份核验和原子提交，全部成功后写入逐组件引用。传输中断只保留绑定
精确清单与触发能力的 owner-only UUID 工作区；其他失败清理该工作区，受限取消也只接受有效 marker。
成功结果仅返回受管根目录或系统浏览器入口，不改凭据、`current`、LaunchAgent 或进程。

C4 第六批把已经分离好的浏览器、语音和文档内容根接入 schema-v2 归档构建器。构建器固定三种可选
类型、首次使用触发器、复用合同和依赖边：语音/文档只能精确依赖 Python，只有浏览器可声明系统兼容
复用；所有输入继续经过大小、条目、链接和敏感文件过滤，并在任何归档产生前通过可执行健康入口检查。
输出分别统计基础下载和延迟下载，并给每个可选包生成可直接交给签名发布器的压缩哈希与规范化内容
身份。该批让真实依赖树可以独立发布，但仍保持默认关闭。

C4 第七批把已验证的可选内容接入上游现有运行时合同。Desktop 用受管 Python 可执行文件探测实际
X.Y 与扩展 ABI，把语音和文档组件的 `site-packages` 按稳定顺序写入内容寻址、只读的 `.pth` 投影，
并把该目录作为 `HERMES_LAZY_INSTALL_TARGET` 注入 Hermes LaunchAgent；浏览器入口则通过
`AGENT_BROWSER_EXECUTABLE_PATH` 注入。投影只接受当前用户拥有、不可由 group/world 写入且没有符号
链接的受管内容，重复写入必须逐字节一致；系统浏览器仍只接受前序兼容探针解析出的安全普通可执行文件。
该原语保持默认关闭，不写 LaunchAgent、不操作进程；下一批要在首次安装事务成功后原子更新运行环境、
受控重启 Hermes，并只重试一次原能力调用。

C4 第八批完成默认关闭的受控激活事务。它复用迁移操作锁，只允许与 `account_active` 日志版本一致、
且受管 Connector/Hermes 均已加载的基础版本进入；调用方必须提供包含本次安装结果在内的完整活动可选
组件集合。事务先生成投影并原子替换 Hermes LaunchAgent，只重启 Hermes，再用新日志 readiness 标记和
loopback HTTP 双重证明确认新运行时。任一步失败都会恢复逐字节保存的旧 plist；若 Hermes 已经停过，
还必须重新启动并证明旧运行时健康，否则进入 rollback failure。成功后原能力闭包只执行一次，其自身
失败不会撤销已经健康的组件安装。现行安装按钮与线上 Hermes 请求还没有接入该事务；下一批需要从
能力缺失信号构造完整活动集合，并把触发入口接到这一默认关闭的协调器。

C4 第九批补上完整可选组件集合的只读解析边界。解析器只接受验签器令牌与本次安装器的完整触发闭包，
先对共享仓库执行 fail-closed 快照，再逐项读取当前基础版本的 `capability-references`，要求每个内容身份
仍与签名清单一致，并重新核验 owner-only 收据、整树哈希、入口权限和健康探针。因此后装浏览器时不会
把先前已安装的文档能力从 Hermes 环境中移除。系统浏览器没有受管内容引用，只有当当前 Hermes
LaunchAgent 的精确路径再次通过签名兼容合同和固定扫描时才会被保留；浏览器已移动、权限变松或兼容
探针失效都会在进程变更前拒绝。激活器在取得迁移操作锁并确认服务拓扑后调用该解析器，外部调用方不再
直接提交组件路径。线上缺能力信号仍未接入；下一批先用固定能力类型串起签名触发器、安装与激活。

C4 第十批把固定能力类型接到完整的首次使用事务，但仍保持默认关闭。调用方只能选择 browser、speech
或 document，协调器从验签清单读取该类型的精确 `onDemandTrigger`，生成独立 UUID 工作区，调用按需
安装器，随后重新生成四个基础组件的激活计划，再进入受锁的 Hermes 激活和单次原能力重试。签名清单
不含该能力时不创建工作区、不下载、不规划也不激活；安装失败同样不会触碰 LaunchAgent 或服务；同一
协调器的并发请求只允许首个运行。当前 Hermes 0.21.0 尚不产生可供 Desktop 使用的结构化缺能力事件，
因此本批没有解析错误文本或接入线上请求；上游必须先增加稳定、版本化的能力类型信号。

### C5：界面与真实机器门禁

- 原生预检页展示复用、下载、磁盘占用和按需组件；
- 全新 Mac、已有受管环境、Homebrew 环境、损坏缓存和离线恢复矩阵；
- 继续验证 Hermes-first、唯一 Connector、账号绑定、Android REST/WebSocket/斜杠命令和回滚；
- 精确候选包记录首次下载、完整功能下载、安装后占用与冷启动时间。

C5 第一批先建立不改机器状态的可信预检协调器。它只接受严格验签后的 v2 清单，重新核对基础拓扑，
逐项检查受管仓库的收据、完整内容身份和健康探针，再运行固定路径外部环境扫描。Python 与 Node 即使
版本相同也只作为本机观察结果；只有带签名兼容合同并通过 Desktop 探针的系统浏览器可以进入复用
决策。结果同时给出每项复用、基础下载或首次使用时下载，以及两类下载总字节数。已存在但健康失败
的受管组件会在外部扫描前阻断，避免界面显示一个安装器无法安全覆盖的“可下载”状态。该结果尚未
接入现行安装页，也不创建目录、下载文件或更改服务。

C5 第二批把可信结果转换为独立的原生预检卡片。卡片固定展示目标版本、直接复用数量、首次下载和
按需下载总量，并逐项区分受管复用、兼容系统复用、安装时下载和首次使用下载；所有字节数使用稳定
的二进制单位，避免系统区域设置改变含义。底部持续说明预检只读且不会修改 Homebrew、用户环境或
运行中的服务。中英文展示模型由单元测试覆盖，SwiftUI 卡片已进入应用编译，但在生产 v2 清单、
签名键和能力开关完成前不接入现行安装页面，也没有可执行的下载按钮。

C5 第三批补上卡片之前的可信预检运行时。它只接受固定 HTTPS 清单地址、严格 v2 Ed25519 验签器和
只读扫描器，按“有界下载清单 → 验签 → 扫描本机”的顺序执行；下载或验签失败时不会开始本机扫描，
同一运行时的并发刷新也只允许首个请求。运行时返回完整预检结果供展示模型消费，不下载组件、不创建
安装工作区、不写凭据也不改变服务。生产 v2 地址、信任配置和能力开关仍未加入，因此现行安装页面和
发布包保持不变。

C5 第四批增加与现行 v1 安装清单相互独立的配置门。`HERMES_GO_COMPONENT_PREFLIGHT_ENABLED`
默认关闭；只有显式为 1、提供单独的 v2 组件清单 HTTPS 地址，并且现有发布源、频道、架构、签名键
标识和 Ed25519 公钥全部有效时才形成可信配置。启用值异常、缺字段、非 HTTPS/含凭据或歧义路径的
地址、非规范 base64url 公钥都 fail closed。普通发布包继续写入 false 和空 v2 地址；本批只让下一步
能够安全构造预检运行时，尚未启动网络、扫描或界面展示。

C5 第五批把配置门、可信运行时、受管组件扫描和原生卡片接到 Desktop 状态。默认配置下不构造
运行时、不发网络请求也不扫描文件；完整启用后，账号启动完成及用户主动刷新时才下载并验签 v2
清单，成功后在现行安装卡片之前展示只读结果。受管复用除完整内容身份外，还要求签名入口仍位于
组件根内，是当前用户拥有、不可被组或其他用户写入的普通可执行文件。预检不会执行 Hermes 或
Connector，避免只读页面启动服务；运行级 readiness 继续由安装与激活门完成。任何配置、下载、
验签或扫描失败都不显示可操作卡片，也不会进入安装、LaunchAgent 或服务变更。

C5 第六批先把 v2 基础组件安装器拆成确认边界明确的 `prepare → commit`。`prepare` 只在 owner-only
缓存工作区下载、校验并解压缺失组件；不会写入组件仓库或发布版本引用。它返回的不可伪造准备令牌
只允许原安装器提交或取消。`commit` 在确认后重新计算每个暂存树的完整内容身份和入口健康状态，再
逐项写入不可变组件仓库，全部通过后才原子发布版本引用与激活计划。运输中断只保留符合签名文件名、
大小和私有权限约束的 partial；已完成归档与解压树会被清理并在重试时重新验证。现有一阶段调用改为
内部顺序执行这两步，保持调用方兼容。本批尚未给预检卡片增加下载或安装动作，也不改 LaunchAgent、
凭据或服务。

C5 第七批把同一次可信预检保留为不可伪造会话：运行时完成有界清单下载、Ed25519 验签和只读扫描后，
同时返回展示结果与验签器产生的安装令牌。界面继续只消费展示结果；后续 `prepare` 只能消费该令牌，
不需要从版本号、下载地址或界面行重新拼装安装权限。兼容的 `load` 仍只返回普通结果，现有调用行为
不变。本批只建立预检到准备阶段的信任传递，没有接入按钮、工作区、组件提交或服务变更。

C5 第八批把可信预检、私有缓存准备、精确确认、组件提交和持久化迁移入口收敛到一个默认未接线的
状态机。准备阶段只接受同一会话里的展示结果与验签令牌，并继续保证组件仓库、凭据、LaunchAgent、
绑定和进程零改动；确认文本或准备句柄不匹配时也保持该状态。精确确认后才重新核验并提交四个基础
组件，再从返回的内容寻址激活计划生成固定 Python/Node 根的 LaunchAgent 配置并调用唯一迁移边界。
取消和失败删除本次私有工作区；传输中断发生在准备句柄返回前，也只能经有效 UUID/marker 清理入口
删除。若迁移随后失败，已提交内容与版本引用仍是未激活的安全缓存，可供重试或 GC。迁移已成功但
临时清理失败时返回单用途清理句柄，不能把成功误报为回滚。现有 v1 日志的
中断恢复仍假定 `current` 版本软链接，因此实际 v2 迁移适配器、日志模式字段和恢复实现必须下一批一起
完成；在此之前不接安装按钮，也不改变生产配置、服务或发布物。

C5 第九批先升级持久化迁移日志，使恢复流程不再根据当前磁盘内容猜测安装布局。新日志 schema 2
要求每个 run 固定记录 `bundled_release` 或 `component_store`；同一 run 更换布局会与版本、绑定身份
不匹配一样被拒绝，所有状态迁移都保留该字段。已经安装的 schema 1 日志严格按历史
`bundled_release` 解释，并在下一次合法状态转换时原子升级；schema 1 夹带新字段、schema 2 缺字段、
未知布局或未知 schema 都 fail closed。这一批不改变现有 v1 迁移/恢复分支，下一批由 v2 适配器按
日志字段选择是否撤销 `current` 软链接。安装按钮、服务、生产配置和发布物仍不改变。

C5 第十批实现默认未接线的 v2 持久化迁移适配器。它在进入账号绑定或本机持久化前核对清单与激活
计划的版本、组件集合、内容身份和入口路径，随后复用既有操作锁、账号绑定、Hermes-first、双重健康
证明、远端确认与自动回滚流程。组件路径直接写入已经重新验真的内容寻址入口及固定 Python/Node 根，
不会暂存 v1 整包、创建版本目录或切换 `current`；会话令牌合同标记也按该激活计划验证 LaunchAgent。
失败回滚和断电恢复根据日志布局保留任何无关的 v1 `current`，只有 `bundled_release` 才撤销对应软链。
现有 v1 迁移顺序和恢复语义保持不变。本批仍不接安装按钮，不改变生产配置、运行服务或发布物。

C5 第十一批将 v2 可信预检、组件安装器、迁移适配器、日志、精确 LaunchAgent 控制器和提交配置组合
为一个正式运行时。构造运行时仍是惰性的：不会创建受管根、缓存、LaunchAgents 或 Hermes Home，首次
网络与只读扫描只会在调用预检后发生，组件仓库及服务变更仍只能由同一运行时签发的准备句柄在精确
确认后进入。运行时单独接收 v2 发布信任配置和冻结的 Hermes 运行合同，避免从展示行或 v1 清单重建
安装权限。生产 v2 能力信号和 UI 动作仍留在后续批次，因此默认包行为不变。

C5 第十二批增加独立、默认关闭的 Cloud 能力信号。现有 v1
`desktopBootstrap.runtimeContract` 不再被当作组件安装授权；只有账号绑定、现有受管安装门和新的
`ACCOUNT_DESKTOP_COMPONENT_INSTALL_ENABLED` 同时开启时，Gateway 才额外声明
`componentManifestSchemaVersion: 2`。Desktop 将该字段传入单独的 fail-closed 可用性判断，要求本地
v2 配置有效、schema 精确为 2 且运行合同精确为 `hermes-serve-v1`。缺字段、未来 schema 或合同不匹配
都不能进入组件运行时或发起 v2 清单请求，已显示的只读结果在能力撤回或退出账号时清除。生产运维尚
不接纳新开关，UI 安装动作、服务和发布物仍不改变。

C5 第十三批把已通过双重能力门的界面预检切换到正式组件运行时。每次成功刷新会在内存中同时保留
展示结果和同一次 Ed25519 验签产生的不可伪造安装令牌；刷新失败、能力撤回或退出账号会一起清除两者。
异步刷新完成时会再次检查能力门，避免撤回期间启动的旧请求重新发布结果。界面仍只显示普通预检模型，
不能从版本号、大小或组件行重建安装权限。运行时构造保持惰性，本批没有
安装按钮，不创建下载工作区，不提交组件，也不修改凭据、LaunchAgent、绑定、进程、生产配置或发布物。

C5 第十四批把可信会话接入预检卡片的两阶段安装动作。只有组件预检与本机迁移预检同时可用时才显示
“下载缺失组件”；开始准备前刷新 Cloud 能力并复查本机，准备阶段只写 owner-only 缓存。原生确认页展示
精确签名版本与确认文本；提交前再次刷新能力和复查服务，随后才允许组件提交、账号绑定、Hermes-first
启动、双重健康证明和回滚事务。v1/v2 安装、账号操作和手动刷新互斥，避免两条迁移同时运行。准备失败
主动清理本次 UUID 工作区；清理未完成或提交成功后的临时清理失败只保留精确单用途重试，不会重新安装。
Gateway 已选择 schema 2 且本地 v2 配置存在时，旧 v1 下载按钮不会作为验签或扫描失败后的隐式回退；
失败显示结构化错误并保留刷新重试。
所有可见失败继续映射现有 `HR-MIGRATE-001` 至 `HR-MIGRATE-005`。生产能力位和默认包配置仍关闭，本批
不部署、不运行安装，也不生成发布物；真实签名包与干净 Mac 流程留作发布前人工验收。

任何阶段都不授权生产发布。Developer ID、公证、stapling 和干净机器启动仍按 Desktop 发布门禁
单独完成。
