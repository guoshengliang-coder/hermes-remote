# Hermes 兼容版本管理与本机升级迭代规划

日期：2026-10-25。状态：用户已批准持续实施；I0 发现真实锁协议缺口，I1–I3 已有本地实现，I4/I5 未完成。未通过的迁移路径不开放升级，详见实施记录。

执行证据与尚未通过的门禁见 [实施记录](HERMES_COMPATIBILITY_EXECUTION.md)。分期完成必须以实际验收为准。

目标是让管理员在 Desktop 发起验证、查看证据、批准或撤回 Hermes 推荐版本，让普通用户根据本机条件升级到最新的已验证兼容版本，并能在失败时恢复。兼容实现由开发者或 AI Agent 编写，测试系统提供证据，管理员负责发布决策。

本规划不授予管理员权限、不启动定时任务、不修改现用 Hermes、不部署服务。后续实施、客户端发布及生产启用分别按仓库既有流程推进。

## 1 产品决策与首版边界

- 继续遵守一台 Mac 使用一份用户 Hermes 的原则；保留用户主动通过官方工具更新的能力。兼容清单约束 GO 的推荐与一键升级，不夺取用户对版本的控制权。
- 管理员入口名称为“**Hermes 兼容版本管理**”。入口只对服务端授权的账号显示，所有管理 API 独立鉴权。
- 初始管理员指定为 `guoshengliang@gmail.com` 对应的已验证现有账号。实际权限绑定稳定 account ID；实施时通过受控操作核实绑定，不按客户端提交的邮箱自动提权。
- 第一版跟进官方稳定发布，仅支持经实际演练的一种 macOS 架构和安装类型。首先以用户当前安装的真实布局为样本，不能仅凭界面上的版本号推定其为旧 venv 或新版 PM。
- 普通用户默认只能通过 GO 升级到符合其安装与组件组合的已发布推荐目标。尚未验证的上游版本仍可展示；高级未验证升级入口列为后续范围。
- 第一期就验证真实升级和恢复的可行性。管理员页面、测试数量、源码审计都不能代替完整升级结果。
- 不承诺任意未来协议自动兼容，也不承诺开始使用新版后任意无损降级。

## 2 当前基础与缺口

规划参考仓库 `origin/main` 的快照 `4ba4505f66b34dca85215aa51bcbbef4a4f4654e`。这不是对任何机器当前安装版本的断言。

| 已有基础 | 可复用部分 | 还缺什么 |
|---|---|---|
| HG-199 只读版本管理 | 官方发布查询、版本与 commit 展示、条件检查、记录读取 | 可用执行器、真实恢复路径和已发布推荐记录 |
| Desktop 账号系统 | 邮箱登录、会话、设备绑定和既有管理请求 | 独立于设备 owner/operator 的全局兼容管理权限 |
| Desktop 与组件发布 | 版本化产物、签名清单、索引、发布回读 | 独立的兼容清单 schema、审批与发布流程 |
| 上游契约文档和客户端测试 | 已消费的 REST/RPC、解析器样本和回归 | 可重复的真实 Hermes 版本与升级矩阵 |
| HG-199 草稿原型 | 部分备份、记录、故障测试和协调经验 | 正式入口可行性、真实机器采集和恢复；不能整体视为已交付 |

现有受管安装存在历史布局；组件清单与本机 Hermes 安装不能视为同一个版本对象。兼容规划需要识别二者，但本项目首版不强迫所有用户先迁移组件布局。

## 3 职责与执行位置

| 角色或系统 | 职责 | 不承担的能力 |
|---|---|---|
| 兼容管理员 | 发起验证、审阅报告、批准推荐、撤回推荐、查看审计 | 点击“支持”不能覆盖失败证据，也不能生成兼容代码 |
| 开发维护者或 AI Agent | 分析差异、编写适配与回归、按流程交付组件更新 | 不因代码合并就自动认证 Hermes 版本 |
| 验证任务服务 | 固定任务输入、排队、派发 CI、收集结果、关联报告 | 不任意执行管理员输入的命令 |
| 隔离测试执行器 | 安装与升级测试 Hermes、模拟故障、验证核心业务 | 不默认使用管理员日常 Mac、真实用户数据或生产凭据 |
| 受保护发布任务 | 校验证据和审批、签名、上传、回读、切换推荐索引 | 私钥不下发 Desktop 或测试执行器 |
| 普通 Desktop | 验证清单、匹配目标、发起本机升级和恢复 | 不负责自动发明协议适配 |

首版一个管理员可以同时发起和批准任务，不强行引入多人审批。测试结果不可由管理员手填“通过”；人工验收项必须附记录并明确范围。

管理动作继续使用既有账号服务。CI 派发凭据放在服务端受限执行边界，Desktop 不持有 GitHub 管理令牌。验证任务无发布密钥；运行上游代码的测试环境与签名发布环境分离。

## 4 记录模型与推荐规则

### 4.1 分开管理四类记录

| 记录 | 必需内容 |
|---|---|
| 上游版本 | 官方仓库、版本、tag、解析后的固定 commit、发现时间；tag 改指向时生成异常，不覆盖旧身份 |
| 验证任务与报告 | run ID、Hermes commit、GO 源提交与产物版本、测试套件版本、平台与安装类型、升级来源、逐项结果和证据引用 |
| 兼容决策 | 支持范围、已知问题、客户端要求、升级和恢复范围、绑定报告摘要、批准人及时间、修订号 |
| 发布快照 | 单调递增的清单修订号、不可变内容及摘要、签名身份、发布时间、推荐状态、撤回原因 |

不能用一个 `supported=true` 表达所有组合。已验证“新版全新安装可用”与已验证“某类旧安装可以升级”是两个结论。

组件要求最初按实际测试过的组合记录。需要扩大成版本范围时必须有依据；只给最低版本号不意味着所有未来版本自动兼容。客户端版本缺失或未知时显示“无法确认”，不能当作满足条件。

仓库保存 schema、测试和政策；数据库保存任务、审批和审计；普通客户端以已经签名发布的不可变快照为准。草稿修改不会直接改变线上推荐，不引入两个可以各自生效的清单来源。

### 4.2 状态和匹配

- 验证任务：排队、运行、通过、失败、基础设施异常、取消。环境失败与产品不兼容分开记录。
- 兼容结论：未验证、已验证、有限支持、已知不兼容。
- 发布状态：未发布、发布中、已发布、发布失败、已撤回。测试通过不直接等于已推荐。
- 选择顺序：验签及清单有效性 → 排除撤回目标 → 匹配平台和安装身份 → 匹配升级来源 → 匹配 GO 组件组合及核心能力 → 选择符合条件的最高稳定版本。
- 必须先更新某个组件时，展示有序步骤；必要组件尚未正式发布时，不允许把目标标为可执行。
- 已运行比推荐更高的 Hermes 时，不自动降级。报告实际版本及验证状态，保留正常功能。
- 多个手机或 Web 客户端版本无法完整确认时，明确显示已验证组合和未知客户端；不能声称全部客户端已兼容。升级前说明已知不兼容的旧客户端。

### 4.3 清单失效与撤回

签名正确不代表清单足够新。缓存可供查看；新升级开始前需要在定义的新鲜度范围内确认推荐未撤回。断网或无法确认时保留服务，暂停新的升级，不把正常运行标为损坏。

审批绑定精确报告和决策内容摘要。目标、依赖或限制改变后原审批失效。重复点击不能重复发布；陈旧页面不能覆盖新决策。开始变更前再次检查清单；升级已经开始后收到撤回，不能粗暴杀掉更新，应完成安全收尾并提供后续处理。

## 5 分期实施

### I0 验证执行路径与冻结首版范围

**用户结果：** 明确当前这类安装到底怎样可靠地升级，有真实结果支撑后续界面。

工作项：

1. 清点当前标准安装身份、入口、依赖管理方式、受影响服务及更新锁；不操作日常服务。
2. 在一次性用户环境或测试 Mac 复现该安装类型和合成历史。固定官方目标，评估公开 CLI 或机器接口的目标选择、备份、停写、更新、恢复和结果能力。
3. 完成一次真实更新与至少一次失败恢复，核对磁盘与运行版本、原配置、旧历史及新写入。覆盖旧 venv 到 PM 的首次迁移时，把它作为独立路径。
4. 对比 HG-199 原型，列出复用、替换、移除清单。不得以“未修改上游源码”为理由继续无界依赖内部函数。
5. 冻结首版支持矩阵、核心功能清单和官方接口缺口。若公开入口不能精确执行展示目标，选择有界的上游接口补齐任务；不得展示稳定版本却更新到移动的 main，也不得再次整体实现私有更新流程。

验收：留下可重跑命令/脚本、固定输入、实际运行证据及恢复结果；所有关键缺口有明确任务。只有缺口说明时 I0 标记未完成，不能宣布升级链路可用。

负责人：Desktop/升级维护者；用户作为产品负责人确认首版支持范围。后续 I1、I2 可在范围冻结后并行推进，执行团队是否并行由实施阶段安排。

### I1 管理员权限与兼容记录基础

**用户结果：** 指定账号可以管理验证候选，普通账号没有管理权限。

工作项：

1. 增加服务端兼容管理角色和逐请求授权，复用账号 session；角色与设备拥有/分享权限分离。
2. 提供受控的初始角色授予与撤销操作，核实指定邮箱对应的已验证 account ID。第一版不建设通用 RBAC 或多人组织后台。
3. 建立上游候选、验证任务、报告、决策、审计数据和 API；为副作用定义幂等与并发版本检查。
4. Desktop 增加管理员专属入口：版本列表、详情、报告占位与权限状态。暂不可把空报告确认成支持。
5. 给普通页面修正文案：功能未开放、条件不满足、未验证和已知不兼容分开表达。

验收：普通账号直接调用管理 API 仍被拒绝；客户端伪造邮箱无效；角色撤销后旧 session 不能继续管理；邮箱变化不会自动给另一个账号管理员权限；重复和并发操作有测试；审计可追溯。

涉及：Gateway 账号层、数据库迁移、Desktop；更新账号 API/安全文档、Desktop 设计/测试文档和错误码表。此期完成不代表升级功能完成。

### I2 隔离验证流水线与失败处理

**用户结果：** 管理员在 Desktop 点“开始验证”，得到真实、可解释的报告。

工作项：

1. 管理员手动同步官方稳定发布并派发固定目标任务；后续自动同步使用同一入口。
2. 服务端派发固定 workflow 和受限参数，展示排队、阶段、耗时、结果与脱敏日志；禁止任意脚本/路径输入。
3. 重用 I0 的真实执行脚本，增加核心 REST/RPC、解析与展示样本、历史、配置、升级和恢复测试。
4. 在隔离 Mac 上验证真实依赖、LaunchAgent、端口释放、鉴权和 Connector 连接。模拟模型可用于确定性协议测试，真实模型/设备验收另记，不得将模拟通过标为全面真实验证。
5. 报告绑定目标 commit、GO 代码/产物和测试版本。源码或产物变化后必须重验受影响范围。结果回传认证、重复/伪造/跨 run 回传拒绝；CI 不可直接写推荐。
6. 失败分为环境问题、安装/恢复问题、核心不兼容、可选功能不兼容。管理员可重跑或查看修复任务；开发者/Agent 进行 coding、回归及组件发布。

验收：从 Desktop 发起并完成一轮真实测试；故意制造一个协议不兼容和一个基础设施失败，报告正确区分；报告不能越过目标或被旧结果覆盖；失败结果不能被点击改成通过。

基础设施：需要可隔离重置的 macOS 执行环境，复用现有 CI。没有 macOS/物理设备证据的范围标为待验收，不能认证该范围。

### I3 管理员批准与推荐清单发布

**用户结果：** 管理员可以批准有证据的版本，普通 Desktop 能获得适合本机的推荐。

工作项：

1. 管理页面显示固定版本、验证范围、组件要求、已知限制、报告链接与发布影响。
2. 通过的必需检查与必要人工验收齐全后，允许批准；限制范围外的结论不能由自由文本扩大。核心失败不能用“有限支持”绕过。
3. 审批提交给受保护发布任务，复用现有签名信任与发布回读机制，增加独立兼容快照和索引；不覆盖现有 app/组件索引。
4. 私钥继续只在受保护签名系统；若信任配置需要升级，先发布能验证新清单的 Desktop。既有发布环境审批在迁移完成前仍保留，页面应显示真实待批准状态。
5. 公开下载并核对签名、内容和修订号后才显示“已发布”。任务崩溃可重试，上传成功而索引切换失败不能显示成功。
6. 实现撤回、审计、并发控制、缓存与重放保护。撤回发布新修订，保留历史，不自动修改已安装 Hermes。
7. 普通 Desktop 显示上游最新和 GO 推荐两种结果，明确组件前置条件；升级执行尚未交付时如实标记。

验收：完成批准—发布—普通客户端匹配—撤回全流程；坏签名、旧修订、过期缓存、陈旧审批、重复点击和网络失败均有明确行为。清单更新无需重发 Desktop，新增适配代码仍须发布对应组件。

### I4 本机一键升级与失败恢复

**用户结果：** 对首版支持的安装，点击一次确认即可完成已推荐目标升级。

工作项：

1. 复用 I0 正式路径，串联安装匹配、当前推荐复核、依赖前置条件、用户确认、维护排空、恢复点、官方更新、服务恢复和最终验证。
2. 确定上游与 Desktop 的单一服务操作责任，互斥于安装、修复、Connector 更新和外部 updater；仅变更必要服务，不重新绑定账号。
3. 升级前验证恢复点覆盖代码、依赖和一致的数据/配置；只备份不恢复过，不能宣称可恢复。原型中 home 外依赖是否可重建必须明确。
4. 真实执行进程和持久记录承接 UI 生命周期。关闭页面不杀更新；Desktop 重开可关联原操作。阶段反映可证明的结果，不编造进度百分比。
5. 准备阶段可取消，发生变更后的取消按官方能力安全收尾；支持更新失败、服务恢复失败、连接失败的不同操作。
6. 提交成功前核对实际运行版本、依赖、鉴权、历史可读与受管连接。升级后的客户端核心业务以隔离验收和实际设备记录共同覆盖。
7. 新版尚未恢复业务写入时，可沿已验证路径回到升级前恢复点。新版已产生新数据时禁止静默覆盖数据库；优先继续修复，并保留当前数据供明确的恢复选择。

验收：从实际安装的 Desktop 点击升级成功；至少覆盖断网、依赖失败、进程中断、Desktop 退出重开、启动失败、外部更新冲突及恢复后重试；原账号绑定、模型配置和旧历史保留。新版运行后新增数据不被恢复操作静默丢弃。

限制：第一版不提供任意降级，不接管无法识别的第三方进程。外部服务无法安全排空时给出具体处理动作。若 I0 路径需要上游补齐接口，完成该依赖后再验收 I4。

### I5 首个推荐版本上线与持续维护

**用户结果：** 管理员能完成日常版本维护，普通用户实际使用推荐升级。

工作项：

1. 对首个候选完成 I2 验证、必要 coding、组件发布和复验；I3 批准推荐，I4 在选定测试设备完成真实升级验收。
2. 验证一轮撤回推荐和故障处理；撤回不强制降级、不终止已进入变更阶段的更新。
3. 先管理员测试设备，再少量明确参加测试的设备，最后扩大推荐范围；每批有独立证据，不凭管理员批准扩大未测试平台。
4. 配置周期发现或 release 事件触发、重复任务去重、超时和失败通知。推荐发布继续需要管理员确认；明确唯一主发现机制，避免重复调度。
5. 记录维护负责人、待验证队列、已知问题、支持范围和处理优先级。默认优先最新稳定候选与当前用户升级路径；开发分支不进入首版推荐。
6. 明确发布所需的 Cloud、Desktop、Connector、Android/Web 版本及顺序，按各自发布门禁执行。

验收：管理员从发现候选到发布、普通用户从推荐到实际升级的完整流程完成一次；版本、历史、配置、连接和手机/Web 核心业务均有实际记录。未执行的范围明确保留为限制。

## 6 排序与交付门槛

依赖：`I0 → I1/I2 → I3`；`I0 + I3 的清单消费合同 → I4`；`I1–I4 → I5`。I4 执行代码可以在清单合同冻结后开发，但不能在已验证目标和正式清单就绪前开放普通升级。

| 门槛 | 可宣布的完成结果 | 不可替代的证据 |
|---|---|---|
| G0 执行可行 | 首条升级路径成立 | 真实升级及失败恢复 |
| G1 管理可用 | 管理员可发起验证并发布推荐 | 服务端权限、真实报告、签名清单与客户端回读 |
| G2 用户可用 | 用户可点击完成升级 | 安装客户端实测、数据与业务验收 |
| G3 持续维护 | 新版本可持续纳入或撤回 | 一轮发现、适配、验证、审批、发布、撤回演练 |

I1–I3 是管理功能里程碑，不能被称为“升级功能交付”。项目首个完整交付截止于 I5/G2，G3 持续运行。I0 完成前不承诺总工期；I0 结束根据官方接口缺口、测试机能力及需适配客户端重估排期，避免以测试数量估算真实升级进展。

## 7 开发与测试共同要求

- 每个迭代实施前做测试影响和错误码评审；可测试缺陷先补失败回归。所有用户失败使用已注册 HR 码、中文/英文摘要、可重试性及恢复动作，日志脱敏。
- Gateway/Connector/Protocol 运行构建与测试；账号权限和任务状态必须覆盖真实数据库集成。协议变更同时说明 Android/Desktop/Web 消费影响。
- Desktop 运行 assets、Swift 测试、app 打包；管理员与普通账号 UI 做原生检查。正式签名/公证和内部临时签名渠道按现有政策分别验收。
- Android/Web 按受影响功能运行组件基线和要求的设备层验证；云端“手机可访问”指示不能代替实际手机发送、审批或附件测试。
- 验证范围覆盖旧历史、合成新历史、真实依赖、真实 macOS 服务及故障恢复；不把注入 runner 的测试报告为真实进程恢复。
- 不把测试机模型密钥、用户历史、完整本机路径、会话内容或上游原始错误直接上传管理台。报告保存必要的版本、阶段、检查结果及脱敏证据。
- 兼容审批不授权客户端源码合并、组件发布或 Cloud 部署；这些遵循既有集成门禁。只有已发布并可取得的前置组件才能进入普通升级方案。

## 8 界面与首批任务拆分

普通“本机 Hermes”页面保留：当前安装/运行版本、上游最新、适合本机的推荐、前置更新、升级进度、结果与恢复入口。

管理员入口包括：候选版本列表、版本详情、验证任务与报告、支持范围和已知问题、批准发布、撤回及审计。首版不建设通用组织后台、任意命令控制台或管理员远程升级用户机器的功能。

首批任务按下表建立；编号是本规划内编号，尚未创建外部工作项。

| 编号 | 任务 | 依赖 | 完成产物 |
|---|---|---|---|
| HC-01 | 当前安装类型与官方更新入口审计 | 无 | 固定输入、能力缺口、首版范围 |
| HC-02 | 真实升级及失败恢复演练 | HC-01 | 可复跑脚本和证据，I0 验收 |
| HC-03 | 管理员与记录/API 合同 | HC-01 | 授权、schema、状态及测试设计 |
| HC-04 | 服务端权限与 Desktop 管理入口 | HC-03 | I1 验收 |
| HC-05 | 隔离任务派发与结果回收 | HC-02、HC-03 | I2 流水线与报告 |
| HC-06 | 审批、签名发布、撤回和目标匹配 | HC-04、HC-05 | I3 验收 |
| HC-07 | 正式执行器与恢复接入 | HC-02、HC-06 合同 | I4 验收 |
| HC-08 | 首个候选的差异适配与发布 | HC-05 的失败结果，按需 | 对应组件产物与复验 |
| HC-09 | 管理员及普通用户端到端验收 | HC-06、HC-07、必要的 HC-08 | I5 首次真实交付 |
| HC-10 | 周期发现、维护与撤回演练 | HC-09 | 可持续运行机制与操作文档 |
